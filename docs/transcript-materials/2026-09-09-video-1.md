## Kontrolleri klass ja dispetšer — `0:01:10` {#kontroller-ja-dispetser}

Kontrolleri (controller) klassil on **üks ja ainus eesmärk**: siia kirjutatakse veebiteenused ehk **endpoint'id**, mida me ise koodist kunagi välja ei kutsu. Terves ülejäänud koodis on meie "näpujäljed" — me ütleme sõna otseses mõttes "käivita see meetod, siis too meetod". Kontrolleris on aga meetod, mida **meie käivitada ei saa**, kuid saab keegi teine.

See "keegi teine" on **dispetšer** (Springis `DispatcherServlet`). Kui veebist tuleb päring (kõne) sisse, siis dispetšer vaatab, kellele see kuulub, ja käivitab õige kontrolleri meetodi.

### Skeem

```text
Brauser / väline süsteem
        │  HTTP-päring  (nt POST /api/login)
        ▼
   DispatcherServlet  ("dispetšer")
        │  leiab õige klassi + meetodi
        ▼
   LoginController.loginUser(...)      ← seda meetodit kutsub AINULT dispetšer
        │  delegeerib edasi
        ▼
   LoginService.loginUser(...)         ← siit algab meie "päris" kood
```

### Päriselu analoogia

Dispetšer on nagu telefonikeskuse operaator. Keegi helistab sisse ("saada telegramm sõnumiga: minu kasutajanimi ja parool"), operaator kuulab ära ja suunab kõne õigesse osakonda. Sina ise operaatorit ei käskluta — sa lihtsalt helistad ja tema teeb ülejäänu.

## `@RestController` ja `@PostMapping` — kuidas dispetšer meetodi leiab — `0:02:50` {#restcontroller-mapping}

### Selgitus

`@RestController` on Spring Webi teegi annotatsioon. Klassi peale pandult annab see klassile "erilised võimed": dispetšer teab nüüd, et **sellesse faili tuleb üldse sisse vaadata** ja otsida sealt kaardistusi (mapping'uid). Ilma selle annotatsioonita dispetšer seda faili ei vaataks.

Aga kuidas dispetšer teab, **millist** meetodit mingi konkreetse päringu peale käivitada? Selleks on **mapping-annotatsioonid**: `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` (üldnimena `@RequestMapping`). Neis on kaks poolt:

- **HTTP-meetod** ütleb, **mis tegevus** see on — anna andmeid (GET), lisa (POST), uuenda (PUT), kustuta (DELETE);
- **URL** defineerib **subjekti / ressursi** — millest jutt käib.

Need kaks poolt koos määravad üheselt ära, milline meetod käivitub.

### Koodinäide (`backend/.../controller/LoginController.java`)

```java
@RestController                       // dispetšer, vaata sellesse klassi sisse
@RequiredArgsConstructor
public class LoginController {

    private final LoginService loginService;

    @PostMapping("/api/login")        // POST + /api/login  →  see meetod
    public void loginUser(@RequestBody LoginRequest loginRequest) {
        loginService.loginUser(loginRequest);   // ei tee ise midagi — delegeerib
    }
}
```

Kui sisse tuleb `POST /api/login`, teab dispetšer: käivita `LoginController.loginUser(...)`. `@RequestBody` ütleb lisaks: selle päringu kehas (JSON-is) on kaasas objekt, mille sa pead mulle üle andma `LoginRequest`-ina.

### Päriselu analoogia

`@RestController` on silt ukse peal "Klienditeenindus — palun sisenege". `@PostMapping("/api/login")` on täpsem juhis seina peal: "Sisselogimise avaldused — see laud."

## Service klass — äriloogika omaette failis — `0:06:35` {#service-klass}

### Selgitus

Kui kontrolleri ainus ülesanne on sissetuleva päringu peale **mingi tegevus käivitada**, siis kus me selle tegevuse päriselt samm-sammult ära programmeerime? **Service klassis.**

Videos võrreldakse teenindajaga: service on "kelnerpoiss", kes jookseb edasi-tagasi, toimetab ja **delegeerib omakorda** töö edasi (nt repositooriumile). Kogu tegelik äriloogika — kõik sammud algusest lõpuni — elab siin.

### Koodinäide (`backend/.../service/LoginService.java`)

```java
@Service
@RequiredArgsConstructor
public class LoginService {

    private final UserRepository userRepository;

    public void loginUser(LoginRequest loginRequest) {
        Optional<User> optionalUser = userRepository.findUserBy(
                loginRequest.getUsername(),
                loginRequest.getPassword(),
                "A");
        // ... edasine äriloogika: kas leiti? mis roll? jne
    }
}
```

### Päriselu analoogia

Kontroller on nagu restorani administraator, kes võtab tellimuse vastu ja hüüab köögi poole. Service on kokk, kes teeb roa päriselt valmis — võtab retsepti, käib sahvris, segab, praeb.

## Meetodinimed kanduvad kihtide vahel edasi — `0:08:21` {#meetodinimed}

### Selgitus

Kui vaadata nelja kasti (Controller, Service, Repository, Mapper) ja iga kasti sees olevate meetodite nimesid, siis torkab silma: **kontrolleri ja service'i meetodil kipub olema sama nimi**.

Tehniliselt **ei pea** nad sama nime kandma. Aga oleks väga imelik, kui kontrolleris nimetame tegevuse `loginUser` ja service'is kutsuksime hoopis `findCities`. Tegevus **jätkub** ühest kihist teise — äriloogiline nimi kandub lihtsalt edasi. Kui esimene meetod on `findUser`, siis järgmine ei saa olla `updateLocations`.

### Skeem

```text
LoginController.loginUser(...)   ─delegeerib→   LoginService.loginUser(...)
        sama äriloogiline tegevus, sama nimi
```

### Päriselu analoogia

Teatejooks: teatepulk (tegevus) antakse edasi, aga jooksjad ei vaheta pulka äkitselt õunaks. See on kogu aeg sama pulk.

## Miks kihid on eraldi failides (huvide lahusus) — `0:10:19` {#huvide-lahusus}

### Selgitus

Tegevust **ei saagi** kontrollerisse kirjutada. Kui kogu loogika oleks ühes failis, siis fail lihtsalt paisub. Erinevatel pooltel on **erinevad huvid** ja me tahame asju eraldada — mitte hoida kõike ühes koodifailis.

Boonus: kui ma puutun kokku mingi veebiteenusega, saan läbi kontrolleri kohe üles leida, **kus see teenus algab** ("stardipauk"). Kontrollerid on eraldi kataloogis, service'id eraldi. Iga teenuse alguspunkti leian kiiresti üles, aga tegelik mahukas action on mujal.

### Päriselu analoogia

Maja plaan: köök, magamistuba ja vannituba on eraldi ruumid, mitte kõik ühes toas. Kui otsid kraanikaussi, tead kohe, millisesse ruumi minna.

## Repository kui "uks" ühte kindlasse tabelisse — `0:11:52` {#repository-uks}

### Selgitus

Service ei räägi andmebaasiga otse — ta käib läbi **repositooriumi**. Repository ei ole "üldine andmete klass". Ta on **üks konkreetne uks ühte konkreetsesse tabelisse**.

`UserRepository` on uks `user`-tabelisse. Kui oleks `CityRepository`, oleks see uks `city`-tabelisse. Iga uks viib ühe temaatilise andmehulga juurde — mitte "andmebaasi", vaid ühe kindla tabeli juurde.

### Skeem

```text
LoginService
     │
     ▼
UserRepository  ──uks──►  tabel  bank."user"
CityRepository  ──uks──►  tabel  bank.city
RoleRepository  ──uks──►  tabel  bank.role
```

### Päriselu analoogia

Restoranis on supihoidla uks, magusahoidla uks ja burksihoidla uks. Iga uks viib ühte kindlasse lattu. Ei ole olemas üht "toiduust", mille tagant tuleks suvaline asi.

## Objekti poole pöördutakse ainult muutuja (sildi) kaudu — `0:12:31` {#muutuja-silt}

### Selgitus

Kõik need meetodid (`loginUser`, `findUserBy` jne) on **objekti meetodid** (instantsi meetodid). Neid saab käivitada ainult **objekti kaudu**, ja objektini saab jõuda **ainult ühel viisil — muutuja (sildi) kaudu**.

Sellepärast ongi `LoginService`-s väli `private final UserRepository userRepository;` — see silt viitab `UserRepository` objektile. Ilma sildita ei saaks `userRepository.findUserBy(...)` kirjutada.

### Päriselu analoogia

Ma ei saa klassiruumis kellegagi rääkida, kui ma tema nime ei tea — eriti kui me kõik oleksime pimedad. Ainus võimalus pöörduda on nime (sildi) kaudu.

## `@Service` ja miks annotatsioon on kohustuslik — `0:14:07` {#service-annotatsioon}

### Selgitus

Mis juhtub, kui panna `@Service` service-klassi peale? Spring teeb runtime'is kuskil ise koodirea nagu `new LoginService(...)` — **tekitab sellest klassist objekti** ja paneb selle enda konteinerisse.

Kui `@Service` **puudub**, siis Springil ei ole sellest klassist ühtegi objekti. Ja kui kontroller vajab konstruktoris `LoginService` objekti, siis Spring ei leia konteinerist ühtegi sobivat kandidaati → rakendus ei käivitu.

`@Service`, `@RestController`, `@Repository` — kõik teevad sama põhiasja: annavad Springile märku "tee minust objekt ja hoia seda konteineris".

## Spring konteiner ja bean'id — `0:15:35` {#spring-konteiner}

### Selgitus

**Spring-konteiner** on koht, kus Spring hoiab enda tehtud objekte. Käivitamise hetkel ("bootimisel") teeb Spring iga stereotüübiga märgitud klassist objekti (`new LocationService()`, `new LoginController(...)` jne) ja paneb need konteinerisse. Sealt on nad **kättesaadavad üle kogu koodibaasi** vastavalt klassi tüübile.

Neid konteineris elavaid objekte nimetatakse **bean'ideks** (kohviubadeks).

### Skeem

```text
Rakenduse käivitus
        │
        ▼
 Spring loeb klassid, mille peal on @Component / @Service / @RestController / ...
        │
        ▼
 ┌─────────────── Spring-konteiner ───────────────┐
 │  LoginController-objekt                        │
 │  LoginService-objekt                           │
 │  UserRepository-objekt (Spring genereerib)     │
 │  ...                                           │
 └────────────────────────────────────────────────┘
```

### Päriselu analoogia

Konteiner on nagu ettevõtte töötajate nimekiri. Kui sind on tööle võetud (annotatsioon peal), oled nimekirjas ja igaüks saab sind projekti kaasata. Kui sind nimekirjas pole, siis sind pole olemas — keegi ei saa sulle ülesannet anda.

## `@Component` kõikide stereotüüpide taga — `0:16:43` {#component}

### Selgitus

`@RestController`, `@Service`, `@Repository` on kõik **erivormid** ühest ja samast asjast: nende kõigi taga on `@Component`. `@Component` tähendab: "sellest klassist peab tekkima objekt (bean)".

Iga annotatsioon lisab lisaks veel oma erivõimed (kontroller → dispetšer vaatab sisse; repository → andmebaasi-toega jne), aga põhituum on igal pool sama — tee objekt ja hoia konteineris.

Sa võid ka ise suvalise klassi peale `@Component` panna (nt mõni utiliit-teisendaja), kui tahad, et Spring sellest ühe objekti teeks ja seda halduks.

## Dependency Injection (DI) — sõltuvuste süstimine — `0:19:07` {#di}

### Selgitus

**DI = Dependency Injection = sõltuvuste süstimine.** See on mehhanism, mille abil Spring **meie eest** ühendab objektid omavahel kokku — me ei kirjuta ühtegi koodirida, kus ütleksime `userRepository = ...`.

Küsimus on: kuidas Spring **tehniliselt** saab need sildid (`private final UserRepository userRepository`) taha ühendada õige objekti? Vastus: **konstruktori kaudu**.

### Skeem

```text
Konteiner:  [ UserRepository-objekt ]
                     │
                     │  Spring annab selle konstruktorisse
                     ▼
      new LoginService( userRepository )
                     │
                     ▼
      LoginService-objekt, mille väli userRepository on nüüd ühendatud
```

## Konstruktor, `final` väli ja sõltuvuste järjekord — `0:20:50` {#konstruktor-final}

### Selgitus

**Konstruktor** on ainus mehaaniline viis, kuidas objekt saab sündida. Kui teeme konstruktori, mis võtab sisse `UserRepository` objekti, siis see ongi ainus tee `LoginService` objekti luua — ja Spring peab kaasa andma vajaliku objekti.

Väli märgitakse `final`-iks. `final` tähendab **konstanti**: objekt selle sildi taga ei saa kunagi muutuda, seotakse täpselt üks kord — ja just sel hetkel, kui klassist objekt luuakse. Kui `final` väli jääks väärtustamata, oleks see `null` ja täiesti kasutu — IDE-s süttib punane pirn "sul on vaja konstruktorit".

**Sõltuvuste järjekord.** Spring ei saa teha objekte suvalises järjekorras — ta peab need tegema "tagurpidi", alt üles:

### Skeem

```text
1. Mapper    — sõltuvusi pole            → objekt valmis
2. Repository — sõltuvusi pole            → objekt valmis
3. Service   — vajab Repository + Mapper  → nüüd saab teha
4. Controller — vajab Service             → viimasena valmis
```

`AtmLocationController` ei saa sündida enne, kui `AtmLocationService` objekt on olemas, sest konstruktor nõuab seda. Spring lahendab selle graafi ise ära — seni kuni me anname talle märku (annotatsioonid) ja vajalikud konstruktorid.

## Lombok `@RequiredArgsConstructor` — `0:24:29` {#lombok}

### Selgitus

Konstruktori kirjutamine käsitsi on tüütu boilerplate. **Lombok** teeb selle meie eest: `@RequiredArgsConstructor` genereerib konstruktori **kõikidele `final` väljadele**.

Vihje videost: "Jaava lemmik... Lombok" — annotatsioon, mis tasuks panna vähemalt igale klassile, millel on sõltuvus kellestki teisest.

**Miks mapper ja repository seda ei vaja?** Nemad ei suhtle ühegi teise objektiga — neil pole `final` sõltuvusvälju. Service räägib repositooriumi ja mapperiga, seega **service vajab** konstruktorit. Mapper ise ei suhtle enam kellegagi, repository samuti mitte → neil pole vaja `@RequiredArgsConstructor`-it.

### Koodinäide

```java
@Service
@RequiredArgsConstructor          // Lombok teeb: LoginService(UserRepository userRepository)
public class LoginService {
    private final UserRepository userRepository;   // "required" = final ilma väärtuseta
}
```

## Kohvioa ikoon IntelliJ-s (Spring bean) — `0:29:56` {#kohvioa-ikoon}

### Selgitus

IntelliJ näitab `final` sõltuvusvälja kõrval **kohvioa ikooni** (roheline uba). See tähendab: "siin on potentsiaalselt objekt, mille Spring saab automaatselt konteinerist ühendada" (`@Autowired` toimub automaatselt).

- Kui `@Service` on `LoginService`-l peal → Spring teeb objekti, hoiab konteineris, uba on nähtav ja ühendus toimib.
- Kui võtta `@Service` ära → Spring ei tee objekti, konteineris pole sobivat kandidaati, IntelliJ kaebab "Bean-objekti ei õnnestu lahendada".

### Päriselu analoogia

Kohvioa ikoon on nagu roheline tuluke pistikupesa kõrval: "siia saab midagi ühendada, vool on olemas".

## Entity klass — üks objekt = üks tabelirida — `0:33:32` {#entity}

### Selgitus

Levinud eksiarusaam: "entiteet teeb tabelist objekti". **Vale.** Entiteedi klassist saab teha kasvõi tuhat objekti, ja **üks objekt hoiab ühe tabelirea andmeid**. See ei ole tabeli objekt, see on **tabelirea** objekt.

`UserRepository` on seotud konkreetse entiteediga — `User` — ja `User` on seotud konkreetse tabeliga (`bank."user"`). Iga väli klassis vastab ühele veerule.

### Koodinäide (`backend/.../persistence/user/User.java`)

```java
@Getter @Setter
@Entity
@Table(name = "\"user\"", schema = "bank")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id", nullable = false)
    private Integer id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "role_id", nullable = false)
    private Role role;                    // hoiab tervet Role-objekti, mitte ainult numbrit

    @Column(name = "status", nullable = false)
    private String status;

    @Column(name = "password", nullable = false)
    private String password;

    @Column(name = "username", nullable = false)
    private String username;
}
```

### Skeem

```text
tabel bank."user"
┌────┬─────────┬──────────┬──────────┬────────┐
│ id │ role_id │ username │ password │ status │
├────┼─────────┼──────────┼──────────┼────────┤
│ 2  │   1     │ admin    │ ...      │ A      │  ←── üks User-objekt
│ 3  │   2     │ rain123  │ ...      │ A      │  ←── teine User-objekt
└────┴─────────┴──────────┴──────────┴────────┘
```

### Päriselu analoogia

`User` klass on nagu ankeedi **plank**. Iga täidetud ankeet (objekt) on ühe inimese andmed. Plank ise ei ole "kõik inimesed" — see on vorm ühe rea jaoks.

## Miks `@Data` entiteedil on ohtlik — `0:45:35` {#data-oht}

### Selgitus

Lomboki `@Data` genereerib muu hulgas `toString()` meetodi, mis kaasab **kõik väljad** — sealhulgas seosed nagu `role`. Probleem: niipea kui koodis (või logis) `toString()` käivitub, **puudutab** see `role` välja, ja LAZY-seos toob siis andmebaasist iga rea kohta lisapäringu.

Kui pärid `user`-tabelist 100 rida ja `toString()` käib igaühe peale, teeb JPA **100 ekstra päringut** `role`-tabeli vastu ("N+1 probleem"). Seetõttu kasutatakse entiteedil pigem `@Getter @Setter` eraldi, mitte `@Data`.

### Päriselu analoogia

`toString()` on nagu uudishimulik külaline, kes tahab iga kord kogu su elu ära kuulata. Kui iga kord tuleb kõik detailid kohale tuua, läheb õhtusöök väga aeglaseks.

## `@ManyToOne`, LAZY vs EAGER — `0:46:48` {#lazy-eager}

### Selgitus

`@ManyToOne` seob mitu `user`-rida ühe `role`-reaga. Andmete toomise strateegia (`fetch`) on kaks:

| Strateegia | Käitumine |
|---|---|
| **`FetchType.LAZY`** (laisk) | `role` andmeid **ei tooda**, kuni koodis mõnda `role`-välja päriselt puudutatakse. Objektis hoitakse esialgu vaid viide (number). |
| **`FetchType.EAGER`** (innukas) | `role` tuuakse **alati** kohe kaasa, sõltumata sellest, kas seda koodis kasutatakse. |

JPA valis vaikimisi mõistlikud seaded ise (need klassid genereeriti). `@ManyToOne` vaikeväärtus on tegelikult EAGER, seepärast pannakse käsitsi `fetch = FetchType.LAZY`, et vältida asjatuid päringuid. See kõik on **mugavustehnoloogia** — vanasti pidi `Connection`-i, `SELECT`-lause, parameetrid ja objekti kokkupaneku kõik ise käsitsi kirjutama.

### Skeem

```text
LAZY:   SELECT * FROM "user" WHERE ...        (role_id = 1, aga Role-objekti veel pole)
           │  kood puudutab user.getRole().getName()
           ▼
        SELECT * FROM role WHERE id = 1        (alles nüüd)
```

## Find Instance vs Find Collection vs Count vs Exists — `1:14:54` {#find-variandid}

### Selgitus

IDE päringudisainer pakub esimese valikuna, mis **tüüpi** päring see on:

| Valik | Mida tagastab | Kui midagi ei leia |
|---|---|---|
| **Find Instance** | üks objekt (üks rida) | `null` (või tühi `Optional`) |
| **Find Collection** | list objekte (0..n rida) | tühi list |
| **Count** | number (mitu rida vastab) | `0` — kolmandat varianti pole |
| **Exists** | `boolean` (kas leidus vähemalt üks) | `false` |
| **Delete** | tavaliselt `void` | — |

Sisselogimisel otsime **ühte rida** (kasutajanime + parooli + staatuse järgi) → **Find Instance**. Kui päring saab vastuseks kaks rida, aga meetod lubab ühte objekti → **läheb katki** (viga). Andmebaasis pole "anna mulle esimene" maagilist sõna — päring teeb täpselt seda, mida küsid.

## Kuidas on tagatud, et otsing leiab kõige rohkem ühe rea — `1:19:27` {#unikaalsus}

### Selgitus

Kui programmeerin "otsi mulle **üks** rida ja tee sellest objekt", pean **süsteemselt garanteerima**, et kaht sobivat rida ei saa kunagi tekkida. Meie süsteemis on see kaitstud **`username` unikaalsuspiiranguga** (`UNIQUE` constraint andmebaasis) — sama kasutajanimega rida ei saa kaks korda eksisteerida.

Kaitse peab olema **andmebaasi tasemel**, mitte ainult koodis. Koodikontrollist ("kas selline kasutaja on juba olemas?") üksi ei piisa — keegi võib käsitsi rea lisada. Kui piirang on tabeli enda küljes (`CREATE TABLE ... UNIQUE` või `ALTER TABLE`), siis sellest **üle sõita ei saa** — pole "magic word'i", mis ütleks "ma tean, et peab olema unikaalne, aga lisa ikka".

**Mitmeveeruline unikaalsus** (`1:27:06`): piirangu saab panna ka mitme veeru kombinatsioonile — nt eesnimi + perekonnanimi + sünnikuupäev + aadress koos peavad olema unikaalsed, kuigi ükski veerg eraldi ei ole.

### Skeem

```text
username UNIQUE tabelis "user"
        │
        ▼
findUserBy(username, password, status)  →  ei saa tehniliselt tagastada > 1 rida
        │
        ▼
      julge kasutada Find Instance / Optional<User>
```

### Päriselu analoogia

Isikukood: ühest piisab, et inimest üheselt eristada. Kasutajanimi on sama loogika — kui andmebaas seda kombinatsiooni valvab, siis topeltrida lihtsalt ei sünni.

## `@Query` annotatsioon: JPQL ja parameetrid — `1:38:53` {#query-annotatsioon}

### Selgitus

Teine viis (soovitatud) päringu määramiseks: `@Query` annotatsioon meetodi peal. Kui `@Query` on olemas, **paneb JPA lause kokku puhtalt annotatsiooni järgi ja meetodi nime enam ei vaata** — see on **välistav** olukord (kas nime järgi VÕI annotatsiooni järgi, mitte mõlemat).

Eelis: **meetodi nime saab vabalt lühendada** (`findUserBy`), ja `@Query`-ga saab teha ka asju, mida meetodi nime järgi ei saa (nt `UPDATE`).

**Parameetrid** — kaks stiili:

| Stiil | Näide |
|---|---|
| Positsiooniline | `... where u.username = ?1 and u.password = ?2` |
| Nimeline | `... where u.username = :username` |

Nimeline on loetavam. Kui `@Param`-i nimi ja meetodi parameetri nimi **kattuvad**, siis `@Param` "abirattaid" **ei ole vaja** — JPA võtab vaikimisi eelduseks, et kasutad sama nime.

### Koodinäide (`backend/.../persistence/user/UserRepository.java` — praegune seis)

```java
@Query("select u from User u where u.username = :username " +
       "and u.password = :password and u.status = :status")
Optional<User> findUserBy(String username, String password, String status);
```

Süntaks on tähtis: `u` on **alias**, `User` on **entiteet** (mitte tabeli nimi!), `u.username` viitab **väljale** (mitte veerule). Sõna `table` siin ei esine.

## Native query ja miks seda vältida — `1:49:43` {#native-query}

### Selgitus

`@Query(value = "SELECT * FROM ...", nativeQuery = true)` laseb kirjutada **päris SQL-i**, mis läheb otse andmebaasi.

**Miks vältida:** native päring on **andmebaasi-spetsiifiline**. Kui täna oleme PostgreSQL-il ja homme tahame vahetada mootorit, siis kõik native laused tuleb üle käia (dialekt võib olla vale). JPQL (`@Query` ilma `nativeQuery`-ta) viitab **klassidele ja väljadele**, mitte tabelitele ja veergudele → mootorivahetus ei lõhu seda.

## `Optional<T>` — "kast", milles võib olla objekt — `1:57:53` {#optional}

### Selgitus

`Optional` (Java 8+) on **kast**, mille sees kas **on** objekt või **ei ole**. Sõna "wrap" (mähkima) on tehniline termin: `Optional<User>` = `User`-objekt on mähitud `Optional`-kasti sisse.

Andmebaasist üksikrea otsimisel me **ei tea ette**, kas midagi tuleb — sisend tuleb väljastpoolt (internetist), mitte meie programmist. `Optional` haldab täpselt seda "on või ei ole" olukorda: **kast tagastatakse alati**, sisu võib puududa.

### Skeem

```text
findUserBy("rain123", ...)   →  Optional[ User(id=3, username="rain123") ]   (kast + sisu)
findUserBy("student", ...)   →  Optional.empty()                              (kast, tühi)
```

### Päriselu analoogia (kass kastis)

Lapsed on kassi jänesepuuri (kasti) pannud. Vanem küsib: "kas kass on jälle kastis?" Kast on igal juhul olemas — küsimus on, kas kass on **sees**.

## `isPresent()` / `isEmpty()` — kassi ja kartuli analoogia — `2:01:18` {#ispresent-isempty}

### Selgitus

`Optional`-kastil on meetodid:

| Meetod | Tähendus |
|---|---|
| `isPresent()` | `true`, kui sisu on olemas |
| `isEmpty()` | `true`, kui kast on tühi |
| `get()` | võtab objekti kastist välja (eeldab, et sisu on) |

Kumba kontrolli kasutada, sõltub sellest, **millist olukorda sa jälgid**. Sisselogimisel huvitab meid **veaolukord** — kasutajat ei leitud → `isEmpty()` on loomulikum ("kui kartul on otsas, siis on vaja poodi minna").

### Päriselu analoogia (kartulisalat)

"Teeme kartulisalatit. Kas kartul on otsas?" — sind ei huvita, mitu kartulit on, sind huvitab **ainult see olukord**, kus kartulit **pole** (`isEmpty()`), sest siis on vaja tegutseda.

## Optionaliga vs null-kontrolliga loogika — `2:07:03` {#optional-vs-null}

### Selgitus

Kaks stsenaariumi: `rain123` logib sisse (leitakse), `student` logib sisse (ei leita).

**Ilma Optionalita** (`findUserBy` tagastab `User` või `null`):

```java
User user = userRepository.findUserBy(username, password, "A");
if (user == null) {
    throw new SomeException("Vale kasutajanimi või parool");
}
// rain123: user != null → viga ei visata
// student: user == null → viga visatakse
```

**Optionaliga** (`findUserBy` tagastab `Optional<User>`):

```java
Optional<User> optionalUser = userRepository.findUserBy(username, password, "A");
if (optionalUser.isEmpty()) {
    throw new SomeException("Vale kasutajanimi või parool");
}
// rain123: kast pole tühi → viga ei visata
// student: kast on tühi   → viga visatakse
```

Miks Optional parem: pidev `== null` / `!= null` kontroll on tüütu ja "räpane". `isEmpty()` / `isPresent()` loeb peaaegu nagu inimkeel: "kui leidsin midagi, siis tee midagi".

## `orElseThrow()` — tühi kast viskab vea — `2:15:39` {#orelsethrow}

### Selgitus

`orElseThrow()` on `Optional`-i meetod, mis teeb kahte asja korraga:

- kui kastis **on** sisu → tagastab **selle objekti** (tüüp `T`, geneeriline);
- kui kast on **tühi** → **viskab vea** (mille sina määrad).

Nii saab pika `if`-i asendada ühe reaga: "anna mulle sisu, või kui pole, viska viga".

### Koodinäide (kuhu login-loogika ilmselt liigub)

```java
User user = userRepository
        .findUserBy(loginRequest.getUsername(), loginRequest.getPassword(), "A")
        .orElseThrow(() -> new ForbiddenException("Vale kasutajanimi või parool"));

// siit edasi on 'user' garanteeritult olemas
```

Projekti konventsioon (`backend/CLAUDE.md`): ID järgi otsing `repository.findById()` + `orElseThrow` peab olema `public getValid<Entiteet>By(Integer id)` meetodis vastava service'i all.

### Päriselu analoogia

`orElseThrow()` on nagu pakiautomaat: kui pakk on lahtris, saad selle kätte; kui lahter on tühi, teatab automaat kohe veast, mitte ei anna sulle tühja kätt, millega sa hiljem hätta jääd.
