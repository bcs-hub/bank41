## SQL: iga päring algab ühest tabelist — `0:00:05` {#sql-alustamine}

### Selgitus

**SQL** (Structured Query Language) on keel, millega me räägime andmebaasiga. Kõige tähtsam mõte, millega alustada:

> Tavalises `SELECT`-lauses **alustad alati ühest konkreetsest tabelist**. Sa ei saa "pöörduda kahe tabeli poole korraga" — sisenemine on alati ühe tabeli kaudu, ja sealt saab siis edasi liikuda teistesse tabelitesse (`JOIN`-i abil).

`COUNT(*)` loeb kokku, mitu rida vastus sisaldab. Näiteks meie `bank` skeemis:

```sql
-- Mitu rida on user-tabelis?
SELECT count(*) FROM bank."user";   -- 3

-- Mitu rida on role-tabelis?
SELECT count(*) FROM bank.role;     -- 2
```

Tähelepanek: `user` on PostgreSQL-i reserveeritud sõna, seepärast pannakse ta jutumärkidesse: `"user"`.

### Päriselu analoogia

Mõtle andmebaasist kui majast, kus igas toas (tabelis) on üks kindel teema. Sa ei saa astuda korraga kahte tuppa — sa lähed sisse ühest uksest ja alles siis, kui vaja, kõnnid koridori kaudu edasi teise tuppa.

## JOIN – kahe tabeli ühendamine — `0:11:09` {#join}

### Selgitus

**Relatsiooniline andmebaas** tähendab, et andmed on jaotatud eraldi tabelitesse ja **omavahel seotud**. Kasutaja info on `user`-tabelis, aga rolli **nimi** ("admin", "customer") on hoopis `role`-tabelis. `user`-tabelis on ainult `role_id` — number, mis viitab `role`-tabeli reale.

`JOIN` ("liitmine") ühendab kaks tabelit kokku nende numbrite alusel:

```sql
SELECT u.username, r.name AS role_name
FROM bank."user" u
JOIN bank.role r ON u.role_id = r.id;
```

Mida see teeb, samm-sammult:
1. Võta `user`-tabelist rida.
2. Loe sealt `role_id` (nt `2`).
3. Otsi `role`-tabelist rida, mille `id = 2`.
4. Kleebi need kaks rida kõrvuti üheks tulemusreaks.
5. Korda iga `user`-rea kohta.

**Tabeli alias** (`u`, `r`) on lühike hüüdnimi, mille annad tabelile `FROM`/`JOIN` järel, et edaspidi lühemalt kirjutada (`u.username` asemel `"user".username`).

**Veeru alias** (`AS role_name`) annab tulemusveerule uue nime — see on ainult kuvamiseks, andmebaasis midagi ei muutu. Päris ümbernimetamine nõuaks `ALTER TABLE`-t.

### Skeem

```
user-tabel                         role-tabel
┌────┬──────────┬─────────┐        ┌────┬──────────┐
│ id │ username │ role_id │        │ id │ name     │
├────┼──────────┼─────────┤        ├────┼──────────┤
│ 1  │ admin    │   1 ────┼───────▶│ 1  │ admin    │
│ 2  │ rain     │   2 ────┼───────▶│ 2  │ customer │
└────┴──────────┴─────────┘        └────┴──────────┘
                    JOIN u.role_id = r.id
                              │
                              ▼
              ┌──────────┬───────────┐
              │ username │ role_name │
              ├──────────┼───────────┤
              │ admin    │ admin     │
              │ rain     │ customer  │
              └──────────┴───────────┘
```

### SELECT * vs veergude loetlemine

`SELECT *` (asterisk, "wildcard") tähendab "anna kõik veerud". Päris elus me tavaliselt **ei taha kõiki veerge** — valime täpselt need, mida vaja:

```sql
SELECT u.username, u.status, r.name
FROM bank."user" u
JOIN bank.role r ON u.role_id = r.id;
```

### Päriselu analoogia

`JOIN` on nagu kahe nimekirja kõrvuti panemine: ühes on inimeste nimed ja garderoobinumbrid, teises garderoobinumbrid ja mantlid. Numbri järgi saad kokku panna, kellele milline mantel kuulub.

## Primaarvõti, välisvõti ja NOT NULL kitsendused — `0:20:17` {#votmed-kitsendused}

### Selgitus

**Primaarvõti** (primary key, "kollane võti") — veerg `id`, mis on igal real **unikaalne ega kordu kunagi**. PostgreSQL-is genereeritakse see automaatselt (`serial` / sekvents-loendur). Kui ütled "anna mulle rida `id = 2`", saad 100% täpselt ühe kindla rea, isegi kui tabelis on miljon rida. See on rea **identifikaator**.

**NOT NULL** — kitsendus, mis ütleb, et see veerg **ei tohi tühjaks jääda**. Kui üritad lisada rida ilma selle väljata, andmebaas keeldub: rida ei teki. Meie `user`-tabeli loomise skript:

```sql
CREATE TABLE "user" (
    id       serial       NOT NULL,
    role_id  int          NOT NULL,   -- kohustuslik, ise pead sisse panema
    username varchar(255) NOT NULL,
    password varchar(255) NOT NULL,
    status   char(1)      NOT NULL,
    CONSTRAINT user_ak_1 UNIQUE (username),   -- username peab olema unikaalne
    CONSTRAINT user_pk PRIMARY KEY (id)
);
```

**Välisvõti** (foreign key, "sinine võti") — tehniline seos kahe tabeli vahel. Seda ei loo mitte `CREATE TABLE` ise, vaid **eraldi `ALTER TABLE` skript**:

```sql
ALTER TABLE "user" ADD CONSTRAINT user_role
    FOREIGN KEY (role_id)
    REFERENCES role (id);
```

See lause ütleb: `user.role_id` **peab** viitama mõnele olemasolevale `role.id`-le. IntelliJ näeb tabeli ülesehitust ja kuvab seepärast selle veeru kõrval sinist võtmeikooni.

**Vaikimisi täidetavad vs käsitsi täidetavad väljad:**
- `id` — tuleb andmebaasist automaatselt (`GeneratedValue`), sina ei täida
- `role_id` — sina pead ise õige numbri sisse panema (see on `NOT NULL` + välisvõti)

### Päriselu analoogia

`NOT NULL` on nagu kokkulepe restoranis: "kas teeme kõik nii nagu kokku leppisime, või ei tee üldse". Kui üks kohustuslik osa on puudu, siis tellimust vastu ei võeta.

## Välisvõti kaitseb: viidatud ridu ei saa kustutada — `0:41:22` {#fk-kaitse}

### Selgitus

Kui `role`-tabeli reale `id = 2` viitavad `user`-tabeli read, siis seda `role`-rida **ei saa kustutada**:

```sql
DELETE FROM bank.role WHERE id = 2;
-- Viga: "update or delete on table role violates foreign key constraint"
-- Väärtus 2 on endiselt viidatud tabelis user.
```

Sama kehtib lisamisel:

```sql
INSERT INTO bank."user" (role_id, username, password, status)
VALUES (99, 'admin2', '123', 'A');
-- Viga: "Key (role_id)=(99) is not present in table role."
```

Andmebaas **ise kaitseb** andmete terviklikkust: sa ei saa viidata millelegi, mida pole olemas, ega kustutada midagi, millele mujal veel viidatakse.

**Alternatiiv:** mõned süsteemid (õpetaja tõi näiteks LHV) ei kasuta tehnilist välisvõtit, vaid hoiavad seoseid **programmiliselt** — sinist võtit ei näidata, aga numbrid on ikka tabelites. See annab vabaduse kustutada, aga kaotab andmebaasi automaatse kaitse. Relatsioonilises andmebaasis me tavaliselt **tahamegi**, et andmed oleksid tehniliselt seotud ja kaitstud.

## WHERE tingimuslause (ja miks üks võrdusmärk) — `0:19:15` {#where}

### Selgitus

`WHERE` piirab, millised read tulemusse jäävad:

```sql
SELECT u.username, r.name
FROM bank."user" u
JOIN bank.role r ON u.role_id = r.id
WHERE r.name = 'customer';
```

**Tähtis erinevus programmeerimisest:** SQL-is on **üks võrdusmärk** `=`, mitte kaks (`==`). Põhjus: SQL-is ei saa päringus väärtust omistada, seega pole segadust — `=` tähendab alati "kas on võrdne".

### Päriselu analoogia

`WHERE` on nagu sõel: kõik read valatakse sellest läbi ja alles jäävad ainult need, mis tingimusele vastavad.

## LIKE ja %-metamärgid — `0:23:34` {#like}

### Selgitus

`LIKE` võimaldab otsida **osalist vastet**, mitte täpset võrdust. `%` on metamärk, mis tähendab "ükskõik mis, ükskõik kui palju":

```sql
-- Algab tähtedega "cos"
WHERE username LIKE 'cos%'

-- Sisaldab kuskil "mi" (ükskõik kus sõnas)
WHERE username LIKE '%mi%'
```

- `'cos%'` — peab **algama** stringiga "cos", ülejäänu ükskõik
- `'%mi%'` — "mi" võib olla ükskõik kus (algus, keskel, lõpus) — see on sisuliselt "contains"

### Skeem

```
'cos%'   →  cos|tume, cos|mos       (algus peab klappima)
'%mi%'   →  ad|mi|n, |mi|tteaktiivne  (mi kuskil sees)
```

## AND / OR ja lühishindamine — `0:27:00` {#and-or}

### Selgitus

Mitu tingimust saab kombineerida `AND` ja `OR` abil. `AND` puhul peavad **mõlemad pooled** olema tõesed:

```sql
SELECT * FROM bank."user"
WHERE status = 'A' AND password = '123';
```

**Lühishindamine (short-circuit):** kui `AND` esimene pool rehkendub juba `false`-iks, siis andmebaas **ei vaevugi teist poolt vaatama** — kogu rida kukub niikuinii välja. Pole vahet, mis teine tingimus on.

### Skeem

```
Rida 1:  status='A' (true)  AND  password='123' (true)   →  true   → JÄÄB
Rida 2:  status='A' (true)  AND  password='xxx' (false)  →  false  → KUKUB
Rida 3:  status='D' (false) AND  (ei vaadatagi)           →  false  → KUKUB
```

Vaata ka [tõeväärtustabel AND/OR](../theory-materials/tõeväärtustabel-and-or.md).

## WHERE rehkendub alati tõeseks või vääraks — `0:29:04` {#where-tõeväärtus}

### Selgitus

`WHERE` tingimus **peab iga rea kohta rehkenduma kas `true` või `false`-iks**. Andmebaas käib kõik read ükshaaval läbi ja küsib: "kas selle rea kohta on tingimus tõene?"

Sellest järeldub paar huvitavat asja:

```sql
SELECT * FROM bank."user" WHERE true;       -- annab KÕIK read
SELECT * FROM bank."user" WHERE 100 = 100;  -- annab KÕIK read (100=100 on alati true)
```

Tingimus ei pea "sisuliselt midagi vaatama" — kui see rehkendub alati `true`-ks, jäävad kõik read alles. See on lihtne mõttemudel: **vahet pole, kui palju `AND`/`OR`-e ja veerge — lõpuks peab kogu avaldis rehkenduma ühe rea kohta tõeseks või vääraks.**

## INSERT – uue rea lisamine — `0:31:26` {#insert}

### Selgitus

```sql
INSERT INTO bank."user" (role_id, username, password, status)
VALUES (1, 'mati', '123', 'A');
```

Nüansid:
- `id` jäetakse loetelust välja — andmebaas genereerib selle ise. Võib ka kirjutada `id` ja anda väärtuseks `default`.
- `role_id` **peab** olema (NOT NULL + välisvõti) ja peab viitama olemasolevale rollile
- `username` peab olema **unikaalne** (`UNIQUE` kitsendus) — sama nime teist korda ei saa
- `status` — meie tabelis `char(1)`, praktikas `'A'` (aktiivne) või `'D'` (mitteaktiivne). Väärtuste piiramise saaks samuti kitsendusega tabelisse sisse ehitada.
- valikulised väljad (nt `location`-tabeli `latitude`, `longitude`) võivad jääda täitmata (`null`), sest neid pole `NOT NULL`-iks märgitud

Kui mõni kohustuslik väli on puudu → **rida ei teki**, andmebaas viskab vea.

## UPDATE – ridade muutmine — `0:37:27` {#update}

### Selgitus

```sql
UPDATE bank."user"
SET username = 'peeter'
WHERE username = 'mati';
```

- `SET` — millist veergu (või mitut, komaga eraldatult) muudad ja mis uus väärtus on
- `WHERE` — **millised read** muutuvad. Kui `WHERE` sobib mitmele reale, muudetakse kõik need.
- Kui jätad `WHERE` ära, muudad **kõik read** — ettevaatust!

Kui `WHERE` tabab mitut rida ja üritad panna kõigile sama `username`, siis `UNIQUE` kitsendus lööb vahele ja muudatust ei tehta.

## SQL injection ja miks JPA meid kaitseb — `0:41:22` {#sql-injection}

### Selgitus

**SQL injection** on rünnak, kus kasutaja sisend läheb otse SQL-päringu sisse ilma kontrollimata. Kuulus näide: politsei kiiruskaamera, kuhu sõidutati auto numbrimärgiga, mis sisaldas SQL-koodi.

Mõte: `;` (semikoolon) lõpetab SQL-lause. Kui rakendus paneb sisendi ilma puhastamata päringusse:

```sql
SELECT * FROM "user" WHERE username = '<SISEND>'
```

ja `<SISEND>` on `x'; DROP TABLE user; --`, siis tegelikult käivitub kaks lauset: päring **ja** tabeli kustutamine.

**Kaitse:**
- kontrolli sisendit (nt keeldu semikoolonist, kasuta parameetreid mitte string-liitmist)
- **JPA / Spring Data teeb selle automaatselt** — tehnoloogia ei lase ründevektoreid sisendina läbi. Seepärast me kursusel enamasti SQL-i käsitsi ei kirjutagi.

## Restorani analoogia: "too kombo viis" — `0:46:13` {#restoran}

### Selgitus

Õpetaja kasutab restorani metafoori, et selgitada, mis backend'is toimub. Klient tahab **"valik üks"** (kreemjas kõrvitsasupp + veiseliha burger + tiramisu = "kombo viis"). Vastuvõtu töötaja (frontend) ei valmista ise midagi — ta lihtsalt edastab tellimuse tagaruumi.

| Restoran | Tarkvara |
|---|---|
| Klient laua taga | brauser (Client) |
| Vastuvõtt / serveerija | Frontend |
| Tegevuste → protseduuride kaardistus | Spring dispetšer (URL → meetod) |
| Tellimuste kontrollija (püsitöötaja) | **Controller** |
| Tellimuste teenindus (püsitöötaja) | **Service** |
| Supihoidla **uks** (ainus sissepääs) | **Repository** (üks tabeli kohta) |
| Supi komplekteerija (püsitöötaja) | **Mapper** |
| Supp, burger, kohv (tekivad ja kaovad) | ajutised objektid (Entity, DTO) |
| **Kandik**, millele kõik pannakse | **DTO** (Data Transfer Object) |

Tähtsad mõtted:
- **Püsitöötajad** (kontrollija, teenindus, komplekteerija, uksed) on **alati olemas** — neid on igaüht **ainult üks**. Kui see "vend tööle ei tule", kukub kogu asi kokku. → need on Spring **bean-objektid**.
- **Supp/kandik** tekivad iga tellimuse jaoks uuesti ja kaovad pärast → ajutised objektid.
- Igasse hoidlasse pääseb **ainult läbi selle ühe ukse** → iga tabeli jaoks oma repository.
- Asjad **kandikul on omavahel seotud** (supp on kandiku peal, sool supi kõrval) → objektid viitavad üksteisele mäluviidete kaudu.

### Skeem

```
Klient → Vastuvõtt → [kaardistus] → Kontrollija → Teenindus
                                                      │
                              ┌───────────────────────┼───────────────┐
                              ▼                       ▼               ▼
                        Supihoidla uks         Burksihoidla uks   Magusahoidla uks
                              │                       │               │
                              └──────────► Komplekteerija ◄───────────┘
                                                │
                                          KANDIK (kõik koos)
                                                │
                                                ▼
                                     Vastuvõtt → Klient
```

## Spring dispetšer: URL + HTTP meetod → Controller — `0:48:45` {#dispetser}

### Selgitus

Me ei pea seda kaardistust ise haldama — Spring skannib käivitumisel kõik `@RestController`-annotatsiooniga klassid ja leiab kaardistused ise üles (näed konsoolis rida "scanning for @RestController...").

## HTTP meetodid: POST, GET, PUT, PATCH, DELETE — `0:49:49` {#http-meetodid}

## Bean-objektid ja Spring Container — `0:54:57` {#beanid}

### Selgitus

Java virtuaalmasinas (JVM) elavad objektid kuhimälus (heap), millele viitavad mäluviited. Tavaliselt objekt **tekib, kasutatakse, kaob prügikasti** ja järgmisel korral tehakse uus.

Aga mõnda objekti (Controller, Service, Repository, Mapper) läheb **korduvalt vaja** ja pole mõtet neid iga kord uuesti luua. Need on **bean-objektid** ("kohvioad"):

- Kui server käivitub, teeb Spring nendest klassidest **automaatselt objektid** (üks igast) ja hoiab neid **Spring Container**'is (õppevideol kollane kast).
- Objekt saab kindla mäluviite (nt `ref#001`) ja **jääb sinna kogu serveri elutsükliks** — isegi kui server jookseb kaks aastat järjest.
- See on **optimeerimine**: ei raisata ressurssi objektide pidevale loomisele ja kustutamisele.

Klassist tehakse bean lihtsalt annotatsiooni lisamisega:

```java
@RestController   // → bean
@Service          // → bean
@Repository        // → bean (Spring Data teeb ka ilma annotatsioonita)
```

### Skeem

```
┌──────────────── Spring Container ────────────────┐
│  ref#001  LoginController                          │  ← alalised objektid
│  ref#002  LoginService                            │     (üks igast klassist)
│  ref#003  LocationRepository                      │
│  ref#004  LocationMapper                          │
└──────────────────────────────────────────────────┘

     valged / ajutised:  LoginRequest, Location, List<...>  (tekivad ja kaovad)
```

## Controller / Service / Repository / Mapper kihid — `1:00:04` {#kihid}

### Selgitus

Backend'is on kolm-neli klassi järjestikku, igaühel oma **üks selge roll**:

1. **Controller** — ainus eesmärk: siia kirjutad meetodi, mis **käivitub sissetuleva sõnumi peale**. Tegevuse stardipunkt. Muud siin ei ole.
2. **Service** — kogu **äriloogika** (business logic). Lihtsustatult: põhikood. Kuidas süsteem peab käituma, kust andmeid pärida, mida võtta, mida visata.
3. **Repository** — kiht, mis oskab **saata SQL-päringuid andmebaasi**. Iga konkreetse tabeli jaoks oma repository ("üks uks ühe hoidla kohta").
4. **Mapper** — vahepealne "kokkupanija", mis **teisendab andmeid ühelt objektilt teisele** (nt entiteedist DTO-ks). Ainult Location'iga seotud teisendused käivad `LocationMapper`-is.

Mõte on **osade eraldamine** (separation of concerns): keegi teab, mida käivitada; keegi teab, mis liigutused teha; keegi suhtleb andmebaasiga. See on väga tavaline arhitektuurimuster.

### Skeem

```
Sõnum → Controller → Service → Repository → Andmebaas
                        │
                        └──→ Mapper (Entity ↔ DTO teisendus)
```

## Dependency Injection ja siltmuutuja — `1:19:23` {#di}

### Selgitus

`LoginController` peab käivitama meetodi `LoginService`-is. Aga **meetodit saab käivitada ainult objekti kaudu** — ja objektil peab olema **silt** (viide, muutuja), et selle poole pöörduda.

> Kui sa tüübi nime ei tea, ei saa sa talle öelda "too see asi". Sul on vaja **nime / silti**.

`LoginController` ja `LoginService` on **kaks eraldi klassi, kaks eraldi faili**. `Controller`-il on vaja välja (siltmuutuja), mis viitab konteineris olevale `Service`-objektile:

```java
@RestController
public class LoginController {

    private final LoginService loginService;   // ← silt (viide bean-objektile)

    public LoginController(LoginService loginService) {
        this.loginService = loginService;      // Spring "süstib" objekti siia
    }
}
```

**Dependency Injection (DI)** ongi see: rakendus loob ise vajalikest klassidest objektid, hoiab neid konteineris, ja **süstib** need meie muutujatesse siis, kui vaja. Meie ise ei kirjuta kuskil `new LoginService()` — objekt on juba olemas, meil on vaja ainult **ligipääsu**.

("Java" nimi muide tuleb Java saarest, mis oli kuulus kohviistanduste poolest — sellest ka "bean" = kohviuba.)

## Entity klass ja JPA annotatsioonid — `1:24:58` {#entity}

### Selgitus

**Entity** ("olem", entiteet) — Java klass, mis vastab **ühele tabelile**, ja tema objekt vastab **ühele reale** sellest tabelist. Kui pärid 2 rida, tekib 2 objekti.

Kui võtta annotatsioonid ära, on see tavaline "vanilla" Java klass private väljadega. Erilise teevad **annotatsioonid**:

```java
@Entity
@Table(name = "location")       // seob klassi konkreetse tabeliga
@Getter
@Setter
public class Location {

    @Id
    @GeneratedValue                // väärtus tuleb andmebaasist, ise ei täida
    private Integer id;

    @ManyToOne
    @JoinColumn(name = "city_id")  // andmete liitmine (nagu SQL JOIN)
    private City city;             // NB! City on eraldi klass, mitte String

    @Column(name = "number_of_atms")   // snake_case veerg ↔ camelCase väli
    private Integer numberOfAtms;

    private String status;
}
```

Reeglid annotatsioonide kohta:
- Klassi kohal olev `@Entity`, `@Table` kehtib **kogu klassi** kohta
- Välja kohal (samal koodireal) olev `@Id`, `@Column` kehtib **selle välja** kohta
- `@Getter`/`@Setter` (Lombok) — kuna väljad on `private`, pole neile otse ligi (`objekt.id`); getter-meetodid (`getId()`, `getStatus()`) annavad ligipääsu
- `City` tüüpi väli tähendab, et selle taga on omakorda `City` entiteet oma väljadega (`id`, `name`)

### Skeem

```
Tabel "location" (üks rida)          Location objekt
┌────┬─────────┬────────┐            ┌──────────────────────┐
│ id │ city_id │ status │   ────▶    │ id = 2               │
│ 2  │   1     │  A     │            │ city → City{id:1,... }│
└────┴─────────┴────────┘            │ status = "A"         │
                                     └──────────────────────┘
```

## Entiteeti ei tohi serverist välja anda – DTO — `1:37:00` {#dto}

### Selgitus

}

## MapStruct Mapper: entiteedist DTO-ks — `1:40:56` {#mapper}

### Selgitus

`LocationMapper` on `interface` (`@Mapper`), mis kasutab **MapStruct** tehnoloogiat ("Java bean mappings, the easy way"). Ta teisendab objekte ühelt kujult teisele.

```java
@Mapper(componentModel = "spring")
public interface LocationMapper {

    LocationInfo toLocationInfo(Location location);          // ainsus

    List<LocationInfo> toLocationInfos(List<Location> locations);  // mitmus
}
```

- **Kaardistus käib alati üksiku objekti tasandil.** Isegi kui vajad list-meetodit (`toLocationInfos`), peab ainsuse meetod (`toLocationInfo`) olemas olema — seal defineeritakse, kuidas üks objekt teiseks teiseneb.
- MapStruct oskab **sama nimega väljad ise kokku panna**. Erineva nime või pesastatud välja (nt `location.city.name` → `cityName`) puhul juhendad `@Mapping`-uga:

```java
@Mapping(source = "city.name", target = "cityName")
LocationInfo toLocationInfo(Location location);
```

- List-meetod käib **tsükliliselt** iga objekti läbi, kutsub üksiku kaardistuse ja lisab tulemuse uude listi.
- Genereeritud implementatsioon tekib kausta `src/main/generated/`.

### Skeem

```
List<Location> (entiteedid)          List<LocationInfo> (DTO-d)
 ├─ Location{sikupilli}  ──map──▶     ├─ LocationInfo{id, cityName, name}
 └─ Location{tondi}      ──map──▶     └─ LocationInfo{id, cityName, name}
```

## LoginController: @RestController ja @PostMapping — `2:13:45` {#logincontroller}

### Selgitus

**Struktuur:** kontrollerid lähevad alampaketti `controller/`, DTO-d alampaketti `controller/` (või `.../dto`). Klassi nime lõppu **alati** postfix `Controller`.

Töövoog (õpetaja stiil): "proge ühes kohas seni, kuni tuleb takistus, siis liigu teise faili ja naase".

```java
package ee.bcs.bank.controller;

import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController                      // → REST-kontroller + bean-objekt
public class LoginController {

    @PostMapping("/api/login")       // POST + tee "/api/login"
    public void loginUser(@RequestBody LoginRequest loginRequest) {
        // esialgu void — tagastust täpsustame hiljem
    }
}
```

Meetodi struktuuri otsused:
- **Nähtavus `public`** — meetodit kutsub välja Spring'i raamistik "kuskilt mujalt", seega peab olema nähtav
- **Tagastustüüp** — alusta `void`-iga, täpsusta hiljem ("jõuame ringiga tagasi")
- **Nimi** — tegusõna: `loginUser` (või lihtsalt `login`)
- **`@PostMapping("/api/login")`** — kui muid atribuute pole vaja, käib tee otse sulgudesse (`value` atribuudi nimi jäetakse ära). Muude atribuutide (`consumes`, `produces`, ...) korral tuleks kirjutada `@PostMapping(value = "...", ...)`.

Pärast seda teab dispetšer: kui tuleb `POST /api/login`, käivita `LoginController.loginUser()`.

## LoginRequest DTO ja @RequestBody (levinud vigane import) — `2:33:48` {#loginrequest}

### Selgitus

Sissetulev sõnum on JSON. Selle vastuvõtmiseks on vaja **klassi sama struktuuriga**:

```java
package ee.bcs.bank.controller;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

@Data                 // Lombok: getterid, setterid, toString, equals...
@NoArgsConstructor
@AllArgsConstructor
public class LoginRequest {
    private String username;
    private String password;
}
```

**Nimetamine:** `LoginRequest` (mitte `LoginTto` ega `LoginUser`) — kuna see objekt jääb **igaveseks ainult sissetuleva sõnumi kandjaks**. Kui sama klassi kasutataks ka vastuses, sobiks nimi `...Response` või neutraalne `...Dto`. Hoia nimed lühikesed — klassi nimi kordub muutuja nimes, muutuja nimi meetodites.

**Väljad `private`** → otse ligi ei saa → getterid/setterid on vajalikud. Lombok'i `@Data` teeb need. `@AllArgsConstructor` lubab objekti luua konstruktoriga. Tehnoloogia (Jackson) kasutab neid, et JSON-ist objekt kokku panna.

**Meetodi parameeter ja `@RequestBody`:**

```java
public void loginUser(@RequestBody LoginRequest loginRequest) { ... }
```

- `LoginRequest` — parameetri **tüüp**
- `loginRequest` — **silt** (muutuja nimi), mille kaudu meetodi sees andmetega toimetad: `loginRequest.getUsername()`
- `@RequestBody` — ütleb Spring'ile: "sõnumi keha (JSON) tuleb siia objekti panna"

> ⚠️ **Väga klassikaline viga:** `@RequestBody` importimisel pakub IDE **kahte varianti** — üks on Swagger'i annotatsioon, teine `org.springframework.web.bind.annotation.RequestBody`. **Vali Springi oma.** Kui valid vale, siis Request Body ei jõua meetodisse ja objekt saab väärtuseks `null`. Koodireal näeb kõik õige välja — viga on **vales importis**.
