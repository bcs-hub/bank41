## DataNotFoundException ja Exception-klassid — `0:04:44` {#datanotfoundexception-ja-exception-klassid}

### Selgitus

Java's tuleb vea signaliseerimiseks **visata (throw)** objekt, mis on loodud mingist **Exception-klassist**. Projektis on juba olemas kohandatud erindiklassid paketis `infrastructure/exception/` — nende vahel tuleb valida, mis kõige paremini sobib.

Kaks kandidaati:
- `DataNotFoundException` — kui midagi andmebaasist ei leitud.
- `ForbiddenException` — kui tegevus on keelatud.

Kuna "ühtegi asukohta ei leitud" on selgelt andmete puudumise juhtum, sobib `DataNotFoundException`.

### Koodinäide (`backend/src/main/java/ee/bcs/bank/infrastructure/exception/DataNotFoundException.java`)

```java
package ee.bcs.bank.infrastructure.exception;

import lombok.Getter;

@Getter
public class DataNotFoundException extends RuntimeException {
    private final String message;
    private final String errorCode;

    public DataNotFoundException(String message, String errorCode) {
        super(message);
        this.message = message;
        this.errorCode = errorCode;
    }
}
```

Konstruktor võtab sisse kaks stringi: `message` (inimloetav sõnum) ja `errorCode` (masinloetav kood). Sama struktuuriga on ehitatud ka `ForbiddenException`:

```java
package ee.bcs.bank.infrastructure.exception;

import lombok.Getter;

@Getter
public class ForbiddenException extends RuntimeException {
    private final String message;
    private final String errorCode;

    public ForbiddenException(String message, String errorCode) {
        super(message);
        this.message = message;
        this.errorCode = errorCode;
    }
}
```

Õpetaja rõhutab: uute väärtuste (message, errorCode) käsitsi laiali kirjutamine erinevatesse `throw`-lausetesse on riskantne — palju mõistlikum on need väärtused **koguda ühte kohta** ja sealt viidata. See toob järgmise teema — Enum.

### Päriselu analoogia

See on nagu erineva sisuga kirjaümbrikud postkontoris — ümbriku (Exception-klassi) kuju on alati sama (kaks lahtrit: sõnum ja kood), aga sisu (tegelik tekst ja kood) erineb olukorrast olenevalt.

## ErrorResponse Enum: veakoodid ja -sõnumid ühes kohas — `0:05:36` {#errorresponse-enum}

### Selgitus

Selle asemel, et kirjutada vea sõnumit ja koodi käsitsi otse `throw`-lausesse, koondatakse kõik äriveateated ja -koodid **ühte Enumi** — `backend/CLAUDE.md` nimetab seda `ErrorResponse` enumiks. See annab iga veatüübi jaoks nime (nt `NO_LOCATION_FOUND`), sõnumi ja HTTP staatuskoodi ühes kohas.

Videos vaadati, mis variandid seal juba on (nt `DATA_NOT_FOUND`, `FORBIDDEN`), ja arutati, kas nendest sobiks midagi otse — aga kuna "ei leitud ühtegi pangaautomaati" on väga spetsiifiline sõnum, tuli luua uus konstant: `NO_LOCATION_FOUND`.

Enumi konstruktor võtab sisse `message`-i ja `errorCode`-i (viimane defineeritakse otse enumi konstandi nimest, `name()` meetodiga — vt järgmine sektsioon).

**Tähelepanu:** enumi konstantide vahele **peab jääma koma** — kui lisad uue konstandi ja unustad eelmise järele koma panna, ei kompileeru kood. Üks levinud algajaviga on dubleerida esimene rida ja unustada, et viimasel real on semikoolon (lause lõpp), aga kõikidel muudel ridadel vahepeal koma.

### Koodinäide (illustratiivne, vastab `backend/CLAUDE.md` mustrile)

```java
package ee.bcs.bank.infrastructure.error;

import lombok.Getter;
import org.springframework.http.HttpStatus;

@Getter
public enum ErrorResponse {

    DATA_NOT_FOUND("Andmeid ei leitud", HttpStatus.NOT_FOUND),
    FORBIDDEN("Tegevus on keelatud", HttpStatus.FORBIDDEN),
    NO_LOCATION_FOUND("Ei leitud ühtegi pangaautomaati", HttpStatus.NOT_FOUND);

    private final String message;
    private final HttpStatus httpStatus;

    ErrorResponse(String message, HttpStatus httpStatus) {
        this.message = message;
        this.httpStatus = httpStatus;
    }
}
```

### Päriselu analoogia

See on nagu apteegi ravimikapp, kus igal karbil on oma silt (nimi), sisu (sõnum) ja doosisoovitus (staatuskood) — selle asemel, et iga kord uuesti käsitsi kirjutada, mis karbis on, loed sildilt.

## ApiError ja RestExceptionHandler: kuidas tarbija veast teada saab — `0:06:50` {#apierror-ja-restexceptionhandler}

### Selgitus

Kui Service kihis erind visatakse, tekib küsimus: **kuidas veebiteenuse tarbija** (nt frontend) sellest teada saab? Kontroller ise erindist midagi ei tea — vahepeale on vaja globaalset **erindite käsitlejat**.

Selleks on projektis `ApiError` klass (vea kandik, mis HTTP vastuses tagasi saadetakse) ja `RestExceptionHandler` klass, märgistatud `@ControllerAdvice`-ga — see "kuulab" kõikjal rakenduses visatud erindeid ja teisendab need korrektseks HTTP vastuseks.

Selle mustri lõi õpetaja juba varem `LoginController`-i jaoks — praeguses videos otsiti see üles ja **taaskasutati** samale mustrile toetudes (copy-paste + kohandamine), selle asemel, et kirjutada kõik nullist uuesti.

### Koodinäide (`backend/src/main/java/ee/bcs/bank/infrastructure/error/ApiError.java`)

```java
package ee.bcs.bank.infrastructure.error;

import lombok.Data;

@Data
public class ApiError {
    private String message;
    private String errorCode;
}
```

### Koodinäide (`backend/src/main/java/ee/bcs/bank/infrastructure/RestExceptionHandler.java`, väljavõte)

```java
@ControllerAdvice
public class RestExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler
    public ResponseEntity<ApiError> handleDataNotFoundException(DataNotFoundException exception) {
        ApiError apiError = new ApiError();
        apiError.setMessage(exception.getMessage());
        apiError.setErrorCode(exception.getErrorCode());
        return new ResponseEntity<>(apiError, HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler
    public ResponseEntity<ApiError> handleForbiddenException(ForbiddenException exception) {
        ApiError apiError = new ApiError();
        apiError.setMessage(exception.getMessage());
        apiError.setErrorCode(exception.getErrorCode());
        return new ResponseEntity<>(apiError, HttpStatus.FORBIDDEN);
    }
}
```

`@ExceptionHandler` annotatsiooniga meetod käivitub **automaatselt**, kui kusagil rakenduses (ükskõik millises kontrolleris) visatakse vastavat erinditüüpi — arendaja pole kunagi kohustatud igas kontrolleris `try/catch` kirjutama.

### Skeem

```
LocationService
   │  throw new DataNotFoundException(...)
   ▼
RestExceptionHandler (@ControllerAdvice, kuulab KÕIKI kontrollereid)
   │  püüab erindi kinni, koostab ApiError objekti
   ▼
HTTP 404 vastus:  { "message": "Ei leitud...", "errorCode": "NO_LOCATION_FOUND" }
```

### Päriselu analoogia

See on nagu häirekeskus, mis on ühendatud kõikide majade valvesüsteemidega — ei ole vaja, et igas majas oleks oma eraldi häirekeskus, üks keskus reageerib kõikjal tulevatele signaalidele ühtemoodi.

## @ResponseStatus ja API dokumentatsiooni täiendamine — `0:13:08` {#responsestatus-ja-dokumentatsioon}

### Selgitus

Kontrolleri meetodi juurde tuleb ka dokumentatsiooni (Swagger/OpenAPI `@ApiResponse`) täiendada — lisada kirjeldus selle kohta, mis juhtub, kui staatuskood on `404`. Õpetaja märgib, et **200 (OK) vastuse dokumenteerimine on vaikimisi** — kui üks vastus on juba märgitud, ei ole vaja lisada, et "kui kõik on hästi, tuleb 200" — see on eeldatav käitumine.

Samuti kontrolliti, et `@ResponseStatus` või vastava `@ApiResponse` annotatsiooni sees oleks õige staatuskood — videos avastati viga: kirjas oli vale kood, mis parandati `404`-ks (vastavuses ülalpool kokkulepitud `ErrorResponse.NO_LOCATION_FOUND` staatusega).

### Koodinäide (illustratiivne)

```java
@Operation(summary = "Tagastab pangaautomaatide asukohtade infot")
@ApiResponses({
    @ApiResponse(responseCode = "404", description = "Ühtegi asukohta ei leitud")
})
@GetMapping("/atm/locations")
public List<LocationInfo> findLocations(@RequestParam(required = false) Integer cityId) {
    return locationService.findFilteredLocations(cityId);
}
```

### Päriselu analoogia

See on nagu toote pakendil kirjas olev hoiatus ainult ebatavaliste olukordade kohta ("hoida jahedas") — tavapärast, eeldatavat käitumist ("toode on söödav") ei ole vaja pakendile eraldi kirjutada.

## FEB-7 valmis: Git töövoog ja "body leasing" analoogia — `0:19:40` {#feb-7-valmis-git-toovoog}

### Selgitus

Kui FEB-7 on valmis, liidetakse (merge'itakse) muudatused tagasi õpetaja harusse. Päris töövoos ei saa arendaja otse `master`-isse merge'ida — muudatus läheb läbi **serveri** (nt GitHub/GitLab pull request'i), kus keegi teine (kolleeg, tech lead) vaatab koodi läbi, kinnitab ("pöidlaga heakskiit") ja alles siis liidetakse.

Oluline detail: kui harul on mitu commit'i, ei tuleks neid **squash**-ida (kokku pigistada) üheks — kõik kolm eraldi commit'i peaksid minema `master`-isse eraldi, säilitades ajaloo.

Sellest kasvas välja pikem sisuline kõrvalepõige: õpetaja tõi analoogia **"body leasing"**-ust (rätsepate/alltöövõtu firmadest) — kirjeldades, kuidas mõnes ettevõttes (nt LHV) töötavad ka arendajad, kes formaalselt ei ole selle ettevõtte palgal, vaid on "laenatud" teise firma kaudu, sooviga vältida suurettevõtte bürokraatiat (aastavestlused, vormid) väiksema paindlikkuse nimel.

### Päriselu analoogia

Git-i pull request'i heakskiitmine on nagu toimetaja ülelugemine enne ajaleheartikli avaldamist — autor (arendaja) on kirjutanud teksti, aga see ei jõua avalikkuse ette enne, kui teine paar silmi on selle üle vaadanud.

## Many-to-Many seostabel ja andmete liiasuse vältimine — `0:25:53` {#many-to-many-seostabel}

### Selgitus

`location_transaction_type` on klassikaline **many-to-many (mitu-mitmele)** seos: ühel asukohal (nt Sikupilli Prisma) võib olla mitu teenust (sissemakse, väljamakse, maksed), ja ühel teenusel (nt "raha väljamakse") võib olla mitu asukohta.

Reaalse näite peal: **Sikupilli Prisma** juures on seostabelis kolm rida — kõik kolm teenust olemas. **Tondiraba/Tondi selver** juures on ainult kaks rida — ainult teenused 1 ja 2 (raha sissemakse, väljamakse), kolmas (maksed) puudub.

Õpetaja tõstab siin esile olulise printsiibi: seostabelis **hoitakse ainult neid ridu, mis päriselt eksisteerivad** — mitte kõiki kolme rida iga asukoha jaoks, kus mittevajalikud on märgitud "ei" (false). See vältimine on teadlik otsus **andmete liiasuse** vastu: kui teenuseid oleks sada ja enamik neist ei kehti, oleks jaburalt palju kasutuid ridu (99 "ei" + 1 "jah") hoida andmebaasis. Mõistlikum on hoida andmebaasis vaid see, mida **peab teadma**, ja tuletada ülejäänu (mis puudub, on vaikimisi "ei") **loogikaga** (koodis).

### Skeem

```
Sikupilli Prisma andmebaasis:            Tondiraba Selver andmebaasis:
  location_id=1, transaction_type_id=1     location_id=2, transaction_type_id=1
  location_id=1, transaction_type_id=2     location_id=2, transaction_type_id=2
  location_id=1, transaction_type_id=3     (transaction_type_id=3 PUUDUB — see EI TÄHENDA
                                             uut rida "false"-iga, vaid puudumist üldse)
```

### Päriselu analoogia

See on nagu kaupluse laoseis, kus kirja pannakse ainult see, mida päriselt on — ei kirjutata iga toote kohta eraldi rida "seda pole laos", kui asi on selge juba sellest, et rida puudub.

## MapStruct: automaatne väljade mäppimine ja @Mapping(ignore) — `0:36:52` {#mapstruct-automaatne-mappimine}

### Selgitus

Kui `LocationMapper`-is ühe välja jaoks (nt `longitude`) on lähte- (`Location`) ja sihtobjektis (`LocationInfo`) **täpselt sama nimi**, ei ole `@Mapping`-annotatsiooni vaja kirjutada — MapStruct **oskab iseseisvalt aru saada**, et need väljad käivad kokku.

Sellegipoolest soovitab õpetaja **kõik väljad ikkagi eksplitsiitselt kirja panna**, isegi kui need on samanimelised — mitte jätta abstraktset "vaikimisi käitumist" varjatuks. Põhjendus: kui koodilugeja (nt uus arendaja) tuleb hiljem vaatama, kuidas `LocationInfo` kokku pannakse, näeb ta koodist **täpselt**, mis kust tuleb — ei pea pead vaevama, mis samanimelised väljad taustal "iseenesest" käituvad.

Kui aga väli **ei tohiks** üldse mäppitud saada (nt sama nimega väli, mida teadlikult ignoreerida), kasutatakse `@Mapping`-annotatsiooni atribuuti `ignore = true`.

### Koodinäide (illustratiivne)

```java
@Mapper(componentModel = "spring")
public interface LocationMapper {

    @Mapping(source = "id", target = "locationId")
    @Mapping(source = "city.cityName", target = "cityName")
    @Mapping(source = "locationName", target = "locationName")
    @Mapping(source = "longitude", target = "longitude")
    @Mapping(source = "latitude", target = "latitude")
    @Mapping(target = "transactionTypes", ignore = true)
    LocationInfo toLocationInfo(Location location);

    List<LocationInfo> toLocationInfos(List<Location> locations);
}
```

`transactionTypes` on siin teadlikult `ignore = true` — see väli täidetakse **hiljem, eraldi loogikaga** (mitte otse `Location`-ilt), sest sellist infot lähteobjektis olemas ei ole.

### Päriselu analoogia

See on nagu kaks nimekirja, kus samad tooted on kirjas samas järjekorras — kui nimekirjad juba loomulikult "sobituvad" (samad nimed), ei ole vaja iga rea juurde märkida "see rida vastab teisele reale". Aga ikkagi on selgem, kui iga rida on eraldi märgitud, mitte jäetud "iseenesest mõistetavaks".

## Uus DTO: TransactionTypeDto — nimekonflikt entiteediga — `0:44:42` {#uus-dto-transactiontypedto}

### Selgitus

Task nõuab, et igas asukoha-vastuse objektis (`LocationInfo`) oleks väli `transactionTypes` — **list objektidest**, kus igaühel on: `transactionTypeId`, `transactionTypeName`, `isAvailable`.

Kuna sellist objekti veel ei eksisteeri, tuleb see luua. Aga tekib nimekonflikt: kõige loomulikum nimi oleks `TransactionType` — kuid see nimi on **juba hõivatud** JPA entiteedi klassi poolt (mis peegeldab andmebaasi tabelit). Kahe erineva klassi jaoks (Entity vs DTO) ei saa kasutada sama nime samas paketistruktuuris.

Lahendus: uue klassi nimeks valitakse **`TransactionTypeDto`** (suuline lühend "Tto") — DTO-nimemall, mida projekt juba mujal kasutab (vt `backend/CLAUDE.md` "DTO vs entiteedid" konventsiooni).

Sama küsimus tekkis ka mõtte tasandil: kas selline objekt sobiks ka **uue transaction type'i lisamiseks** (POST päring)? Vastus: **ei** — kuna DTO-l ei tohiks lisamisel ID-d ette anda (ID tuleb andmebaasist), vajaks lisamisstsenaarium eraldi klassi (nt `TransactionTypeRequest`). Praegu, kuna lisamisfunktsionaalsust veel ei nõuta, jäetakse see klass loomata — YAGNI-põhimõte ("You Aren't Gonna Need It" — ära loo asju, mida hetkel vaja ei ole).

### Koodinäide (illustratiivne)

```java
package ee.bcs.bank.transactiontype.controller;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
@AllArgsConstructor
public class TransactionTypeDto {
    private Integer transactionTypeId;
    private String transactionTypeName;
    private Boolean isAvailable;
}
```

Klassil on nii **tühja argumendiga konstruktor** kui ka **kõiki välju sisaldav konstruktor** — see annab paindlikkuse, kuidas iganes objekti hiljem luuakse (kas Setterite kaudu või ühe konstruktori väljakutsega).

### Päriselu analoogia

See on nagu kaks eri nimesilti kahele erinevale ametikohale ("Kokk" vs "Peakokk") — kuigi mõlemad seostuvad köögiga, ei saa kaks eri töötajat kanda täpselt sama nimesilti, kui need tähendavad süsteemis erinevat asja.

## Algoritmi kavandamine: miks naiivne päring ei tööta — `0:57:29` {#algoritmi-kavandamine}

### Selgitus

Enne kirjutamist arutletakse, **kuidas** täita `LocationInfo` objekti `transactionTypes` väli õigete andmetega. Esimene, näiliselt loogiline idee: käia otse läbi `location_transaction_type` seostabelit ja tuua sealt kõik konkreetse asukoha read.

**Probleem:** see toob välja **vaid need read, mis eksisteerivad** — nt Tondiraba puhul kaks rida, mitte kolm. Aga task nõuab, et vastuses oleks **kõik kolm** teenust, koos `isAvailable = false`-iga puuduva jaoks. Seostabelist otse päring ei annaks kunagi infot **puuduvate** teenuste kohta — ta ei "tea", et midagi peaks olemas olema, aga ei ole.

### Skeem

```
Naiivne päring: "SELECT * FROM location_transaction_type WHERE location_id = 2"
  → tagastab 2 rida (transaction_type_id 1, 2)
  → EI tagasta infot transaction_type_id=3 kohta (ei "true", ei "false" — LIHTSALT PUUDUB)

Aga vajalik tulemus: 3 objekti, kus kolmandal isAvailable=false
```

### Päriselu analoogia

See on nagu kohalviibimise nimekiri koolis, kus kirja pannakse ainult **kohal olnud** õpilased — kui tahad teada, kes **puudus**, ei piisa ainult sellest nimekirjast, vaja on ka **kogu klassi nimekirja**, et arvutada välja, kes sellel ei ole.

## Õige algoritm: eksisteerimiskontroll iga kombinatsiooni kohta — `1:03:48` {#oige-algoritm}

### Selgitus

Õige lähenemine: **iga asukoha** ja **iga võimaliku teenuse** kombinatsiooni jaoks eraldi küsida andmebaasilt: "kas selline rida seostabelis eksisteerib?" See on kahekordne tsükkel (nested loop):

1. Käi läbi kõik asukohad (`LocationInfo` list).
2. Igas asukohas käi läbi kõik kolm võimalikku teenust (`TransactionTypeDto` list, mille kõik `isAvailable` väärtused algavad `false`-iga).
3. Iga (asukoht, teenus) paari jaoks küsi andmebaasilt: "kas `location_transaction_type` tabelis on rida sellise `location_id` ja `transaction_type_id`-ga?" (tõeväärtuslik vastus, `true`/`false`).
4. Kui vastus on `true`, seadista vastava `TransactionTypeDto` `isAvailable` väärtuseks `true`.

Õpetaja rõhutab teadlikult: see lahendus **ei ole optimaalne** (andmebaasi poole pöördutakse mitu korda samade andmete pärast) — aga eesmärk on õppida **algoritmilist mõtlemist** (tsükkel tsükli sees, iga elemendi eraldi käsitlemine), mitte kirjutada kohe kõige tõhusamat SQL-i. Efektiivsem variant (üks SQL-päring JOIN-idega) on põhimõtteliselt võimalik, aga jäetakse teadlikult hilisemaks harjutuseks.

### Skeem

```
for igaLocationInfo in locationInfos:
    for igaTransactionTypeDto in [kõik 3 võimalikku teenust]:
        eksisteerib = existsByLocationIdAndTransactionTypeId(
                          igaLocationInfo.locationId,
                          igaTransactionTypeDto.transactionTypeId)
        igaTransactionTypeDto.isAvailable = eksisteerib
    igaLocationInfo.transactionTypes = [need 3 täidetud TransactionTypeDto objekti]
```

### Päriselu analoogia

See on nagu kontrolljälgimislist enne lennukisse minekut — iga reisija kohta kontrollitakse eraldi, iga vajaliku dokumendi olemasolu ("on pass olemas? on pilet olemas? on viisa olemas?"), isegi kui suurem osa vastuseid on lihtsalt "jah".

Kõigepealt on vaja **kõiki** transaction type'e (kõiki kolm rida `transaction_type` tabelist) — selleks luuakse uus `TransactionTypeRepository`, mis laiendab Spring Data JPA baasliidest. }

## TransactionTypeMapper: entity → dto ja vaikeväärtus — `1:23:17` {#transactiontypemapper}

### Selgitus

Kui `TransactionType` entity (väljad: `id`, `name`) on olemas ja `TransactionTypeDto` (väljad: `transactionTypeId`, `transactionTypeName`, `isAvailable`) on olemas, on vahele vaja **Mapperit**, mis teisenduse käsitsi kirjutamise ära teeb.

Erinevalt eelmistest mapper'itest (nt `LocationMapper`), kus enamik väljanimesid ühtisid, siin on kõik väljanimed **erinevad** (`id`→`transactionTypeId`, `name`→`transactionTypeName`) — MapStruct ei oska siin midagi "iseenesest" ära arvata, kõik peab olema eksplitsiitselt kirjas.

Lisaks: `isAvailable` väljal **ei ole vastet** lähteobjektis (`TransactionType` entity-l sellist välja pole) — see info ei saagi tabelist tulla. Lahendus: `@Mapping`-annotatsiooniga määratakse **vaikeväärtus** (`constant`), mis pannakse igale värskelt loodud DTO-le, sõltumata sisendist:

### Koodinäide (illustratiivne)

```java
@Mapper(componentModel = "spring")
public interface TransactionTypeMapper {

    @Mapping(source = "id", target = "transactionTypeId")
    @Mapping(source = "name", target = "transactionTypeName")
    @Mapping(target = "isAvailable", constant = "false")
    TransactionTypeDto toTransactionTypeDto(TransactionType transactionType);
}
```

`constant`-atribuut võtab sisse ainult **stringi** — isegi kui sihtväli on `Boolean`, kirjutatakse väärtus jutumärkides (`"false"`), ja MapStruct teeb konversiooni tüübi järgi ise ära.

Vaikeväärtuseks valitakse `false` (mitte `true`), sest hilisem kahekordne tsükkel ([vt eelmine sektsioon](#oige-algoritm)) muudab seda `true`-ks ainult juhul, kui teenus **päriselt eksisteerib** antud asukohas — see peegeldab õiget "algolek: ei ole kättesaadav, kuni tõestatud vastupidist" loogikat.

### Päriselu analoogia

See on nagu tühja hindamislehe väljastamine, kus kõik lahtrid on vaikimisi "läbi kukkunud" (false), ja hiljem märgitakse ainult tegelikult läbitud punktid "õnnestunuks" (true) — vaikeväärtus on ettevaatlik eeldus, mida tõestamine muudab.

### Selgitus

Kuna kogu andmehulk on tegelikult **list** (kõik transaction type'id, mitte üks korraga), tuleb `toTransactionTypeDto`-meetod ümber teha listi-versiooniks. Sarnaselt eelnevalt õpitud mustriga (vt [video-1 materjal, "Mapper ja MapStruct"](2026-09-11-video-1.md#mapper-mapstruct)): kui **üksik-objekti** teisendusmeetod on olemas, oskab MapStruct **iseseisvalt tuletada** ka listi versiooni.

```java
@Mapper(componentModel = "spring")
```

## LocationTransactionTypeRepository: existsBy... päringumeetod — `1:41:49` {#existsby-paringumeetod}

### Selgitus

Vaja on kontrollida, kas seostabelis **eksisteerib** rida konkreetse `locationId` ja `transactionTypeId` kombinatsiooniga. Spring Data JPA toetab meetodinimede peale ehitatud päringute peret — üks nendest on `existsBy...`, mis tagastab `boolean` (mitte kogu objekti või listi).

Selle jaoks luuakse uus `LocationTransactionTypeRepository` (entity `LocationTransactionType` seostabeli jaoks veel ei eksisteerinud eraldi repositooriumit, kuigi entity oli juba olemas).

`existsBy`-meetod erineb `findBy`-meetodist tehniliselt: taustal ei tooda kõiki ridu kätte, vaid andmebaas kontrollib ridade **arvu** (`count`) ja tagastab `true`, kui arv on suurem kui null.

### Koodinäide (illustratiivne)

```java
public interface LocationTransactionTypeRepository
        extends JpaRepository<LocationTransactionType, Integer> {

    boolean existsByLocationIdAndTransactionTypeId(Integer locationId, Integer transactionTypeId);
}
```

Meetodinime osad (`Location`, `Id`, `And`, `TransactionType`, `Id`) vastavad täpselt seostabeli väljadele — Spring Data JPA parsib nime ja koostab vastava SQL/JPQL päringu automaatselt, ilma et arendaja peaks käsitsi `@Query` kirjutama.

### Skeem

```
existsByLocationIdAndTransactionTypeId(1, 3)
        │
        ▼
SELECT COUNT(*) FROM location_transaction_type
  WHERE location_id = 1 AND transaction_type_id = 3
        │
        ▼
count > 0  →  true / false
```

### Päriselu analoogia

See on nagu küsimus "on see nimi nimekirjas?" versus "too mulle terve nimekiri" — esimesele piisab lihtsast jah/ei vastusest, mis on kiirem ja lihtsam kui kogu nimekirja läbi töötlemine.

## Topeltsükkel: isAvailable väärtuste määramine ja testimine — `1:53:26` {#topeltsykkel-ja-testimine}

### Selgitus

Kõik osad koos: `LocationService`-is käiakse tsükliga läbi iga `LocationInfo`, ja igas neist läbitakse veel tsükliga kõik `TransactionTypeDto`-d, seadistades `isAvailable`-väärtuse vastavalt `existsByLocationIdAndTransactionTypeId`-le.

### Koodinäide (illustratiivne)

```java
private void addTransactionTypes(List<LocationInfo> locationInfos) {
    for (LocationInfo locationInfo : locationInfos) {
        List<TransactionTypeDto> transactionTypeDtos = createTransactionTypeDtos();
        for (TransactionTypeDto transactionTypeDto : transactionTypeDtos) {
            boolean exists = locationTransactionTypeRepository.existsByLocationIdAndTransactionTypeId(
                locationInfo.getLocationId(), transactionTypeDto.getTransactionTypeId());
            transactionTypeDto.setIsAvailable(exists);
        }
        locationInfo.setTransactionTypes(transactionTypeDtos);
    }
}

private List<TransactionTypeDto> createTransactionTypeDtos() {
    Sort sortByNameDescending = Sort.by(Sort.Direction.DESCENDING, "name");
    List<TransactionType> transactionTypes = transactionTypeRepository.findAll(sortByNameDescending);
    return transactionTypeMapper.toTransactionTypeDtos(transactionTypes);
}
```

Tondiraba/Sikupilli andmed vahepeal **kustutati** andmebaasist (üks rida seostabelist), et kontrollida, kas puuduva rea juures ilmub õigesti `false` — see kinnitas, et algoritm reageerib õigesti andmete tegelikule seisule, mitte lihtsalt "ikka kõik true".

### Päriselu analoogia

See on nagu testrežiim tulekahjualarmisüsteemis — enne kasutusele võtmist tekitatakse teadlikult "häire" (andmete kustutamine), et kontrollida, et süsteem tegelikult reageerib õigesti, mitte alati vaikimisi ühte moodi vastab.

## Refaktoreerimine (Extract Method): loetav ja äriloogiline kood — `2:00:18` {#refaktoreerimine-extract-method}

### Selgitus

Kui teenus **töötab õigesti**, algab teine, eraldiseisev etapp: koodi teha **loetavamaks**. Õpetaja rõhutab: "töötab" ja "on hea kood" ei ole sama asi — praeguses kujul on meetod pikk ja raske lugeda, kuigi tehniliselt korrektne.

Kasutatud tehnika on **Extract Method** (IDE refaktoreerimisfunktsioon, tavaliselt klahvikombinatsiooniga nagu `Ctrl+Alt+M`): valid koodiploki, ja IDE tekitab sellest automaatselt uue, eraldi nimega meetodi, mille kehasse liigub valitud kood, ja väljakutse asendab selle vana koha peal.

Kolm eraldi meetodit tekkisid tükk-tükk haaval:
1. **Valideerimine** — kontroll, et vähemalt üks asukoht eksisteerib (varem `if`-lause otse peameetodis).
2. **Andmete täiendamine** — `transactionTypes`-välja lisamine igale `LocationInfo`-le.
3. **DTO-de loomine** — kõigi kolme `TransactionTypeDto`-objekti loomine algseisus.

Meetodi nimed valiti **äriloogilised**, mitte tehnilised — nt esialgne mõte `handleX` asendati täpsemaga: `validateAtLeastOneLocationExists` (mitte lihtsalt "handle", vaid ütleb täpselt, mida meetod kontrollib).

### Koodinäide (illustratiivne)

```java
private void validateAtLeastOneLocationExists(List<Location> locations) {
    if (locations.isEmpty()) {
        throw new DataNotFoundException(
            ErrorResponse.NO_LOCATION_FOUND.getMessage(),
            ErrorResponse.NO_LOCATION_FOUND.name()
        );
    }
}
```

Arutati ka, kas mõned pisemad koodiread (nt üherealine repositooriumi väljakutse) tasub üldse eraldi meetodiks tõsta — õpetaja märgib, et see on **maitse küsimus**: iga uus meetod lisab kaks rida "raamistikku" (deklaratsioon + sulgudud), mis pole alati loetavuse võitu väärt, kui sisu on niigi väga lühike ja selge.

### Päriselu analoogia

See on nagu esseed toimetades pikkade lausete jagamine lühemateks lõikudeks pealkirjadega — sisu ei muutu, aga lugejal on palju lihtsam aru saada, mis osa käsitleb mida.

## Extract Method mehaanika: "sildid" väljaspool koodilõiku — `2:07:40` {#extract-method-mehaanika}

### Selgitus

Extract Method'i tegemisel on kriitiline mõista, mis juhtub **muutujatega**, mis viidatakse koodilõigu sees, aga on **defineeritud väljaspool** seda (enne koodilõigu algust). Selline muutuja ei "ole teadlik" oma välisest elust — kui koodilõik läheb eraldi meetodisse, ei saa see muutuja enam automaatselt kaasa; see tuleb **käsitsi parameetrina edasi anda**.

Sama kehtib vastupidises suunas: kui koodilõik loob **uue väärtuse**, mis läheb kasutusse ka **pärast** seda koodilõiku (väljaspool), peab see väärtus tulema meetodi **tagastusväärtusena** (`return`) — Java meetod saab tavaliselt tagastada vaid **ühe** objekti (erinevalt mõnest teisest keelest, kus saab tagastada mitu väärtust korraga).

Näide: kui `transactionTypes`-silt (muutuja) on loodud koodilõigu **sees** ja kasutust ei ole väljaspool, on kõik lihtne — kogu loogika saab minna otse eraldi meetodisse. Aga kui `locationInfo` viidatakse koodilõigu sees, olles defineeritud **enne** koodilõiku (välises tsüklis), peab see minema meetodi **parameetrina** sisse.

### Skeem

```
Enne Extract Method:
  LocationInfo locationInfo = ...;      ◄── defineeritud VÄLJASPOOL koodilõiku
  ┌─────────────────────────────────┐
  │  <koodilõik, mida ekstraktida>  │   kasutab locationInfo SEES
  │  transactionTypes = ...;        │   ◄── loodud SEES koodilõigu
  └─────────────────────────────────┘
  kasutab transactionTypes VÄLJASPOOL? EI → jääb koodilõigu sisse

Pärast Extract Method:
  addTransactionTypes(locationInfo);    ◄── locationInfo antakse PARAMEETRINA
```

### Päriselu analoogia

See on nagu retsepti osa väljalõikamine eraldi kaardile — kui retsept viitab köögiriistale, mis on juba köögis olemas (väljaspool retsepti), peab uus kaart selgelt kirja panema, mida kaasa tuua; kui retsept toodab lõpptulemuse (koogi), peab kaart selgelt näitama, mis lõpuks käest antakse.

## Lõplik meetod loeb nagu lugu + kokkuvõte ja plaanid — `2:23:53` {#loplik-meetod-ja-kokkuvote}

### Selgitus

Pärast kolme meetodi eraldamist näeb peameetod välja lühike ja **järjestikku loetav**, nagu lühijutt: otsi andmed → valideeri → teisenda DTO-deks → lisa lisainfo → tagasta.

### Koodinäide (illustratiivne, kokkuvõtlik lõppseis)

```java
public List<LocationInfo> findFilteredLocations(Integer cityId) {
    List<Location> locations =
        locationRepository.findFilteredLocations(cityId, Status.ACTIVE.getCode());
    validateAtLeastOneLocationExists(locations);
    List<LocationInfo> locationInfos = locationMapper.toLocationInfos(locations);
    addTransactionTypes(locationInfos);
    return locationInfos;
}
```

Õpetaja rõhutab, kuidas sellist koodi **loeda**, kui midagi on segane: ära proovi lugeda kõike korraga. Loe rida-realt, "usalda" iga meetodinime (mida see väidab tegema) esimesel läbimisel, ja mine detailidesse **ainult sinna**, kus midagi läks valesti või on ebaselge. See on realistlik viis, kuidas kogenud arendajad ka päriselus võõrast koodi loevad — mitte tervet süsteemi korraga peas hoida.

Lõpus tehti kokkuvõte ja plaanid:

- **FEB-8** jäi suures pildis valmis, kuigi veel oli võimalusi täiendavaks meetoditeks lõikamiseks (õpetaja jättis mõne "ilusama" jaotuse teadlikult tegemata, kuna ei tulnud kohe head nimeideed pähe — see on normaalne osa refaktoreerimisest).
- Muudatused **merge'iti** õpetaja harusse; õpilastel palutakse teha oma haru **õpetaja uuenenud haru pealt uuesti**, mitte jätkata vanalt versioonilt.
- Järgmisel nädalal: veel praktilisi backend-harjutusi, seejärel projektide planeerimise õpetus (kuidas alustada mitte "nullist", vaid olemasoleva "mocki" pealt arendust jätkata).
- Õpetaja tunnistas otse, et see nädala teema (algoritmiline mõtlemine, tsükkel tsükli sees, mitmekihiline loogika) on üks keerulisemaid backend'i kursuse osi — julgustas mitte kartma, kui midagi tundub praegu segane, kuna see areneb praktikaga ("hands-on experience").

### Päriselu analoogia

Hea, refaktoreeritud meetod on nagu raamatu sisukord — kui sisukorra pealkirjad on selged, ei pea lugeja kohe iga peatükki läbi lugema, et aru saada, millest raamat kokkuvõttes räägib; ta saab minna otse sellesse peatükki, mis teda huvitab või mis on ebaselge.
