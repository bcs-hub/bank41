## VEB-12 – BaseModal'ist LocationInfoModal komponendi ekstraktimine — `0:00:19` {#komponendi-ekstraktimine}

Eelmises videos loodi `BaseModal` — korduvkasutatav modal-raamistik slotidega. Nüüd on vaja seda kasutada konkreetse ülesande jaoks: näidata pangaautomaadi asukoha infot.

### Selgitus

Õpetaja toob välja kaks võimalikku lähenemist:

1. **Kirjutada sisu (title/body slotid) otse sinna vaatesse, kus modali vaja on** (nt `AtmsView.vue`). See töötab, aga risustab vaate koodi.
2. **Luua konkreetsele ülesandele oma komponent** (nt `LocationInfoModal.vue`), mis ise kasutab `BaseModal`-it seespool ja täidab slotid valmis sisuga. Väljapoole jääb nähtavaks ainult üks puhas tag: `<LocationInfoModal />`.

Teine variant valitakse, kuna see annab **selgema vastutusjaotuse**: kui arendaja tuleb hiljem vaadet lugema, näeb ta lihtsalt `<LocationInfoModal />` ja teab kohe, et see osa tegeleb asukoha info kuvamisega — tal pole vaja mõelda kogu modali sisemisele HTML-struktuurile.

### Skeem

```
AtmsView.vue (Parent)
   │
   │ <LocationInfoModal>
   ▼
LocationInfoModal.vue (Child)
   │  kasutab BaseModal'it,
   │  täidab title/body slotid
   ▼
BaseModal.vue (Grandchild vaatenurgast Parent'ile)
```

### Koodinäide

Praktikas loodi IDE "Extract Component" tööriistaga uus fail otse vanast koodilõigust. Lõplik `LocationInfoModal.vue` näeb koodibaasis välja nii:

```vue
<script>
import BaseModal from '@/components/modal/BaseModal.vue'
import AtmImage from '@/components/image/AtmImage.vue'
import TransactionTypesCheckbox from '@/components/location/TransactionTypesCheckbox.vue'

export default {
  name: 'LocationInfoModal',
  components: { TransactionTypesCheckbox, AtmImage, BaseModal },
  props: {
    locationInfoModalIsOpen: Boolean,
    location: Object,
  },
  emits: ['event-location-info-modal-closed']
}
</script>

<template>
  <BaseModal
    :is-open="locationInfoModalIsOpen"
    @event-modal-closed="$emit('event-location-info-modal-closed')"
  >
    <template #title>{{ location.locationName }}</template>

    <template #body>
      <div class="container text-center">
        <div class="row justify-content-center">
          <div class="col">
            <h5>Automaatide arv: {{ location.numberOfAtms }}</h5>
            <TransactionTypesCheckbox
              :transaction-types="location.transactionTypes"
              :switches-disabled="true"
            />
          </div>
          <div class="col">
            <AtmImage :image-data="location.imageData" />
          </div>
        </div>
      </div>
    </template>
  </BaseModal>
</template>
```

Pane tähele: `LocationInfoModal` ei tea midagi modali sulgemise **tehnilisest teostusest** (CSS, z-index, backdrop) — ta lihtsalt annab `BaseModal`-ile edasi `isOpen` väärtuse ja kuulab `event-modal-closed` sündmust, mille ta omakorda saadab edasi oma vanemale uue nimega `event-location-info-modal-closed`.

### Miks nimi muutub sündmuse edastamisel?

`BaseModal` saadab neutraalse sündmuse `event-modal-closed` (ta ei tea, mis modal ta on). `LocationInfoModal` aga muudab selle spetsiifilisemaks nimeks — see on oluline, kui rakenduses on hiljem mitu erinevat modalit: iga modali sulgemissündmus peab olema eristatav.

## Props ja event'ide vool läbi kolme taseme (Parent → Child → Grandchild) — `0:07:11` {#props-vool}

Kui komponendid on nüüd kolmetasandilised (`AtmsView` → `LocationInfoModal` → `BaseModal`), tuleb mõista, kuidas info nende vahel liigub.

### Selgitus

Vue's kehtib range reegel: **andmed (props) voolavad alati ainult ülevalt alla** — vanemalt lapsele, lapselt lapselapsele. **Sündmused (events) voolavad alati alt üles** — vastupidises suunas. Otsest "hüpet" üle ühe taseme pole olemas: kui `AtmsView` tahab midagi öelda `BaseModal`-ile, peab see info läbima `LocationInfoModal`-i.

### Skeem

```
AtmsView (Parent)
   │  props alla ↓                    ↑ events üles
   ▼                                  │
LocationInfoModal (Child)
   │  props alla ↓                    ↑ events üles
   ▼                                  │
BaseModal (Grandchild)
```

### Koodinäide

Andmed voolavad `AtmsView`-st alla:

```vue
<LocationInfoModal :location-info-modal-is-open="locationInfoModalIsOpen"
                   :location="location"
                   @event-location-info-modal-closed="locationInfoModalIsOpen = false"
/>
```

`LocationInfoModal` võtab need vastu propsina ja annab need omakorda edasi `BaseModal`-ile (`:is-open="locationInfoModalIsOpen"`). Kui kasutaja klõpsab `BaseModal`-i sulgemisnupul, saadab see sündmuse üles `LocationInfoModal`-ile, kes saadab selle omakorda üles `AtmsView`-le, kus lõpuks muudetakse `locationInfoModalIsOpen` väärtuseks `false`.

### Miks mitte kirjutada `parent.$refs` abil otse "kaugele" komponendile?

Vue toetab tehniliselt ka teisi viise (nt `ref`), aga õpetaja rõhutab, et projekti kokkulepitud arhitektuur on **props alla, events üles** — see hoiab andmevoo alati ennustatava ja jälgitavana, isegi kui komponentide puu kasvab sügavamaks.

## Git ajalugu ja saladused – ärge kunagi committige API võtmeid — `0:22:01` {#git-saladused}

Väike kõrvalepõige — kui kogemata luuakse ja kustutatakse fail Git repositooriumis, tõstatub oluline turvateema.

### Selgitus

Kui fail Git repositooriumisse **commititakse** ja hiljem kustutatakse, ei kao see failisisu tegelikult kuskile — see **jääb Git ajalukku alles** ja on kõigile, kellel on ligipääs repositooriumile, endiselt leitav ja loetav (isegi kui fail ise "praeguses" versioonis enam ei eksisteeri).

**Praktiline reegel:** ärge kunagi commitige paroole, API võtmeid või muid saladusi otse koodifaili sisse — isegi kui plaanite need "hiljem eemaldada". Kui see kogemata juhtub:

1. Kustutage fail ja tehke uus commit.
2. **Vahetage saladus välja** (nt genereerige uus API võti) — vana võti tuleb lugeda kompromiteerituks, kuna see on Git ajaloos endiselt olemas.
3. Kasutage selle asemel **keskkonnamuutujaid** (environment variables) — kood viitab muutuja nimele (nt `MY_PASSWORD`), mille tegelik väärtus tuleb käivitamise ajal väljastpoolt koodibaasi ega ole kunagi koos koodiga versioonihalduses.

### Miks see AI-arenduse kontekstis eriti oluline on?

Õpetaja mainib, et AI-assistendid (nt Claude) on saladuste suhtes üldiselt tundlikud — kui assistent avastab, et loeb faili, milles on API võti, võib ta ise soovitada selle koheselt tühistada/uuendada, kuna igasugune fail, mida AI-le "ette söödetakse", võib teoreetiliselt kuhugi salvestuda.

## Oma CSS-klasside lisamine projekti (main.css) — `0:36:39` {#oma-css-klassid}

Asukoha nimi peab visuaalselt näima klõpsatava lingina, kuigi tehniliselt kasutatakse tavalist `<div>` elementi (mitte `<a>` linki, kuna me ei taha, et see viiks kuhugi teisele URL-ile).

Seetõttu asendatakse `<a>` tavalise `<div>`-ga, millele antakse CSS abil "lingi väljanägemine" ilma lingi funktsionaalsuseta.

## Event'i nimetamine lapse (child) vaatenurgast — `0:48:24` {#event-nimetamine}

Kui asukoha nimi (nüüd klõpsatav "link") saadab sündmuse üles vanemkomponendile, tuleb sündmusele anda sobiv nimi.

### Selgitus

Kesksed reegel: **laps (child) komponent ei tea kunagi, mida vanem (parent) tema sündmusega peale hakkab.** Seetõttu ei tohi sündmuse nimi kunagi kirjeldada äriloogikat (nt `event-open-location-info-modal`) — laps ise ei tea, et vanem plaanib sellest sündmusest modali avada. Sündmuse nimi peab kirjeldama **ainult seda, mis lapse sees tegelikult juhtus**: kasutaja klõpsas asukoha nimel.

### Koodinäide

```vue
<!-- LocationsTable.vue (Child) -->
<div @click="$emit('event-location-name-click', location.locationId)">
  {{ location.locationName }}
</div>
```

```vue
<!-- AtmsView.vue (Parent) -->
<LocationsTable :locations="locations" @event-location-name-click="handleOpenLocationInfoModal" />
```

Sündmuse nimi `event-location-name-click` kirjeldab täpselt, mis juhtus (asukoha nime peale klõpsati) — mitte seda, mida vanem selle peale otsustab teha (avada modal). Vanem ise valib, mida ta selle infoga peale hakkab, kutsudes välja oma meetodi `handleOpenLocationInfoModal`.

### Päriselu analoogia

See on nagu uksekell — kui keegi vajutab uksekella, saadab see helina "keegi on ukse taga", mitte käsku "ava uks". Maja omanik (parent) otsustab ise, kas ta läheb ust avama, ignoreerib helinat või teeb midagi muud.

## Meetodi nimetamine ausalt – handleOpenLocationInfoModal — `0:55:49` {#meetodi-nimetamine}

Vanemkomponendis tuleb luua meetod, mis käivitub asukoha nime klõpsamisel.

### Selgitus

Õpetaja arutleb pikalt nime valiku üle. Esialgne mõte oli `openLocationInfoModal()`, aga see nimi **valetaks** — meetod ei tee ainult modali avamist, vaid ka andmete päringut serverist. Kuna meetod teeb "natuke rohkem" kui nimi lubaks, valitakse hägusem, aga ausam nimi: `handleOpenLocationInfoModal` — eesliide `handle` annab mõista, et midagi käsitletakse/töödeldakse, ilma et lubataks täpselt, mis kõik seal sees toimub.

### Praktiline reegel

> Kui meetodi nimi ütleb "tee X", aga meetod tegelikult teeb X-i **ja** midagi muud lisaks (nt andmepäring, kontroll, mitu sammu), on nimi eksitav. Kasuta üldisemat sõna (`handle...`) või jagunda meetod mitmeks väiksemaks osaks.

### Koodinäide

```js
handleOpenLocationInfoModal(locationId) {
  LocationService.getAtmLocationRequest(locationId)
    .then(response => this.handleGetLocationResponse(response))
    .catch()
},

handleGetLocationResponse(response) {
  this.location = response.data
  this.locationInfoModalIsOpen = true
}
```

Meetod `handleOpenLocationInfoModal` saab argumendiks `locationId` (see tuli event'i "pakikesena" kaasa lapselt), pärib andmed serverist ja alles siis, kui vastus käes, avab modali.

## Uue teenuse kirjutamine üksiku andmestiku pärimiseks — `1:03:00` {#uus-teenus}

Andmete kuvamiseks on vaja backend'ist tuua ühe konkreetse asukoha täisandmed (mitte kõigi asukohtade nimekiri, mis on juba `getAtmLocationsRequest` meetodiga olemas).

### Selgitus

Videos uuritakse API kontrakti ("piibel" — Stoplight/Swagger dokumentatsioon), et leida, milline endpoint tagastab ühe konkreetse asukoha andmed. Tähtis tähelepanek: kuigi API kontraktis on ressursi nimi mitmuses (`/atm/locations`), on **ühe konkreetse ressursi** URL loogiline hoida samuti struktureeritult — `GET /atm/locations/{locationId}` tagastab täpselt ühe objekti, mitte massiivi.

### Koodinäide

Reaalne `LocationService.js` fail koodibaasist:

```js
export default {
  postAtmLocationRequest(location) {
    return axios.post('/api/atm/locations', location)
  },

  getAtmLocationRequest(locationId) {
    return axios.get(`/api/atm/locations/${locationId}`)
  },

  getAtmLocationsRequest(cityId) {
    // ... olemasolev meetod kõigi asukohtade toomiseks
  },
}
```

Pane tähele nimekonventsiooni: `getAtmLocationRequest` (ainsus, toob ühe) versus `getAtmLocationsRequest` (mitmus, toob kõik). See erinevus üheski tähes peegeldab täpselt API käitumise erinevust.

### Miks mitte nimetada mõlemat samamoodi?

JavaScript ei toeta **meetodi signatuuri ülekoormamist** (method overloading) — erinevalt Java'st ei saa samas failis olla kaks meetodit sama nimega, mis erinevad ainult parameetrite poolest. Seega peavad erineva käitumisega meetodid saama kindlasti erinevad nimed.

## Template literal (backtick) süntaks dünaamilise URL-i jaoks — `1:13:36` {#template-literal}

Vaja on koostada URL, kuhu keskele tuleb muutuja väärtus (`locationId`).

### Selgitus

JavaScript pakub **template literal** (mall-string) süntaksit, mis kasutab tavaliste jutumärkide (`'` või `"`) asemel **backtick** märki (`` ` ``, tavaliselt klaviatuuril tildeklahvi juures). Selle sees saab muutuja väärtuse sisestada otse teksti sisse, kasutades `${muutujaNimi}` süntaksit — ilma et peaks stringe `+` märgiga kokku liitma.

### Skeem

```
Tavaline stringide liitmine:
'/api/atm/locations/' + locationId

Template literal (loetavam):
`/api/atm/locations/${locationId}`
```

### Koodinäide

```js
getAtmLocationRequest(locationId) {
  return axios.get(`/api/atm/locations/${locationId}`)
},
```

Kui `locationId` väärtus on näiteks `12`, saadab see päringu aadressile `/api/atm/locations/12` — täpselt nii, nagu backend REST API seda ootab (ID on osa URL-i teekonnast, mitte eraldi query-parameeter).

### Päriselu analoogia

See on nagu täidetav lünkadega tekst ("Tere, [NIMI]! Sinu tellimuse number on [NUMBER]") — backtick-stiil lubab lünki otse teksti sisse kirjutada, selle asemel et tükke käsitsi kokku liimida.

## Andmete "voolamine" alla läbi komponentide — `1:31:11` {#andmete-voolamine}

Kui andmed on serverist kätte saadud, tuleb need viia sinna, kus neid tegelikult kuvatakse — kolm taset allapoole.

### Selgitus

Õpetaja kordab metafoori "voolamisest": iga tasand komponentide puus peab andmed **teadlikult vastu võtma propsina** ja **teadlikult edasi andma** järgmisele tasandile. Ükski komponent ei saa "vahele jätta" — kui `AtmsView`-l on andmed, aga `LocationInfoModal` ei võta neid oma props'ina vastu, jäävad andmed "kinni" ülemisel tasandil ja ei jõua kunagi sinna, kus neid kuvada tahetakse.

### Skeem

```
AtmsView                    location = { locationName: "Kesklinn", ... }
   │  :location="location"
   ▼
LocationInfoModal            props: { location: Object }
   │  {{ location.locationName }}
   │  :image-data="location.imageData"
   ▼
AtmImage                     props: { imageData: String }
```

### Koodinäide

Iga sammu juures peab olema selgelt defineeritud prop:

```js
// LocationInfoModal.vue
props: {
  locationInfoModalIsOpen: Boolean,
  location: Object,
},
```

```vue
<!-- LocationInfoModal.vue template -->
<AtmImage :image-data="location.imageData" />
```

```js
// AtmImage.vue
props: {
  imageData: String,
},
```

### Miks anda `AtmImage`-le ainult `imageData`, mitte kogu `location` objekti?

Õpetaja rõhutab olulist disainiotsust: `AtmImage` komponent ei peaks teadma kogu `location` objekti struktuurist — talle antakse kaasa **ainult see osa, mida ta tegelikult vajab** (`imageData` string). See teeb komponendi taaskasutatavaks ka olukorras, kus pilti kunagi soovitakse kuvada mõne teise objekti (mitte `location`) andmete põhjal — komponent ise ei ole "lukustatud" konkreetsesse andmestruktuuri.

## AI-abiga refaktoreerimine ja sellega kaasnevad riskid — `1:53:09` {#ai-refaktoreerimine}

Kui otsustati muuta propsi nimi `location` asemel täpsemaks `imageData`, kasutati selleks AI-assistendi (Claude Code) refaktoreerimisvõimet.

### Selgitus

AI-l paluti muuta muutuja nimi kõikjal projektis, kus seda kasutatakse — nn "rename" refaktoreerimine. AI leidis ja muutis kolm kohta, kus muutujat kasutati. See töötas enamasti korrektselt, aga videos näidatakse ka reaalset tagajärge: **AI jättis ühe koha muutmata**, mis põhjustas hiljem jooksuaegse vea (`LocationView` läks katki, kuna seal viidati endiselt vanale, enam mitteeksisteerivale väljale).

### Praktiline õppetund

> **Refaktoreerimist tehes — olgu see käsitsi või AI abiga — kontrolli ALATI läbi kõik kohad, kus muudetud kood tegelikult kasutusel on**, mitte ainult see üks fail, kus muudatust algselt tegema hakkasid. AI-l on kalduvus jätta mõni koht märkamata, eriti kui projekt on suur või seosed ei ole failide vahel ilmselged.

### Veaotsingu käik (debug protsess)

Videos näidatakse tüüpilist veaotsingut:

1. Brauseri konsoolis (Developer Tools) nähakse veateadet koos failinime ja reanumbriga.
2. Minnakse vaatama seda konkreetset kohta koodis.
3. Leitakse, et seal viidatakse muutujale, mida enam ei eksisteeri (nimi oli refaktoreeritud, aga see üks koht jäi vahele).
4. Parandatakse käsitsi.

## Komponendi taaskasutus lisa-propsiga (switchesDisabled) — `2:10:35` {#komponendi-taaskasutus}

`TransactionTypesCheckbox` komponent oli algselt loodud `LocationView`-s kasutamiseks, kus kasutaja **saab** linnukesi muuta (uue asukoha lisamise vormis). Nüüd on vaja sama komponenti kasutada `LocationInfoModal`-is, kus linnukesed peavad olema **ainult vaadatavad**, mitte muudetavad.

### Selgitus

Selle asemel, et luua täiesti uus, peaaegu identne komponent, lisatakse olemasolevale komponendile uus, valikuline prop `switchesDisabled` koos vaikeväärtusega, mis säilitab olemasoleva käitumise muutumatuna (vaikimisi väärtus on `false`, ehk vanad kasutuskohad jätkavad tööd täpselt samamoodi nagu enne).

### Koodinäide

Reaalne `TransactionTypesCheckbox.vue`:

```vue
<script>
export default {
  name: 'TransactionTypesCheckbox',
  props: {
    transactionTypes: Array,
    switchesDisabled: {
      type: Boolean,
      default: false
    }
  },
  // ...
}
</script>

<template>
  <input
    class="form-check-input"
    type="checkbox"
    role="switch"
    :disabled="switchesDisabled"
    :checked="transactionType.isAvailable"
  />
</template>
```

Kasutus kahes erinevas kontekstis:

```vue
<!-- LocationView.vue — kasutaja SAAB muuta -->
<TransactionTypesCheckbox :transaction-types="location.transactionTypes" ... />

<!-- LocationInfoModal.vue — kasutaja EI SAA muuta -->
<TransactionTypesCheckbox
  :transaction-types="location.transactionTypes"
  :switches-disabled="true"
/>
```

### Miks vaikeväärtus `false`, mitte `true`?

See on tahtlik otsus: kuna komponenti kasutati juba varem ilma seda propsit üldse andmata, peab **vaikeväärtus säilitama vana käitumise**. Kui vaikeväärtuseks oleks pandud `true`, oleks kõik olemasolevad kasutuskohad (nt `LocationView`) äkitselt "katki läinud" — linnukesed poleks enam muudetavad, kuigi see polnud plaanis.

## Event emit ahel mitme taseme kaudu ("düsfunktsionaalne perekond") — `2:28:37` {#event-emit-ahel}

Modali sulgemisnupp asub kõige sügavamal komponendil (`BaseModal`). Kui kasutaja klõpsab sellel, peab sõnum jõudma kõige ülemise taseme (`AtmsView`) muutujani, mis kontrollib modali nähtavust.

### Selgitus

Õpetaja kasutab humoorikat analoogiat: see on nagu **düsfunktsionaalne perekond**, kus lapselaps (`BaseModal`) ei räägi otse vanavanemaga (`AtmsView`) — kõik peab käima läbi keskmise põlvkonna, vanema (`LocationInfoModal`). Iga tasand peab teadlikult "edasi kuulama" ja "edasi saatma" sõnumit, muidu jääb see teel kinni.

### Skeem

```
BaseModal (Grandchild)
   │ emit 'event-modal-closed'
   ▼
LocationInfoModal (Child)
   │  @event-modal-closed="$emit('event-location-info-modal-closed')"
   │  (kuulab Grandchild'i sõnumit, saadab OMA sõnumi edasi)
   ▼
AtmsView (Parent)
   │  @event-location-info-modal-closed="locationInfoModalIsOpen = false"
   │  (alles siin tegelikult MUUDETAKSE state'i)
```

### Koodinäide

Kogu ahel kolmes failis:

```vue
<!-- BaseModal.vue: saadab neutraalse sündmuse üles -->
<button type="button" class="btn-close" @click="close" />
```
```js
methods: {
  close() {
    this.$emit('event-modal-closed')
  },
}
```

```vue
<!-- LocationInfoModal.vue: kuulab, saadab spetsiifilisema sündmuse edasi -->
<BaseModal
  :is-open="locationInfoModalIsOpen"
  @event-modal-closed="$emit('event-location-info-modal-closed')"
>
```

```vue
<!-- AtmsView.vue: kuulab, MUUDAB olekut -->
<LocationInfoModal
  :location-info-modal-is-open="locationInfoModalIsOpen"
  @event-location-info-modal-closed="locationInfoModalIsOpen = false"
/>
```

### Miks mitte lasta modalil ennast ise sulgeda?

Kuna kogu nähtavuse kontroll (`locationInfoModalIsOpen`) elab tipptasandi komponendis `AtmsView`, **ei saagi** ükski alamkomponent seda muutujat otse muuta — see kuulub vanemale. Iga tasand saab ainult "teatada", et midagi juhtus (nupule klõpsati), ja lasta vanemal enda otsustada, mida sellega peale hakata. See on veidi keerulisem kui otsene manipuleerimine, aga annab palju paremat kontrolli ja paindlikkust — sama sündmuseahel toimib olenemata sellest, mitu erinevat vanemkomponenti soovivad tulevikus `LocationInfoModal`-it kasutada.

### Päriselu analoogia

Kujuta ette kontoriruumi, kus töötaja (grandchild) ei saa otse teavitada tegevjuhti (parent) — ta peab kõigepealt teavitama oma otsest ülemust (child), kes omakorda otsustab, kas ja kuidas seda infot tegevjuhile edastada. See tundub esmapilgul aeglasem, aga annab igale tasandile kontrolli selle üle, mida ja kuidas edasi antakse.
