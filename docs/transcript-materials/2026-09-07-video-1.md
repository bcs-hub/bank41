## Kordamine: Slotid Vue komponentides — `0:00:02` {#kordamine-slotid-vue-komponentides}

Tund alustab kordamisega — enne uue teema juurde minemist tuletatakse meelde, mida `slot` (pesa) Vue komponendis annab.

### Selgitus

Kui komponendil on `slot`, saab sellele komponendile **väljastpoolt sisu ette anda**, mitte kirjutada sisu igal kasutuskorral uuesti. Komponent ise defineerib ainult "koha", kuhu sisu tuleb — ja selle koha täidab see, kes komponenti kasutab.

Näiteks projektis olev modaalkomponent (`BaseModal.vue`) on ehitatud kolme pesaga: `title`, `body` ja `buttons`. Modaali visuaal (kastikene, ristike sulgemiseks, tagafoon) on tehtud üks kord, aga sisu on iga kasutuskorra puhul erinev.

### Skeem

```
BaseModal.vue (universaalne raam)
┌─────────────────────────────┐
│ [slot: title]           [X] │  ← pealkiri tuleb väljastpoolt
├─────────────────────────────┤
│ [slot: body]                │  ← sisu tuleb väljastpoolt
├─────────────────────────────┤
│ [slot: buttons]     [Sulge] │  ← nupud tulevad väljastpoolt
└─────────────────────────────┘
```

### Koodinäide (`frontend/src/components/modal/BaseModal.vue`)

```vue
<template>
  <div v-if="isOpen">
    <div class="modal-content">
      <div class="modal-header">
        <h5 class="modal-title">
          <slot name="title"></slot>
        </h5>
        <button type="button" class="btn-close" @click="close" />
      </div>
      <div class="modal-body">
        <slot name="body"></slot>
      </div>
      <div class="modal-footer">
        <slot name="buttons"></slot>
        <button type="button" class="btn btn-secondary" @click="close">Sulge</button>
      </div>
    </div>
  </div>
</template>
```

Kasutaja, kes seda modaali rakendab, kirjutab sisse ainult see, mis on tema jaoks eriline (pealkiri, sisu, nupud) — kogu ülejäänud disain ja käitumine (avamine, sulgemine, tagafoon) on juba paigas.

### Päriselu analoogia

Slot on nagu piparkoogivorm: vorm (komponent) on kõigil ühesugune, aga glasuur ja kaunistused (sisu) võivad iga piparkoogi puhul erinevad olla.

## Monorepo, mikroteenused ja monoliit — `0:07:24` {#monorepo-mikroteenused-ja-monoliit}

### Selgitus

Selles projektis (`bank41`) on **backend ja frontend samas repos** (kaustade kaupa lahutatud) — seda kutsutakse **monorepoks**. See ei ole traditsiooniline lähenemine päris süsteemides, kus backend ja frontend on tavaliselt eraldi repod, aga väikeste/õpi-/hobiprojektide jaoks on see väga mugav, sest:

- AI abivahenditel (nagu Claude Code) on korraga ligipääs mõlemale poolele, mis annab rohkem konteksti.
- Alustamine on lihtsam — ei pea kohe haldama kahte eraldi repot.

Kuna backend ja frontend selles projektis **ei viita koodi tasandil teineteisele** (ei ole importe üle piiri), on need repod hiljem väga lihtsasti lahutatavad, kui projekt kasvab.

### Monoliit vs mikroteenused

- **Monoliit** — kõik funktsionaalsus on ühes suures rakenduses/programmis.
- **Mikroteenused** — süsteem on tükeldatud väikesteks, iseseisvateks teenusteks, mis igaüks tegeleb ühe kitsa vastutusalaga.

Süsteemid tihtipeale **alustavad monoliidina** ja kasvavad aja jooksul nii suureks/keerukaks, et neid hakatakse lõhkuma väiksemateks teenusteks.

### Päriselu näide: LHV pank

Õpetaja tõi näite oma varasemast töökohast: LHV internetipangas oli algselt maksete süsteem sama rakenduse sees, mis internetipank ise. Aja jooksul saadi aru, et see on ebamõistlik — erinevad kliendid ja süsteemid (nt teised pangad, kes tahavad LHV-t "toruna" kasutada) tahtsid maksete funktsionaalsust kasutada **ilma internetipanga rakenduseta**. Selle tulemusel kirjutati maksete süsteem internetipangast eraldi teenuseks välja — see oli suur ja kulukas projekt, aga pikemas plaanis mõistlik.

### Oluline põhimõte

> Tarkvara ei saagi kunagi "täiesti valmis" — infosüsteemid kasvavad ja muutuvad aja jooksul pidevalt, kuna uued vajadused tekivad.

### Soovitus oma projektide jaoks

Kui teete oma hobiprojekti, kus on frontend ja backend, alustage nendega **samas repos** (monorepona). Kui/kui projekt kunagi kasvab piisavalt suureks, on lihtne need hiljem eraldi repodeks lahutada — täpselt seetõttu, et koodi tasandil ei viita nad teineteisele.

## Java projekti struktuur ja pakid — `0:17:38` {#java-projekti-struktuur-ja-pakid}

### Selgitus

Java projektis asub kogu lähtekood kataloogis `src/main/java`. Kõik, mis on väljaspool seda struktuuri (nt `build`, `out` kaustad), on genereeritud fail — ei ole osa käsitsi kirjutatud lähtekoodist.

Kirjutatud kood **kompileeritakse** — muudetakse paitkoodiks (bytecode), mida arvuti reaalselt käivitab (kaheksa "nulli-ühte" korraga = 1 bait).

### Package (pakk) = aadress

Iga Java klass kuulub mingisse **package'i** (pakk), mis on kirjas faili tipus:

```java
package ee.bcs.bank;
```

Package on nagu tagurpidi veebilehe aadress (`ee.bcs.bank` ~ `bank.bcs.ee`). See annab klassile unikaalse "aadressi" — kaks eri paki klassi võivad kandma sama nime, kuna nende täisaadress on erinev.

### Skeem

```
src/main/java/
└── ee/
    └── bcs/
        └── bank/
            └── BankApplication.java   ← package ee.bcs.bank;
```

### Oluline IntelliJ seadistus

Kui projekti kaustapuu näitab kaustasid `e`, `bcs`, `bank` eraldi üksteise all (mitte kokku liidetuna `ee.bcs.bank`-iks), on midagi valesti seadistatud — IntelliJ peaks samanimelised üksikkaustad automaatselt kokku "voltima" ühele reale.

### Kaks samanimelist klassi

Kui projektis on kaks klassi samas nimega, aga eri package'ites, ei teki probleemi — IDE küsib tab'i vajutades, kumba silmas peetakse (kuna nende täisaadress erineb). Sama nimega klass **samas** package'is ei ole aga lubatud — kompilaator ei tea, kumbale viidata.

### Päriselu analoogia

Package on nagu tänavaaadress — samamoodi nagu "Tallinn, Narva mnt 5" ja "Tartu, Narva mnt 5" saavad mõlemad olemas olla samaaegselt, kuna linn (package) teeb nad eristatavaks.

## Main meetod — programmi sisenemispunkt — `0:26:16` {#main-meetod}

### Selgitus

Igas Java rakenduses on **täpselt üks** `main` meetod — koht, kust kogu programmi käivitamine algab. See on koodilõik, mida on võimalik käivitada väljaspoolt koodifaile (nt käsurealt).

```java
public static void main(String[] args) {
    SpringApplication.run(ee.bcs.bank.BankApplication.class, args);
}
```

(`backend/src/main/java/ee/bcs/bank/BankApplication.java`)

Kuigi meetodeid tohib programmis olla lõpmatult palju, on ainult **üks** neist selline, mis kogu programmi käima lükkab.

### Kaks tüüpi programme

- **Tavaline programm** (nt lihtne `System.out.println` skript) — jookseb ülevalt alla ja lõpetab. Konsoolis kuvatakse `Process finished with exit code 0`.
- **Veebiserver** (Spring Boot rakendus) — käivitub, aga **jääb elama** ega jõua "lõppu", kuna ta ootab pidevalt sissetulevaid päringuid.

### Päriselu analoogia

`main` meetod on nagu maja peauks — igasse majja saab siseneda ainult ühte konkreetsest ukse kaudu, kuigi majas võib olla palju tube (meetodeid).

## Debugimine ja sõna "bug" ajalugu — `0:32:37` {#debugimine-ja-sona-bug-ajalugu}

### Selgitus

IntelliJ IDEA võimaldab käivitada koodi **Debug-režiimis**. See tähendab, et koodi täitmise saab peatada konkreetsel real (**breakpoint**, murdepunkt) ja liikuda sealt edasi rida-realt (nt klahviga `F8`), jälgides muutujate väärtusi reaalajas.

```
Kood käivitub → jõuab breakpointini → jääb seisma
   → vajutad F8 → liigub üks rida edasi → saad vaadata muutujate seisu
```

**Millal debugimist kasutada?**
- Kui kood **ei kompileeru** — kasutatakse tavaliselt kompilaatori veateadet, mitte debuggerit.
- Kui kood **käivitub, aga annab vale/imeliku tulemuse** — siis on debugger asendamatu, et samm-sammult leida, kus loogika läheb valeks.

### Ajalooline anekdoot: kust tuli sõna "bug"?

Õpetaja jutustas legendaarse loo (seotud arvutiteaduse ajaloos tuntud teadlase nimega, kelle täisnime ta kohe meelde ei tuletanud) — vanaaegsetes tohutu suurtes arvutites (kogu ruumi täitvates masinates) tekkis kord vale tulemus. Uuriti masinat lahti võtmata seni, kuni leiti füüsiline **putukas**, kes oli takerdunud kahe kondensaatori vahele ja tekitas lühise. Kui putukas eemaldati, hakkas masin korrektselt tööle.

Sellest ajast on levinud termin **bug** (putukas) tähistama tarkvaravigu, ja **debugging** (putukatõrje) tähistama vea otsimise/parandamise protsessi.

## build.gradle ja sõltuvused — `0:38:53` {#build-gradle-ja-soltuvused}

### Selgitus

Backend-projektis vastutab kogu ehitusprotsessi (build) haldamise eest **Gradle** (sümboliks elevant). See on analoogne frontendi `package.json`-iga.

| Frontend (`package.json`) | Backend (`build.gradle`) |
|---|---|
| kirjeldab, milliseid npm pakette vajatakse | kirjeldab, milliseid Java teeke (library) vajatakse |
| `scripts` (nt `dev`, `build`) | Gradle taskid (nt `bootRun`, `build`) |
| npm on package manager | Gradle on build tool + dependency manager |

### Koodinäide (`backend/build.gradle`)

```groovy
dependencies {
    // Spring Boot
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // Swagger
    implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:3.0.3'

    // Lombok
    compileOnly 'org.projectlombok:lombok'

    // PostgreSQL
    runtimeOnly 'org.postgresql:postgresql'

    // MapStruct
    implementation 'org.mapstruct:mapstruct:1.6.3'
}
```

Kui lisad `spring-boot-starter-web` sõltuvuse, muutub tavaline Java-programm **veebiserveriks** — see on põhjus, miks Spring Boot rakendus jääb pärast käivitamist "elama" (ootab HTTP päringuid), erinevalt lihtsast programmist, mis jookseb läbi ja lõpetab.

### Transitiivsed sõltuvused ("tõmba veel asju alla")

Igal sõltuvusel (dependency) võib omakorda olla **oma sõltuvused**. Kui lisad projektile ühe teegi, tõmmatakse automaatselt alla ka kõik, mida see teek ise vajab — see ahel võib minna mitu tasandit sügavusse. Sellest tekivad tänapäeva "probleemid": suured node_modules/kaustad, versioonikonfliktid (kaks teeki tahavad sama sõltuvuse erinevaid versioone) ja turvarisk (usaldad palju koodi, mida ise ei kirjutanud).

### Miks kasutada teeke (library) ise kirjutamise asemel?

Näide: telefoninumbri valideerimine. Selle enda kirjutamine (kõikide riikide reeglite tundmine) oleks tohutu töö. Google on selle ise juba ära lahendanud ja pakub valmis teeki, mille lihtsalt lisad projekti — paar rida koodi asemel tohutust arendustööst.

### LHV kogemus: teekide usaldamine

Reaalses töökeskkonnas (LHV) ei olnud jäika reeglistikku uute teekide kasutuselevõtuks, aga oli tava hinnata teegi usaldusväärsust: kui palju kasutajaid tal on, kui kaua on ta "elus" olnud, kas seda on loonud tuntud organisatsioon või üksik hobiarendaja. See on riskihindamine — võõra koodi projekti lisamine on potentsiaalne turvarisk.

## Maven vs Gradle — `0:50:26` {#maven-vs-gradle}

### Selgitus

**Maven** oli varasem, laialdaselt kasutatud Java build tool, mis kirjeldas sõltuvusi **XML** vormingus. **Gradle** on hilisem ja tänapäeval populaarsem alternatiiv, mis kasutab palju lühemat ja loetavamat süntaksit (Groovy/Kotlin DSL).

### Näide erinevusest

Maven (XML):
```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

Gradle:
```groovy
implementation 'org.springframework.boot:spring-boot-starter-web'
```

Õpetaja mainis, et alguse ajal, kui pidi Maveniga toimetama, oli see palju tüütum XML-i verboosuse tõttu.

### Sõltuvuste kesksed hoidlad

Sõltuvused (teegid) laetakse alla kesksetest hoidlatest (repositoriumitest), kuhu on koondatud enamik avaliku Java ökosüsteemi teeke. Selliseid hoidlaid haldavatel organisatsioonidel on kulu (serverid, ribalaius) — hetkel on levinud arutelu selle üle, et AI-agendid tarbivad üha rohkem selliste hoidlate ressursse, ilma et sellest tuluks organisatsioonile midagi laekuks.

## @SpringBootApplication — kontroll läheb raamistikule — `0:54:59` {#springbootapplication}

### Selgitus

`@SpringBootApplication` on **annotatsioon** (Java's kirjutatakse `@`-märgiga), mis muudab tavalise Java klassi Spring Boot rakenduse keskseks klassiks. See annab kompilaatorile/raamistikule märku, et see klass peab saama spetsiaalse käitluse (Spring haldab teda kui "beani" oma konteineris).

### Koodinäide (`backend/src/main/java/ee/bcs/bank/BankApplication.java`)

```java
package ee.bcs.bank;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class BankApplication {

	public static void main(String[] args) {
		SpringApplication.run(ee.bcs.bank.BankApplication.class, args);
	}

}
```

### Kontrolli üleandmine (Inversion of Control)

Tavaliselt käivitab `main` meetod otse tavalist koodi. Siin toimub aga huvitav asi: `main` meetod käivitab `SpringApplication.run(...)`, viidates **iseendale** (`BankApplication.class`). Sellega antakse kontroll üle Spring raamistikule — edasi ei jooksuta programmi enam lihtsalt "ülevalt alla", vaid **Spring otsustab**, mis ja millal käivitub.

```
Java käivitab kompilaatori loodud koodi
   → käivitab Spring Boot rakenduse
      → Spring võtab kontrolli üle
         → Spring käivitab meie äriloogika (Library'de ja meie koodi abil)
```

See on sama põhimõte, mis Vue's — raamistik (framework) teeb palju "maagiat" taustal (template'id, reaktiivsus), et arendaja saaks kirjutada vähem koodi ja keskenduda äriloogikale.

### Päriselu analoogia

Erinevad programmeerimiskeeled/platvormid (C#, Python, PHP) omavad kõik oma raamistikke, mis teevad igapäevase arenduse mugavamaks — see ei ole Java'le unikaalne nähtus.

## Objektorienteeritud programmeerimine: objektid ja klassid — `1:05:03` {#objektorienteeritud-programmeerimine}

### Selgitus

Java on **objektorienteeritud keel** — kogu programmi tegevus keerleb **objektide** ümber. Objektil võib sees olla:
- **andmed** (väljad/fields), või
- **tegevused** (meetodid).

### Klass = mall (blueprint)

**Klass** on mall, millest objektid luuakse. Sama klassi (malli) järgi loodud objektid võivad omada erinevaid konkreetseid väärtusi.

```java
public class Student {
    public String firstName;
    public String lastName;
    public int age;
}
```

Selline klass ütleb: "iga Student objekt hoiab endas eesnime, perekonnanime ja vanust" — aga ei määra konkreetseid väärtusi.

### Skeem

```
class Student (mall/blueprint)
┌────────────────────┐
│ firstName: String  │
│ lastName:  String  │
│ age:       int     │
└────────────────────┘
        │
        │ new Student()
        ▼
Konkreetne objekt (mälus)
┌────────────────────┐
│ firstName: null     │
│ lastName:  null     │
│ age:       0        │
└────────────────────┘
```

### Päriselu analoogia

Klass on nagu piparkoogivorm — kõik sama vormiga tehtud piparkoogid on kujult ühesugused (viisnurksed), aga glasuur ja kaunistused (väärtused) võivad iga tüki puhul erinevad olla.

## Primitiivsed väärtused vs objektid — `1:08:12` {#primitiivsed-vaartused-vs-objektid}

### Selgitus

Java's on kaks väärtuste kategooriat:

- **Primitiivid** (nt `int`, `char`, `boolean`) — need on "puhtad" väärtused, mitte objektid. Kui väärtust ei anta, on nende vaikeväärtus **null-väärtus samas tüübis** (nt `int` puhul `0`).
- **Objektid** (nt `String`, `Integer`, `Student`) — need on tegelikud objektid mälus. Kui väärtust ei anta, on nende vaikeväärtus **`null`** (täielik puudumine, "mitte midagi").

```java
int a;        // vaikeväärtus 0 (primitiiv)
Integer b;    // vaikeväärtus null (objekt/wrapper class)
```

### Objektide võrdlemine (`==` vs `.equals()`)

Üks kõige tähtsamaid algajate lõkse: objekte **ei tohi** võrrelda `==` operaatoriga, kuna see võrdleb **mäluviiteid**, mitte sisu.

```java
Integer x = 10;
Integer y = 10;
System.out.println(x == y); // Ei ole garanteeritult true — võrdleb mäluviiteid!
```

Kui kaks silti (muutujat) viitavad kahele **eri** objektile mälus (isegi kui sisu on identne), annab `==` `false`. Kui aga üks silt on omistatud teisele (`y = x`), viitavad mõlemad **samale** objektile, ja `==` annab `true`.

### Skeem: mäluviited

```
int x = 10;        int y = 10;
   x ──► [10]          y ──► [10]     (kaks erinevat mälukohta!)

Integer x2 = 10;    Integer y2 = x2;
   x2 ──► [obj: 10]  ◄── y2            (üks ja sama objekt!)
```

### Reegel

> Objekte võrreldakse sisu järgi meetodiga `.equals()`, mitte `==`-ga. `==` on õige ainult primitiivide (`int`, `char` jms) võrdlemiseks.

## Objektide loomine võtmesõnaga `new` — `1:16:32` {#objektide-loomine-votmesonaga-new}

### Selgitus

Uue objekti loomiseks kasutatakse võtmesõna **`new`**, millele järgneb klassi nimi:

```java
Student student = new Student();
```

See koodirida koosneb kolmest osast:

```
Student   student   =   new Student();
  ▲          ▲                ▲
 tüüp     silt/nimi      objekti loomine (konstruktori kutse)
```

- **Tüüp** (`Student`) — ütleb, millist "malli" objekt peab järgima.
- **Silt** (`student`) — muutuja nimi, mille kaudu objektile hiljem viidata.
- **`new Student()`** — käivitab konstruktori, mis objekti tegelikult tekitab mälus.

### Silt vs objekt

See on kriitiline vahetegemine: **silt (variable) ja objekt on kaks eri asja**. Objektiga on võimalik suhelda **ainult sildi kaudu** — kui objektil ei ole silti (nimeviidet), ei ole sellega enam võimalik midagi teha (see läheb "prügikasti").

### Kompilaatori tüübikontroll

Java on tüübikindel keel — kompilaator kontrollib, et sildile omistatakse õiget tüüpi väärtus:

```java
String streetName = 5; // VIGA! Kompilaator ei luba Int'i String'i muutujasse panna
```

### Muutuja skoop (eluiga)

Silt "elab ja sureb" selles koodiplokis (`{ }`), kus ta on defineeritud. Väljaspool sellist plokki ei ole sildile enam ligipääsu — isegi kui objekt ise (mälus) võib mõnel juhul veel eksisteerida.

```java
if (true) {
    Student student = new Student(); // silt "student" sünnib siin
} // silt "student" sureb siin — enam ei ole ligipääsu
```

### Päriselu analoogia

Silt on nagu inimese nimi — kui unustad kellegi nime, ei tähenda see, et inimene kaob, aga sul ei ole enam mugavat viisi temaga suhelda ("kuule, sina!" asemel "Jaroslav!").

## Konstruktor — `1:36:41` {#konstruktor}

### Selgitus

**Konstruktor** on eriline meetod, mis käivitub automaatselt, kui kirjutad `new KlassiNimi()`. Selle ülesanne on objekti luua ja (soovi korral) algväärtustada.

```java
public class Student {
    public String firstName;

    public Student() {
        // see koodilõik käivitub iga new Student() peale
    }
}
```

### Default (vaikimisi) konstruktor

Kui klassis **ei kirjuta** ühtegi konstruktorit ise, loob **kompilaator** automaatselt tühja, argumentideta konstruktori. Kohe kui kirjutad **ühegi** konstruktori käsitsi, kaob see automaatne vaikekonstruktor ära — sind ootavad nüüd ainult need konstruktorid, mis on sinu enda poolt defineeritud.

### Skeem

```
Kirjutamata konstruktor          Käsitsi kirjutatud konstruktor
        │                                    │
        ▼                                    ▼
Kompilaator loob automaatselt      Vaikekonstruktor KADUB
tühja konstruktori taustal         (kasutada saab vaid seda,
                                    mille sa ise kirjutasid)
```

### Päriselu analoogia

Konstruktor on nagu tehase liinil masin, mis toote (objekti) kokku monteerib — enne seda masinat pole toodet olemas, ja masina väljundiks on alati "toores" (algväärtustega) toode, kui te ise ei ütle masinale, milliste omadustega toode tuleb kokku panna.

## This ja konstruktori parameetrid — `1:57:20` {#this-ja-konstruktori-parameetrid}

### Selgitus

Kui konstruktoris on parameeter ja klassiväli **sama nimega**, on kompilaator segaduses — kumba silmas peetakse? Selle lahendamiseks kasutatakse võtmesõna **`this`**, mis viitab käesolevale objektile.

```java
public class Student {
    public String firstName;

    public Student(String firstName) {
        this.firstName = firstName; // vasak pool: objekti väli. Parem pool: parameeter
    }
}
```

### Skeem

```
new Student("Rain")
        │
        ▼
Student(String firstName)   ← parameeter "firstName" = "Rain"
        │
        ▼
this.firstName = firstName; ← objekti väli "firstName" saab väärtuse "Rain"
```

`this.firstName` viitab **objekti väljale**, samal ajal kui parameetrina saadud `firstName` on ajutine, ainult konstruktori sees elav muutuja.

### Kasutuskoht

```java
Student student = new Student("Rain");
// Nüüd: student.firstName sisemiselt hoiab väärtust "Rain"
```

## Parameeter vs argument — `2:03:20` {#parameeter-vs-argument}

### Selgitus

Need kaks terminit ajavad segamini, aga vahe on lihtne:

- **Parameeter** — see, mida meetodi/konstruktori **definitsioonis** oodatakse.
- **Argument** — see, mida meetodi/konstruktori **väljakutsumisel** tegelikult sisse antakse.

```java
// Definitsioon — "firstName" on PARAMEETER
public Student(String firstName) {
    this.firstName = firstName;
}

// Väljakutse — "Rain" on ARGUMENT
Student student = new Student("Rain");
```

### Päriselu analoogia

Kui restoranis on menüüs kirjas "Valik: liha VÕI kala" (see on parameeter — koht, kuhu valik käib), ja te tellite "kala" (see on argument — konkreetne valik, mis te andsite), siis parameeter kirjeldab "pesa", argument on see, mis sinna pessa tegelikult pannakse.

Igapäevases kõnepruugis on lubatud öelda "annan parameetriks kaasa" — see ei ole tehniliselt 100% täpne, aga klassiruumis piisavalt selge.

## Private väljad ja get-meetodid — `2:06:21` {#private-valjad-ja-get-meetodid}

### Selgitus

Java's on objekti väljad (fields) **vaikimisi privaatsed** (`private`) — see tähendab, et neile ei saa **väljaspoolt klassi** otse ligi (`student.firstName` ei tööta, kui väli on `private`).

```java
public class Student {
    private String firstName; // väljaspoolt ei ole ligipääsu

    public Student(String firstName) {
        this.firstName = firstName;
    }

    public String getFirstName() { // AVALIK meetod, mis annab kontrollitud ligipääsu
        return this.firstName;
    }
}
```

### Miks peita väljad?

Klassi sees (samas failis) on kõikidele väljadele ikka ligipääs — piirang kehtib **väljaspoolt vaadatuna**. Väljade peitmine ja avalike get-meetodite kaudu ligipääsu pakkumine on levinud tava (kontrollitud "uks" andmete juurde, mitte otsetee).

### Meetodi struktuur

```
nähtavus   tagastustüüp   nimi          parameetrid
  ▼            ▼           ▼                ▼
public       String    getFirstName    ()
{
    return this.firstName;   // peab tagastama täpselt seda tüüpi, mis on deklareeritud
}
```

Iga meetod peab deklareerima, kas ta tagastab midagi (nt `String`, `int`, `Student`) või mitte midagi (`void`).

### Konventsioon: pane tulemus muutujasse

Kui kutsud välja meetodi, mis midagi tagastab, ja soovid selle infoga edasi midagi teha, on hea algajate tava panna tulemus kohe muutujasse:

```java
String firstName = student.getFirstName();
System.out.println("Õpilase nimi on: " + firstName);
```

See on täpselt sama põhimõte, mis backend'i reaalses koodis, kus service-meetod pärib andmebaasist objekti (nt `Location` või `Account`) ja tagastab selle kutsujale edasiseks töötlemiseks.

### Päriselu analoogia

Privaatne väli on nagu panga seif — sa ei saa käega otse seifi sisse pista, aga saad kasutada panga pakutud "teenindusakent" (get-meetodit), mis annab sulle kontrollitud viisil ligipääsu sisule.
