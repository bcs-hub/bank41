## BEB-7: pangaautomaatide asukoha teenuse ülesanne — `0:12:18` {#beb-7-ulesanne}

### Selgitus

Uue task'i (BEB-7) eesmärk: luua teenus, mis tagastab pangaautomaatide asukoha infot. Nõuded on kirjas task'i kirjelduses:

- Teenus võtab sisse **query parameetri** `cityId`.
- Kui `cityId` on `null`, tagastatakse **kõik** asukohad.
- Kui `cityId` on määratud, tagastatakse ainult **selle linna** asukohad.
- Tabelid, mis mängivad rolli: `city`, `location` (task'is nimetatud ka "City Allocation" kontekstis).
- Vastuseks tagastatakse listi objektidest väljadega: `locationId`, `cityName`, `locationName`.
- Kui ühtegi asukohta ei leita, peab teenus tagastama vea koodiga `NO_LOCATION_FOUND`.
- API dokumentatsioon (summary + description) tuleb ka kirja panna.

Reaalses valminud projektis (vt `backend/CLAUDE.md`) on see teenus dokumenteeritud kui:

```
GET /api/atm/locations?cityId=   Pangaautomaatide asukohtade loetelu (0 = kõik linnad)
```

See tähendab: lõplikus API-s kasutatakse "kõik linnad" tähistamiseks pigem väärtust `0`, aga videos harjutati läbi loogiliselt samaväärne, `null`-põhine lahendus — mõlemad lahendavad sama probleemi: kuidas eristada "kõik" ühest kindlast valikust.

### Skeem

```
Frontend                              Backend
   │  GET /api/atm/locations?cityId=2    │
   ├─────────────────────────────────────►
   │                                      │ cityId = 2 → otsi ainult
   │                                      │ selle linna asukohad
   │  200 OK [ {locationId, cityName,     │
   │            locationName}, ... ]      │
   │◄─────────────────────────────────────┤

   │  GET /api/atm/locations (cityId puudub)
   ├─────────────────────────────────────►
   │                                      │ cityId = null → tagasta
   │                                      │ KÕIK asukohad
```

### Päriselu analoogia

See on nagu kohviku menüü filtreerimine: "näita mulle ainult taimetoite" versus "näita mulle kõike". Kasutaja saab valida, aga vaikimisi (kui midagi ei vali) näeb ta tervet valikut.

## "Post-it" meetod: vaadete ja sõnumite planeerimine — `0:21:03` {#post-it-meetod}

### Selgitus

Õpetaja soovitab iga vaate (ekraanikuva) kohta koostada struktureeritud "post-it" märkme, mis sisaldab:

- **roll** (kes seda vaadet kasutab — nt admin, tavakasutaja)
- **faili nimi**
- **frontend'i rada** (route/path)

### Päriselu analoogia

## Andmebaasi mudel ja nimekonventsioonid — `0:22:14` {#andmebaasi-mudel-nimekonventsioonid}

### Selgitus

Enne frontend'i lõplikku valmis kavandamist tasub paralleelselt mõelda ka andmebaasi mudelile — kui vaates on väli, tähendab see enamasti, et andmebaasis peab olema vastav veerg. Soovitatud nimekonventsioonid:

- Tabelinimed **ainsuses** (nt `location`, mitte `locations`).
- Veergudes ei korrata tabelinime (nt `role` tabelis on veerg `name`, mitte `role_name` — sest kontekst juba ütleb, et tegu on rolliga).
- Sama põhimõte kehtib läbivalt: lühemad nimed = vähem korduvust koodis.

### Koodinäide (illustratiivne SQL, konventsiooni näitlik)

```sql
-- Hea: tabelinime ei korrata veerus
create table bank.role (
  id   integer primary key,
  name varchar(100) not null
);

-- Halb: tabelinimi kordub veerus
create table bank.role (
  id        integer primary key,
  role_name varchar(100) not null
);
```

### Päriselu analoogia

See on nagu kapis riiete sildistamine — kui kapp juba on märgitud "Sokid", ei ole mõtet iga paari peale veel kord kirjutada "sokid". Piisab lühikesest sisust.

## Task, AI ja "one-shot" kodeerimise reeglid — `0:28:52` {#one-shot-reeglid}

### Selgitus

Kursuse töövoog task'idega:

1. Task kirjeldab **mida** süsteemis peab muutuma (kriteeriumid, nõuded) — see on plaan, mitte kood.
2. Häguste kohtade selgitamiseks võib kasutada **Grill me**-tüüpi Skilli, mis esitab täpsustavaid küsimusi arendajale.
3. Arendaja saab ise proovida lahendust kirjutada, kasutades AI-d abistajana (vihjed, konsultatsioon), või lasta AI-l esmalt luua **kirjeldava dokumendi** muudatustest (ilma koodi kirjutamata) ja seejärel ise koodi kirjutada.
4. **"One-shot" kodeerimine on keelatud** — see tähendab, et ei tohi lihtsalt öelda AI-le "tee kogu task valmis" ja kopeerida tulemus üle vaatamata.

Peamine põhjus: kursuse eesmärk ei ole valmis projekt, vaid **õppimine** — kuidas mõelda, arutleda tiimina ja kasutada AI-d õigesti abivahendina, mitte asendajana.

### Päriselu analoogia

See on nagu autokooli õppimine simulaatoriga, mis sõidab sinu eest — võib-olla jõuad kiiremini sihtkohta, aga eksamil (päriselus) ei oska sa ise juhtida.

## Controlleri loomine: klassinimed ja Spring Bean — `0:36:15` {#controlleri-loomine}

### Selgitus

Uue teenuse loomist alustatakse alati **kontrollerist** (REST endpoint), sest see on koodi "esikaas" — sealt loeb arendaja edaspidi, mida süsteem teeb.

Klassinime valikul arutletakse mitme variandi vahel:

- `AtmController` — liiga geneeriline (viitaks pigem füüsilistele pangaautomaatidele kui asukohainfole).
- `AtmLocationController` — pikk, aga selge.
- `LocationController` — lühem, aga jätab lahtiseks, kas tulevikus tekib nt `Address` entiteet, mis samuti tahaks "Location" nime.

Valik langeb `LocationController` peale — kui hiljem selgub, et nimi ei sobi enam, saab seda **refaktoreerida** (IDE teeb selle turvaliselt kõikjal koodis ümber). See on nn "koodivõla" (technical debt) teadlik, kontrollitud vorm — ei ole vaja kõike ette näha, piisab, kui praegune valik on mõistlik.

### Koodinäide (illustratiivne, järgib `backend/CLAUDE.md` kihistruktuuri)

```java
package ee.bcs.bank.location.controller;

import org.springframework.web.bind.annotation.RestController;

@RestController
public class LocationController {
    // ...
}
```

`@RestController` annotatsioon muudab klassi **Spring Beaniks** — Spring loob sellest klassist objekti ja hoiab seda mälus (nn "Spring konteineris"), et teised osad süsteemist saaksid sellele viidata.

### Päriselu analoogia

See on nagu restorani "kelner" roll — kontroller võtab tellimusi (HTTP päringuid) vastu ja annab need edasi kööki (service kihile), aga ei tee ise süüa.

## Dependency Injection kontrollerklassis — `0:39:50` {#dependency-injection}

### Selgitus

Kui kontroller peab suhtlema mõne teise klassiga (nt Service klassiga), on selleks vaja väli (field), mis viitab sellele objektile. Sellist mehhanismi, kus Spring "sisestab" (injects) vajaliku objekti automaatselt, nimetatakse **Dependency Injection'iks (DI)**.

Praktikas: kirjutad `private final` väljad ja Spring täidab need konstruktori kaudu (kui klassil on üks konstruktor, ei ole isegi `@Autowired` annotatsiooni tarvis).

### Koodinäide

```java
@RestController
public class LocationController {

    private final LocationService locationService;

    public LocationController(LocationService locationService) {
        this.locationService = locationService;
    }
}
```

IDE (nt IntelliJ) oskab sellise klassi ja konstruktori ise genereerida — kui kirjutad `private LocationService locationService;` ja klassi `LocationService` veel ei eksisteeri, pakub IDE selle kohapeal loomist ("Create class").

### Päriselu analoogia

See on nagu kontoritöötaja, kellele antakse tööle asudes automaatselt ligipääs vajalikele tööriistadele (nt IT-osakonna poolt) — ta ei pea ise iga tööriista käsitsi taotlema.

## Meetodi struktuur ja @GetMapping kaardistus — `0:46:47` {#meetodi-struktuur-getmapping}

### Selgitus

Uue meetodi struktuuri osad, mida läbi käiakse:

1. **Nähtavus** (`public`) — teised klassid (Spring'i dispetšer) peavad meetodit väljast kutsuda saama.
2. **Tagastustüüp** — algselt `void`, hiljem täpsustatakse.
3. **Nimi** — algul `findAtmLocations`, hiljem lihtsustatud.
4. **Kaardistus (mapping)** — annotatsioon, mis ütleb, millise HTTP-sõnumi peale meetod käivitub.

`@GetMapping` annotatsioon seob konkreetse URL-raja konkreetse meetodiga — kui tuleb sisse `GET` sõnum sellele rajale, "dispetšer" (Spring'i sõnumite marsruutija) teab, keda välja kutsuda.

### Koodinäide

```java
@GetMapping("/atm/locations")
public void findLocations() {
    // hall (kasutamata) meetod, kuni miski selle välja ei kutsu
}
```

Enne annotatsiooni lisamist näitab IDE meetodit halli värviga — see tähendab, et miski koodis seda meetodit veel välja ei kutsu. Annotatsiooni järel muutub meetod "siniseks" (kasutusel), sest Spring teab nüüd, millal seda käivitada.

### Skeem

```
HTTP GET /atm/locations
        │
        ▼
 Spring'i dispetšer (DispatcherServlet)
        │  otsib sobivat @GetMapping-uga meetodit
        ▼
 LocationController.findLocations()
```

### Päriselu analoogia

See on nagu majanumber ukse peal — kirjakandja (Spring) teab täpselt, millisele uksele (meetodile) konkreetne kiri (HTTP sõnum) toimetada.

## @RequestParam ja request parameeter — `0:52:27` {#requestparam}

### Selgitus

Meetod ise "ei tea oma välisest elust midagi" — kui talle on vaja infot väljastpoolt (nt `cityId` väärtust URL-ist), tuleb see **eraldi ette anda parameetrina**. Selleks kasutatakse `@RequestParam` annotatsiooni, mis ütleb Spring'ile: otsi sõnumi URL-ist nimeline parameeter ja pane selle väärtus siia muutujasse.

### Koodinäide

```java
@GetMapping("/atm/locations")
public void findLocations(@RequestParam Integer cityId) {
    // cityId väärtus tuleb URL-ist, nt ?cityId=2
}
```

Kui sõnumis (URL-is) parameetrit ei ole, aga meetod eeldab seda kohustuslikuna, tagastab Spring automaatselt vea (HTTP 400 — vigane päring), sest ta ei suuda meetodit õigesti käivitada.

### Skeem

```
GET /atm/locations?cityId=2
                    └──┬──┘
                       │
          @RequestParam Integer cityId
                       │
                    cityId = 2
```

### Päriselu analoogia

See on nagu tellimisleht restoranis, kus on kindel lahter "laua number" — kelner (Spring) teab, kust see number tellimuselt lugeda ja kuhu toit hiljem viia.

## Nõutud vs valikuline parameeter (required=false) — `1:01:12` {#nouutud-vs-valikuline}

### Selgitus

Vaikimisi on `@RequestParam` väli **kohustuslik**. Kuna task nõuab, et `cityId` võib puududa (tähendades "kõik linnad"), tuleb parameeter märkida valikuliseks:

```java
@GetMapping("/atm/locations")
public void findLocations(@RequestParam(required = false) Integer cityId) {
    // cityId võib nüüd olla null
}
```

Annotatsiooni omadus (`required = false`) kehtib **ainult selle koodirea kohta**, millega ta on otseselt seotud — see on üldine reegel kõikide Java annotatsioonide puhul.

### Päriselu analoogia

See on nagu vormil olev tärniga tähistatud kohustuslik väli versus tärnita valikuline väli — ilma tärnita välja võib tühjaks jätta, formular ikkagi kehtib.

## API dokumentatsioon (@Operation) — `1:04:33` {#api-dokumentatsioon}

### Selgitus

Iga REST endpoint tasub varustada lühikese ja pikema kirjeldusega (nt Swagger/OpenAPI `@Operation` annotatsiooni `summary` ja `description` väljadega). See on eriti kasulik, kui arendaja, kes hiljem seda teenust muutma tuleb, alustab tavaliselt **kontrollerist** ("nagu raamatukaantest") — hea dokumentatsioon annab talle kohe õige mentaalse mudeli, ilma et ta peaks kogu koodi läbi lugema.

### Koodinäide

```java
@Operation(
    summary = "Tagastab pangaautomaatide asukohtade infot",
    description = "Kui cityId on null, tagastatakse kõik asukohad."
)
@GetMapping("/atm/locations")
public void findLocations(@RequestParam(required = false) Integer cityId) {
    // ...
}
```

Ilma dokumentatsioonita jääb tegevuse (`GET`), annotatsiooni ning tagastustüübi info ainsaks vihjeks — dokumentatsioon aitab mõista **äriloogikat**, mida ainult koodist alati üheselt aru ei saa.

### Päriselu analoogia

See on nagu toote infosilt poeriiulil — ilma selleta pead toote koostisosade teadasaamiseks pakendit lahti tegema; infosildiga saad selguse kohe, ilma pakendit avamata.

## Service kihile suunamine (delegeerimine) — `1:07:11` {#delegeerimine-service-kihti}

### Selgitus

Kontroller ise ei tohiks äriloogikat sisaldada — tema ülesanne on **suunata tegevus edasi** Service kihile ("kelnerpoiss annab tellimuse edasi köögile"). Selleks kutsutakse välja meetod juba loodud `locationService` objektil.

Kui vastavat meetodit Service klassis veel ei ole, oskab IDE pakkuda selle kohapeal loomist — nii tekib Service klassi meetod automaatselt õige signatuuriga (sisendparameetriga, mida kontrollerist kaasa anti).

### Koodinäide

```java
// LocationController
```

## Andmebaasi tabelid ja "Soft Delete" põhimõte — `1:11:33` {#soft-delete}

### Selgitus

Task viitab tabelitele `city` ja `location` (nimetatud ka "City Allocation" kontekstis). Kui proovida andmebaasist rida päriselt kustutada (nt `Location Id`, millele viitab mõni teine tabel, nt `location_transaction_type`), keeldub andmebaas — sest **foreign key** (välisvõti) takistab viidatud rea kustutamist.

Lahendus on **Soft Delete** (pehme kustutamine): rida ei kustutata füüsiliselt, vaid selle `status` veerg muudetakse (nt aktiivsest `A` millekski muuks). Teenused, mis andmeid näitavad, filtreerivad alati ainult `status = 'A'` read.

Sama põhimõtet saab laiendada ka **ajutise nähtavuse** juhtimiseks — nt kaks veergu (`start`/`end` kuupäev), mis määravad, millal andmed muutuvad "elavaks" või "aeguvad". Näitena toodi pangamakse ajastamine: makse salvestatakse "ootel" (pending) staatusega koos kuupäevaga, ning taustal töötav protsess (scheduler) kontrollib regulaarselt, kas mõne ootel makse aeg on käes, ja käivitab siis sama koodilõigu, mida kasutatakse tavalise kohese makse puhul (taaskasutus).

### Skeem

```
Kustutamise katse:
  DELETE FROM location WHERE id = 1
        │
        ▼
  Foreign key viga (location_transaction_type viitab id=1 peale)
        │
        ▼
  Lahendus: UPDATE location SET status = 'D' WHERE id = 1
            (rida jääb alles, aga ei ole enam "aktiivne")
```

### Päriselu analoogia

See on nagu töötaja arhiveerimine personalisüsteemis lahkumisel — teda ei kustutata andmebaasist (sest tema nimi on siiski seotud vanade dokumentide, palgalehtedega), vaid tema staatus muudetakse "mitteaktiivseks".

## @Query ja JPQL: loetav päring — `1:44:16` {#query-jpql}

### Selgitus

Kui meetodinimi läheb liiga pikaks ja loetamatuks (nt `findByCityIdAndStatusOrderByCity_CityNameAscLocationNameAsc`), on parem kasutada **@Query** annotatsiooni koos **JPQL**-iga (Java Persistence Query Language — SQL-i sarnane keel, aga viitab Java klassidele/entiteetidele, mitte otse andmebaasi tabelitele/veergudele).

IDE oskab olemasoleva meetodinime-põhise päringu automaatselt "ekstraktida" `@Query` annotatsiooniks (refaktoreerimisfunktsioon).

### Koodinäide

```java
@Query("""
    select l from Location l
    where l.city.id = :cityId
      and l.status = :status
    order by l.city.cityName asc, l.locationName asc
    """)
List<Location> findLocations(Integer cityId, String status);
```

Tähtsad detailid:

- `Location l` — `l` on **alias**, mis viitab `Location` **entiteedile** (Java klassile), mitte otse andmebaasi tabelile.
- `l.city.id` — JPQL oskab "iseenesest" liikuda seose kaudu sügavamale (`Location` → `City`), ilma et peaks käsitsi `JOIN` kirjutama — see toimub taustal automaatselt.
- `:cityId` — nimeline parameeter, mis seotakse meetodi argumendiga.

See on nagu GPS-i sihtkoha sisestamine aadressina ("Tallinn, Viru 1") selle asemel, et sisestada käsitsi GPS-koordinaadid — JPQL laseb rääkida objektide ja seoste keeles, mitte tabelite-veergude keeles.

## Method overloading ja meetodi signatuur — `1:56:02` {#method-overloading}

### Selgitus

Java lubab **mitut meetodit sama nimega**, kui nende **signatuur** (parameetrite arv ja tüübid) erineb — seda nimetatakse **overloading'uks** (ülelaadimine). Java otsustab, millist meetodit käivitada, sisendite tüüpide järgi (parameetrite *nimed* ei mängi rolli, ainult *tüübid* ja nende järjekord).

```java
public void doSomething(String s, Integer i) { ... }
public void doSomething(Integer i, String s) { ... }  // erinev signatuur, OK

public void doSomething(String a, Integer b) { ... }
public void doSomething(String x, Integer y) { ... }   // veaviga: sama signatuur!
```

Videos tekkis see teema, kui kaaluti kahe eraldi meetodi loomist (üks `cityId`-ga otsimiseks, teine ilma) — probleem: JPA/Spring Data derived query meetodid ei saa jagada sama nime, kui nende signatuur kattub, seega tuli mõelda alternatiivne lahendus (vt järgmine peatükk — "nullitrikk").

### Päriselu analoogia

See on nagu kaks võtmeauku, mis mõlemad kannavad nime "uks" — kui mõlemad võtmed on identsed (sama "signatuur"), ei tea uks, kumba kasutada. Kui võtmed on erineva kujuga (erinev signatuur), töötab kõik.

## Nullitrikk: üks päring kõigi filtrite jaoks — `2:04:38` {#nullitrikk}

### Selgitus

Kahe eraldi meetodi (üks kõigile, teine konkreetsele linnale) lähenemine muutub kiirelt keeruliseks, kui filtreid on rohkem kui üks — kombinatsioonide arv kasvab plahvatuslikult (`if`-lausete "kaheksa haru" probleem kolme filtri puhul).

Õpetaja demonstreeris SQL Console'is elegantse lahenduse: kasutada tingimust kujul `(:parameeter IS NULL OR veerg = :parameeter)`. Kui parameeter on `null`, on tingimuse esimene pool alati tõene (`true`), mistõttu **kogu OR-tingimus läheb tõeseks olenemata veeru väärtusest** — st filter "ei rakendu". Kui parameeter on täidetud, kontrollitakse tavapäraselt võrdsust.

### Koodinäide (JPQL)

```java
@Query("""
    select l from Location l
    where (:cityId is null or l.city.id = :cityId)
      and l.status = :status
    order by l.city.cityName asc, l.locationName asc
    """)
List<Location> findFilteredLocations(Integer cityId, String status);
```

Sama mustrit saab laiendada mitmele filtrile korraga (nt lisaks `cityId`-le ka `numberOfAtms`) — iga filter saab oma `(:parameeter is null or ...)` tingimuse, ja need kombineeritakse `and`-iga. Lahendus töötab "lolli kindlalt" ükskõik millise filtrite kombinatsiooniga, ilma `if`-lausete plahvatuseta.

See võte töötab usaldusväärselt just **ID-väljade** puhul, kuna ID väärtus ei saa andmebaasis kunagi tegelikult olla `null` — seega `null` on turvaline "kõik" tähis.

### Skeem

```
cityId = null:
  (null is null OR city_id = null)  →  (TRUE or ...)  →  TRUE  → rida läbib

cityId = 2:
  (2 is null OR city_id = 2)  →  (FALSE or city_id=2)  →  sõltub reast
```

### Päriselu analoogia

See on nagu turvavärav, mis lubab läbi kõiki, kui pileti kontroll on "väljas" (null), aga kontrollib täpselt piletinumbrit, kui kontroll on "sees" — sama värav, kaks käitumisrežiimi.

## DTO: miks Entity objekte välja ei anta — `2:27:32` {#dto-miks-mitte-entity}

### Selgitus

Põhimõte: **Entity objekte (andmebaasi tabeleid peegeldavad klassid) ei tohi kunagi tagastada otse süsteemist välja** (API vastuses). Selle asemel luuakse **DTO** (Data Transfer Object) — kergem klass, mis sisaldab ainult neid välju, mida väljapoole vaja on.

Videos aruteleti, milline nimi DTO-le anda: nime `Location` ei saa kasutada (see on juba Entity nime all hõivatud), nime `LocationDto` peetakse liiga geneeriliseks. Lisaks eelistatakse DTO-des **lamedat (flat) struktuuri** — mitte objekt-objekti-sees, vaid kõik väljad otse tasapinnal:

```java
// Halb: mitmekihiline struktuur (nagu Entity)
class LocationInfo {

    String locationName;
}

// Hea: lame struktuur
class LocationInfo {
    Integer locationId;
    String cityName;    // otse väli, mitte objekt
    String locationName;
}
```

See kattub `backend/CLAUDE.md` reegliga: *"Kontrollerid näevad ainult DTOsid. MapStructi mapperid teisendavad DTOd JPA entiteetideks ja vastupidi."*

## Mapper ja MapStruct: automaatne teisendus — `2:36:08` {#mapper-mapstruct}

### Selgitus

Entity objekti käsitsi DTO-ks teisendamine (välja-väljalt kopeerimine) on tüütu ja veaohtlik. Selle jaoks kasutatakse raamistikku **MapStruct**: `@Mapper` annotatsiooniga liides, kus iga meetod kirjeldab teisendust `@Mapping(source = "...", target = "...")` abil, ja MapStruct genereerib kompileerimise ajal automaatselt sellele vastava klassi (nt `LocationMapperImpl` kausta `src/main/generated/`).

### Koodinäide

```java
@Mapper(componentModel = "spring")
public interface LocationMapper {

    @Mapping(source = "id", target = "locationId")
    @Mapping(source = "city.cityName", target = "cityName")
    @Mapping(source = "locationName", target = "locationName")
    LocationInfo toLocationInfo(Location location);

    // MapStruct genereerib selle AUTOMAATSELT, sest ülemine meetod
    // (Location -> LocationInfo) juba eksisteerib:
    List<LocationInfo> toLocationInfos(List<Location> locations);
}
```

Väga oluline tähelepanek: kui üksik-objekti teisendusmeetod (`Location` → `LocationInfo`) on juba olemas, oskab MapStruct **iseseisvalt tuletada** ka listi versiooni (`List<Location>` → `List<LocationInfo>`) — genereeritud kood käib lihtsalt `for`-tsükliga läbi kõik elemendid ja rakendab olemasolevat üksikobjekti-meetodit igaühele. See säästab palju käsitsi kirjutatavat koodi (näites umbes 5 rida deklaratsiooni asemel 25-30 rida käsitsi `for`-tsüklit).

`city.cityName` süntaks `@Mapping`-annotatsioonis näitab, kuidas MapStruct oskab minna **sügavamale seose kaudu** (Location → City → cityName), et lamestada tulemus üheks flat DTO väljaks.

### Skeem

```
Location (entity)                    LocationInfo (DTO)
┌─────────────────┐                 ┌──────────────────┐
│ id               │  toLocationInfo │ locationId        │
│ city: City ──────┼───────────────►│ cityName           │
│   ├ id           │  (MapStruct)    │ locationName       │
│   └ cityName      │                 └──────────────────┘
│ locationName      │
│ status            │
└─────────────────┘

List<Location>  ──toLocationInfos (auto-tuletatud)──►  List<LocationInfo>
```

### Päriselu analoogia

See on nagu tõlk, kes juba oskab tõlkida ühe lause — kui talle anda terve raamatu tekst (list lausetest), ei pea talle uuesti õpetama, kuidas tõlkida; ta lihtsalt rakendab sama oskust iga lause peale ükshaaval.
