## 1. Arhitektuurne otsus — sama vaade lisamiseks ja muutmiseks — `0:03:31`

### Selgitus — kaks võimalikku lähenemist

```
Variant A (õpitakse videos):
  /location → sama vaade käitub kahepidi:
    ilma parameetrita = "lisa" olukord
    query-parameetriga (nt ?locationId=12) = "muuda" olukord

  /new-location → ainult lisamiseks

### Plussid ja miinused

```
Ühine vaade (Variant A):
  + Vähem koodikordust — üks fail teenib mõlemat eesmärki
  − Fail läheb pikemaks (rohkem HTML-i ja JS-i ühes kohas)

Eraldi vaated (Variant B):
  + Iga fail jääb lühemaks ja fokusseeritumaks

Õpetaja valis teadlikult **ühise vaate lähenemise**, kuigi möönis, et see pole ainuõige — see on **arhitektuuriline otsus**, kus mõlemad variandid on valiidsed, olenevalt projekti ja tiimi vajadustest.

## 4. `SessionStorageService` — `userIsAdmin()` meetod — `0:34:36`

Kuna menüülink peab olema nähtav ainult adminile, laiendati olemasolevat `SessionStorageService`-i uue meetodiga.

### Koodinäide

```js
// frontend/src/services/SessionStorageService.js
export default {
  userIsLoggedIn() {
    return sessionStorage.getItem('userId') !== null
  },

  userIsAdmin() {
    return sessionStorage.getItem('roleName') === 'admin'
  },
}
```

### Selgitus

Meetod tagastab **booleani** — see on lihtsalt kolmene võrdlus (`===`), mis kontrollib, kas `sessionStorage`-is talletatud roll on täpselt `'admin'`. Kui `return` puudub, kaob boolean-väärtus (`true`/`false`) meetodi sees, samamoodi nagu Promise objekti puhul.

## 7. Sündmuspõhine menüü uuendamine — `updateNavMenu` — `0:49:41`

Kui kasutaja logib sisse, peab menüü **uuenema kohe**, ilma lehte värskendamata. Selleks kasutati juba varem sisse seatud `$emit`-`@event` mustrit `LoginView` ja `App.vue` vahel.

### Skeem

```
LoginView (Child)                    App.vue (Parent)
  login õnnestub
  $emit('event-user-logged-in')  →   @event-user-logged-in="updateNavMenu"
                                       ↓
                                      updateNavMenu() käivitub
                                      isLoggedIn = true
                                      isAdmin = SessionStorageService.userIsAdmin()
```

### Koodinäide

```js
// frontend/src/App.vue
export default {
  name: 'App',
  data() {
    return {
      isLoggedIn: SessionStorageService.userIsLoggedIn(),
      isAdmin: SessionStorageService.userIsAdmin(),
    }
  },
  methods: {
    updateNavMenu() {
      this.isLoggedIn = true
      this.isAdmin = SessionStorageService.userIsAdmin()
    },

    executeLogOut() {
      sessionStorage.clear()
      this.isLoggedIn = false
      this.isAdmin = false
      NavigationService.navigateToHomeView()
    },
  },
}
```

```html
<RouterView @event-user-logged-in="updateNavMenu" />
```

### Miks mitte lihtsalt otse HTML-i sisse kirjutada?

Enne oli lihtsalt käsitsi väärtustatud `isLoggedIn = true` otse Login View'i templeidi sees. Kui lisandus vajadus ka `isAdmin`-i kontrollida, ei mahtunud see enam lihtsalt HTML-i sisse — vaja oli **eraldi meetodit**, mis suudab käivitada mitu tegevust korraga.

### Meetodi nimi "hägusalt" — `update`

```
"update" on hägune sõna — see ei ütle täpselt, mis toimub sees,
aga see äriloogiline tähendus (menüüd uuendatakse) jääb selgeks.
```

See on sama muster, mida käsitleti eelmistes videotes — kui meetod teeb mitut asja, ei tasu talle panna liiga täpset nime, mis "valetaks" ühte konkreetset tegevust kirjeldades.

## 10. Kolmekihiline andmevoog — Props kosk — `1:50:59`

Andmed peavad "voolama" kolme faili vahel: `LocationView` → `LocationForm` → `CitiesDropdown`.

### Skeem — kosk (andmed voolavad alla)

```
LocationView (data: cities)
      │ props :cities="cities"
      ▼
LocationForm (props: cities)
      │ props :cities="cities"
      ▼
CitiesDropdown (props: cities)
```

### Selgitus

```
Vanem annab andmeid lapsele — ainult PROPS'i kaudu.
Laps annab lapselapsele edasi — TA PEAB SEDA ISE PROGRAMMEERIMA.
Andmed ei "hüppa" iseenesest üle vahepealse kihi.
```

Kuigi `LocationView`-l on andmed juba olemas `data()`-blokis, ei jõua need automaatselt `CitiesDropdown`-i — igal vahekihil (siin: `LocationForm`) peab olema oma `props` definitsioon, mis andmed edasi võtab ja oma lapsele annab.

### Koodinäide

```js
// LocationView.vue — omab andmeid
data() {
  return {
    cities: [{ cityId: 0, cityName: '' }],
    // ...
  }
},
methods: {
  handleGetCitiesResponse(response) {
    this.cities = response.data
  },
}
```

```js
// LocationForm.vue — vahekiht, edastab props edasi
props: {
  cities: Array,
},
```

```html
<!-- LocationForm.vue template — annab edasi oma Child'ile -->
<CitiesDropdown :cities="cities" @event-new-city-selected="..." />
```

### Päriselu analoogia

See on nagu kosk mägedes — vesi (andmed) voolab ülevalt alla astmete kaupa, aga iga aste peab ise vee järgmisele astmele edasi laskma. Kui üks aste on "kuiv" (props puudub), ei jõua vesi enam allapoole, isegi kui see kõrgemal olemas on.

## 12. Response/data mudel — üksikasjalik kordamine — `1:28:42`

Enne uue meetodi kirjutamist kordas õpetaja põhjalikult üle, kuidas Axiose vastuse struktuurist andmeid kätte saada — see kordab varasemate videote teemat, kuid süvendatult.

### Skeem

```
response (kogu vastus)
  ├─ response.status       (nt 200)
  ├─ response.statusText   (nt "OK")
  └─ response.data         ← see meid enamasti huvitab
        └─ [{ cityId: 0, cityName: '' }, ...]
```

### Koodinäide

```js
methods: {
  getCities() {
    CityService.getCitiesRequest()
      .then((response) => this.handleGetCitiesResponse(response))
      .catch(() => NavigationService.navigateToErrorView())
  },

  handleGetCitiesResponse(response) {
    this.cities = response.data
  },
},
```

### Vea puhul lisandub veel üks kiht

```
error.response.data.message   ← veakirjelduse tekst
error.response.data.errorCode ← äriloogiline veakood
error.response.status         ← HTTP staatuskood
```

Õpetaja kasutas selle näitlikustamiseks "matrjoška" (vene pesanukk) analoogiat — veaobjektis on veel üks kiht ümbrist enne, kui jõuad tegeliku sisuni.

## 13. Enneaegne meetodiviide — IDE aitab luua puuduva meetodi — `1:18:07`

Sama töövõte, mis on korduvalt varasemates videotes esinenud: kirjutada meetodi väljakutse ette (`handleGetCitiesResponse(response)`), enne kui meetod ise eksisteerib, ja lasta IDE-l genereerida selle skelett.

### Koodinäide (levinud viga selle juures)

```js
// ❌ Vale — puudub "this" viide
.then((response) => handleGetCitiesResponse(response))

// ✅ Õige — viitab klassi meetodile "this" kaudu
.then((response) => this.handleGetCitiesResponse(response))
```

### Selgitus

Kui `this` puudub, ei tea JavaScript, et `handleGetCitiesResponse` on klassi (komponendi) `methods`-bloki meetod — see viga ilmneb tihti just siis, kui meetodit kirjutatakse käsitsi, mitte IDE autocomplete abil.

## 14. Levinud viga — kood satub valesse skoopi (Copy-Paste lõks) — `1:47:14`

Video demonstreeris tahtlikult tehtud vea peal, kuidas märgata, kui copy-paste'itud kood satub vale koodiploki sisse.

### Skeem

```
✅ Õige:
export default {
  methods: {
    getCities() { ... }
  },
  beforeMount() {
    this.getCities()   ← siin on OMA plokk
  },
}

❌ Vale (levinud copy-paste viga):
export default {
  methods: {
    getCities() { ... }

    beforeMount() {     ← kogemata sattus SISSE methods-plokki!
      this.getCities()
    }
  },
}
```

### Kuidas sellist viga märgata?

```
Märk: meetodi nimi (nt getCities) on hall värvi VÕI ei ole enam sinine/aktiivne —
      IDE ütleb, et keegi seda ei kasuta ("unused").
```

Kui meetod, mis alati on varem korrektselt käivitunud, järsku "ei tööta" ilma nähtava veateateta, on esimene kahtlus alati: kas kood on ikka **õiges kohas** (õige skoobi sees). See on eriti levinud viga, kui kopeeritakse koodijuppe teistest projektidest või näidetest, ilma täpselt kontrollimata, kuhu need täpselt sattusid.

## 15. URL-i disain — nimisõna vs. tegusõna — `2:17:38`

Süvitsi käsitleti REST API URL-ide loomise põhimõtet: **URL peab olema nimisõna, tegevus tuleb HTTP meetodist**.

### Selgitus

```
HTTP meetod = TEGUSÕNA (mida teha)
  GET    → too, anna
  POST   → lisa, loo
  PUT    → asenda, kirjuta üle
  DELETE → kustuta

URL = NIMISÕNA (kellega/millega tegu on — "kes, mis")
  /atm-locations
  /cities
  /users/12
```

### Koodinäide

```
GET  /api/cities           ← "too mulle linnad"
POST /api/atm/locations    ← "lisa uus pangaautomaadi asukoht"
PUT  /api/users/12         ← "asenda kasutaja nr 12 andmed"
DELETE /api/users/12       ← "kustuta kasutaja nr 12"
```

### Miks tegusõna URL-is on vale?

```
❌ /api/getCities   — "get" on siin üleliigne, sest GET meetod juba ÜTLEB "too"
✅ /api/cities       — piisab nimisõnast, HTTP meetod annab tegevuse
```

### Päriselu analoogia

Sama loogika kehtib Apollo Kino veebilehe URL-ide juures — kui klikid lingi peale (mis alati läheb GET-päringuna), ütled brauserile "anna mulle see leht", mitte "GET anna mulle GET leht". Tegevus (GET) on juba HTTP protokolli tasandil olemas, URL ise ütleb ainult, **mida** tahetakse.

## 16. Muutuja nimetamine — vältida tegusõnu ja sõna "Request" — `2:22:15`

Sarnane loogika kehtib ka **muutujate nimetamisel**: muutuja nimi peab olema nimisõna (kes/mis), mitte tegusõna.

### Selgitus

```
Klassi nimi   → alati nimisõna (kes/mis)
Muutuja nimi  → alati nimisõna (kes/mis)
Meetodi nimi  → alati tegusõna (mida teeb)
```

### Koodinäide

```js
// ❌ Halb — "post" on tegusõna, tekitab segadust
const postLocation = { ... }

// ✅ Hea — lihtne nimisõna, selge
const location = { ... }
```

### Miks mitte alati sõna "Request" kasutada?

Varasemates videotes kasutati `loginRequest`-muutujat, kuna sisselogimine on kontekstuaalselt kahemõtteline sõna (nii tegusõna kui nimisõna). Pangaautomaadi asukoha puhul selline kahemõttelisus puudub, seega piisab lihtsalt `location`-ist, ilma et oleks vaja lisada sõna `Request`. See on **maitse küsimus**, mitte kindel reegel — sõltub kontekstist, kas lisasõna aitab selgust luua.

## 17. `Request Body` mudel — postitatavate andmete struktuur — `2:14:44`

## 18. Kolmekorruseline sündmuste edastamine (Event kaskaad) — `2:28:11`

Kuna `CitiesDropdown` on nüüd sügavamal (kolmandal tasandil `LocationView`-st), tuleb sündmus edastada läbi mitme `$emit`/`@event` kihi.

### Skeem

```
CitiesDropdown              LocationForm                 LocationView
  @change                     kinnipüüdmine                kinnipüüdmine
  $emit('event-new-       →   @event-new-city-        →   @event-new-city-
  city-selected', value)      selected="$emit(             selected="location.
                               'event-new-city-             cityId = $event"
                               selected', $event)"
```

### Koodinäide (vahekiht — pelgalt edasi viskamine)

```html
<!-- LocationForm.vue -->
<CitiesDropdown
  :cities="cities"
  @event-new-city-selected="$emit('event-new-city-selected', $event)"
/>
```

```html
<!-- LocationView.vue — lõplik vastuvõtja -->
<LocationForm :cities="cities" @event-new-city-selected="location.cityId = $event" />
```

### Selgitus

`LocationForm` ei tea (ega peagi teadma), mida vanem selle sündmusega teeb — ta lihtsalt **viskab sama paki edasi ülespoole**, kasutades sama meetodit (`$emit`), mida ta ise sai. See on "orb" komponent — ta ei tea, kes tema vanem on, ainult teab, et tal on midagi teada anda.

### `emits`-plokk kui dokumentatsioon

```js
// LocationForm.vue
emits: ['event-new-city-selected'],
```

See deklaratsioon aitab IDE-l pakkuda automaatselt sündmuse nime, kui vanemkomponent kirjutab `@` ja hakkab tippima — WebStorm suudab tuvastada, milliseid sündmusi antud komponent võib saata, ilma et arendaja peaks seda meelest teadma.
