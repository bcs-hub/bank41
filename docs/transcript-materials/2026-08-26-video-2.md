## Multiple Page Application (MPA) — klassikaline mitme lehega veebisait — `0:58:33` {#mpa}

### Selgitus

**Multiple Page Application** on klassikaline veebisaidi arhitektuur, kus serveril on **palju eraldi HTML faile** — igal lehel oma fail. Näide (booking.com stiilis): iga hotelli leht on eraldi `.html` fail (`economy-hotel.html`, `citybox-tallinn.html` jne).

Õpetaja kasutab metafoori: MPA on nagu **raamat täis lehekülgi**, kus iga leht on iseseisev.

### Skeem

```
Server (booking.com):
  ├── economy-hotel.html
  ├── citybox-tallinn.html
  └── hilton-tallinn.html
```

Kui klõpsad lingil erinevale hotellile, laeb brauser **täiesti uue HTML faili** — kogu leht laetakse otsast peale uuesti (näed seda korraks valge ekraanina).

## URL-i ülesehitus: aadress vs parameetrid — `0:59:53` {#url-ulesehitus}

### Selgitus

URL koosneb kahest osast:
- **Aadress** — kõik enne küsimärki (`?`) — see viitab konkreetsele ressursile/failile serveris
- **Parameetrid** — kõik pärast küsimärki — sisendid, mis kohandavad lehe sisu (nt kuupäevad, otsingusõnad), kuid ei viita erinevale failile

### Skeem

```
https://booking.com/hotel/economy.html?checkin=2026-08-26&checkout=2026-08-28
└──────────────── aadress ────────────┘└──────── parameetrid ─────────┘
```

### Päriselu analoogia

Aadress on nagu maja number — see viib sind konkreetse hoone juurde. Parameetrid on nagu lisainfo uksekella juures ("kolmas korrus, vasakpoolne uks") — täpsustavad, mida sa täpselt tahad, aga ei muuda hoonet ennast.

## Single Page Application (SPA) — võluraamatu metafoor — `1:04:58` {#spa}

### Selgitus

**Single Page Application** on arhitektuur, kus terve projekti kohta on olemas **ainult üks HTML fail** (tavaliselt `index.html`). Kõik "erinevad lehed", mida kasutaja näeb, on tegelikult **sama HTML-i erinevad dünaamilised olekud**.

Õpetaja metafoor: **maagiline raamat**, millel on:
- **Kaaned** (oranž) — alati samad, ei muutu kunagi (nt navigatsioonimenüü)
- **Sisu** (sinine) — muutub dünaamiliselt vastavalt sellele, mida kasutaja tahab näha

### Skeem

```
Raamatu kaaned (alati samad):    Sisu (muutub dünaamiliselt):
┌─────────────────────┐          ┌──────────────────┐
│  [Menüü: Home|Test]  │  <--->   │  Home lehe sisu    │
│                       │          │  VÕI               │
│                       │          │  Test lehe sisu    │
└─────────────────────┘          └──────────────────┘
```

### Päriselu analoogia

SPA on nagu kinolinal projitseeritav "elav" pilt — ekraan (raamat) ise ei vaheta, aga see, mida ekraanile projitseeritakse, muutub pidevalt. MPA on nagu diaprojektor, mis vahetab füüsiliselt terve slaidi iga kord, kui liigud edasi.

## Client-Server arhitektuur: restorani analoogia — `1:07:00` {#client-server}

### Selgitus

Õpetaja kasutab **restorani metafoori**, et selgitada, kuidas frontend, backend ja andmebaas omavahel suhtlevad:

| Restoran | Tarkvara |
|---|---|
| Klient laua taga | **Client** (brauser kasutaja arvutis) |
| Serveerija (kelner) | **Frontend** — võtab tellimuse vastu, esitleb, aga ei valmista toitu |
| Tagaruum (kokk) | **Backend** — valmistab tegelikult andmed/loogika |
| Menüü/retseptid | **Andmebaas** — kust tulevad tegelikud andmed |

Tähtis nüanss: klient ei tea (ega tahagi teada), mis toimub "tagaruumis" (backend'is) — ta lihtsalt tahab, et "menüüst valik üks" jõuaks lauale. Iga osapool teeb ainult oma osa: serveerija ei lähe ise kööki toitu valmistama, samamoodi frontend ei tee ise andmetöötlust — see on backend'i ülesanne.

### Skeem

```
Client (brauser) <---> Frontend (kelner) <---> Backend (kokk) <---> Andmebaas (laoseis)
```

## Kuidas SPA taustal töötab: index.html + dünaamiline sisu — `1:13:45` {#spa-tehniline}

### Selgitus

Kui brauser laeb SPA rakenduse, näeb protsess välja selline:

1. Serveri aadressile saadetakse sõnum, server vastab **ühe ja ainsa** `index.html` failiga
2. See `index.html` sisaldab alati samu osi (nt navigatsioonimenüü) — need on "raamatu kaaned"
3. Vastavalt sellele, millisele **rajale (URL path)** kasutaja soovib minna, laetakse **vastav vaate fail (view)**, mis paneb kokku ülejäänud HTML-i
4. Brauser saab kätte HTML-i struktuuri, aga **andmeid pole veel** — brauser peab eraldi päringu(d) tegema backend'ile, et andmed kätte saada
5. Kui andmed (JSON formaadis) jõuavad kohale, renderdab brauser need dünaamiliselt lehe sisse

### Skeem

```
1. Brauser --> "anna mulle leht" --> Server
2. Server --> index.html (kaaned + tühi struktuur) --> Brauser
3. Brauser --> "anna mulle andmed" (nt GET /api/locations) --> Backend
4. Backend --> JSON andmed --> Brauser
5. Brauser renderdab andmed olemasolevasse struktuuri
```

### Päriselu analoogia

See on nagu ajalehe raam, mis saabub tühjana (kaante ja pealkirjaga), ja seejärel saabuvad eraldi artiklid (andmed), mis pannakse raami sisse. Raam ise (navigatsioon, kujundus) jääb samaks, ainult sisu vahetub.

## Miks SPA üldse tekkis: Facebook ja React — `1:24:20` {#spa-pohjus}

### Selgitus

SPA tehnoloogia tekkis vajadusest lahendada probleem: kui andmed muutuvad väga sageli/reaalajas (nt sotsiaalmeedia feed), oleks kohutavalt ebamugav, kui **terve lehekülg peaks iga kord uuesti laadima** (näidates korraks valget ekraani).

**React** (loonud Facebook, tänaseks Open Source) töötati välja just selleks, et lahendada lõputu kerimise (infinite scroll) probleem — kui kogu leht laeks iga kord uuesti, kaotaks kasutaja oma koha kerimises.

SPA lahendus: **ainult osa HTML-ist uuendatakse**, mitte kogu leht. See annab illusiooni, nagu liiguksid ühelt "lehelt" teisele, kuigi tehniliselt on kogu aeg tegemist sama `index.html` failiga, mis lihtsalt uueneb osade kaupa.

### Kolm peamist SPA raamistikku

- **Angular**
- **Vue** (mida see kursus kasutab)
- **React** (kõige populaarsem, Facebooki looming)

### Päriselu analoogia

Vana viis (MPA) on nagu terve toa mööbli vahetamine iga kord, kui tahad ühte pilti seinal vahetada. SPA on nagu ainult ühe pildi vahetamine — ülejäänud tuba (raam) jääb puutumata.

## Vue projekti struktuur: router, views, App.vue — `1:46:13` {#vue-struktuur}

### Selgitus

Vue projektis (`frontend/src/`) on tähtsad kaustad:

- **`views/`** — failid, mis reageerivad kindlale URL rajale ja kuvavad konkreetset sisu (nt `HomeView.vue`)
- **`router/`** — kataloog, kus on `index.js` fail, mis seob rajad (path) vastavate vaadetega
- **`App.vue`** — juurkomponent, mis sisaldab elemente, mis on **alati nähtaval** (nt navigatsioonimenüü) — need on "raamatu kaaned"

### Skeem

```
frontend/src/
├── App.vue          <- alati nähtav (nav menu) + <RouterView/>
├── router/
│   └── index.js      <- rajad <-> vaated seosed
└── views/
    └── HomeView.vue   <- konkreetne vaade
```

## Vue Router: routes massiiv ja path/name/component — `1:54:50` {#vue-router}

### Selgitus

`router/index.js` sisaldab **routes massiivi**, kus iga element on objekt kolme väljaga:
- **`path`** — URL rada (nt `/`, `/test`)
- **`name`** — sisemine nimi (konventsioon: `homeRoute`, mitte lihtsalt `home` — nimi eristab, et tegu on ruudi (route) nimega, mitte vaate failinimega)
- **`component`** — millist vaate komponenti sellele rajale laadida

### Koodinäide (projektist, `frontend/src/router/index.js`)

```javascript
import { createRouter, createWebHistory } from 'vue-router'
import HomeView from "@/views/HomeView.vue";

const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    {
      path: '/',
      name: 'homeRoute',
      component: HomeView,
    },
  ],
})

export default router
```

`@` märk viitab alati `src/` kataloogile — see on Vue projekti sisseehitatud kokkulepe, mis välistab segaduse suhteliste teekondadega (nt kas peab kirjutama `./` või `../public/`).

### Lohisev koma (trailing comma)

JavaScript-is on lubatud jätta viimase massiivi/objekti elemendi järele koma (nn "lohisev koma") — see pole viga, ja on hea tava, sest kui hiljem lisad uue rea, on kõigil ridadel juba koma olemas (ei pea meeles pidama esimest korda koma lisada). **JSON failides see aga ei ole lubatud** — seal ei tohi viimase elemendi järel koma olla.

## RouterView ja RouterLink — `1:56:01` {#router-view-link}

### Selgitus

- **`<RouterView/>`** — koht `App.vue` failis, kuhu laetakse hetkel aktiivse raja vastav vaade (dünaamiline osa)
- **`<RouterLink to="...">`** — Vue'i oma "link" element, mis navigeerib rakenduse sees ilma tervet lehte uuesti laadimata

### Koodinäide (kontseptuaalne, App.vue struktuur)

```html
<template>
  <nav>
    <RouterLink to="/">Kodu</RouterLink>
  </nav>
  <RouterView/>
</template>
```

`<RouterView/>` "asub" alati samas kohas — ainult selle sisu vahetub vastavalt aktiivsele rajale.

## Template ja Script osad Vue komponendis — `1:46:45` {#template-script}

### Selgitus

Vue komponendil (`.vue` fail) on kaks peamist plokki:
- **`<template>`** — siia käib **ainult HTML**, mitte JavaScript. See on vaate nähtav osa.
- **`<script>`** — siia käib rakenduse loogika (JavaScript)

**Hea tava:** `<template>` sees tohib olla ainult **üks juurelement** (üks "child"), mis ümbritseb kõike muud (nt üks `<div>`). See on Vue arendajate kokkulepe, mitte range tehniline nõue tänapäeval, aga aitab vältida segadust.

**Tõusev tava:** paljud arendajad panevad `<template>` **enne** `<script>`-i (visuaalne pool eespool). Loogika: kui loed koodi ülevalt alla, näed kõigepealt, mida "lugu" räägib (visuaalne struktuur), ja alles siis, kuidas see funktsionaalsus taustal töötab (andmete hankimine, loogika).

### Koodinäide (projektist, `frontend/src/views/HomeView.vue`)

```html
<script></script>

<template>
  <div class="container text-center">
    <div class="row">
      <div class="col">See on meie äge bank! :)</div>
      <div class="col">
        <img
          src="https://media4.giphy.com/..."
          class="img-thumbnail"
          alt="Lahe, hoiupõrsas, lööme ta katki! "
        />
      </div>
    </div>
  </div>
</template>
```

## Bootstrap Grid süsteem: container, row, col — `2:13:53` {#bootstrap-grid}

### Selgitus

Bootstrap pakub valmis **grid (ruudustik) süsteemi** paigutuse (layout) haldamiseks — mitte ise CSS-i leiutama, vaid kasutama valmis klasse:

- **`container`** — ümbritsev element, mis haldab kogu lehe paigutust
- **`row`** — üks rida ruudustikus
- **`col`** — veerg rea sees; mitu `col` elementi ühe `row` sees jagavad ruumi automaatselt võrdselt

### Skeem

```
container
  └── row
        ├── col  (nt tekst)
        └── col  (nt pilt)
```

### Koodinäide (projektist, `frontend/src/views/HomeView.vue`)

```html
<div class="container text-center">
  <div class="row">
    <div class="col">See on meie äge bank! :)</div>
    <div class="col">
      <img src="..." class="img-thumbnail" alt="..." />
    </div>
  </div>
</div>
```

Bootstrap pakub ka valmis pildiklasse (nt `img-thumbnail`, `img-fluid`) — nii ei pea ise raame ja varjundeid CSS-iga programmeerima.

### Päriselu analoogia

Bootstrap grid on nagu ajalehe küljendus — leht on jagatud veergudeks juba enne, kui hakkad sisu paigutama, nii et sul on kohe struktuur olemas, kuhu teksti ja pilte "valada".

## Git töövoog: Master kaitstud haru ja merge suund — `2:41:37` {#git-merge}

### Selgitus

Reaalses arenduses on `master` (või `main`) haru tavaliselt **kaitstud (protected)** — otse sinna ei saa muudatusi teha (merge'ida). Muudatus peab kõigepealt läbima ülevaatuse (code review), enne kui see lubatakse masterisse.

**Tähtis reegel merge'imisel:** pead olema (checkout'itud) sellel harul, **kuhu töö peab minema**, mitte harul, kust töö tuleb.

- **`Merge feb4 into master`** (olles master'il) — ÕIGE suund, kui tahad valmis tööd Masterisse viia
- **`Merge master into feb4`** (olles feb4-l) — samuti kasulik ja täiesti ohutu tegevus — see toob Master'i uuendused sinu haru sisse, aga **ei kustuta kunagi sinu tehtud tööd**

### Skeem

```
Master (kaitstud haru)
   ^
   | merge feb4 into master (õige suund valmis töö jaoks)
   |
feb4 (sinu arendusharu)
   ^
   | merge master into feb4 (ohutu — toob uuendused sisse, ei kustuta sinu tööd)
```

### Päriselu analoogia

Merge suund on nagu vee valamine anumasse — sa valad *feb4* sisu *masterisse*, mitte vastupidi. Kui proovid valada tühja anumasse (master into feb4, kui masteris pole midagi uut), ei juhtu midagi — "already up to date".

## Git hügieen: harude kustutamine pärast merge't — `2:49:45` {#git-hugieen}

### Selgitus

Kui haru töö on edukalt Masterisse viidud (merge'itud), tuleks see **haru ära kustutada**. Levinud algaja hirm: "äkki läheb veel vaja" — see on asjatu, sest:

- Kogu ajaloo ja versioonid **jäävad Masterisse alles** ka pärast haru kustutamist
- Kui ikkagi vajad muudatust, saad alati luua **uue haru samast Masterist**, kasutades sama tiketinumbrit
- Vanade harude kuhjumine tekitab "prügihunniku" (remote'is sadu-tuhandeid vanu harusid), mis raskendab teistel orienteerumist ja tekitab segadust
- Seda nimetatakse **"Git hügieeniks"** — puhas repo on kõigi ühine huvi

### Päriselu analoogia

Vana haru alles hoidmine "juhuks kui vaja läheb" on nagu kõigi vanade kviitungite hoidmine rahakotis "juhuks kui vaja läheb" — enamik neist ei lähe kunagi vaja, aga nad teevad rahakoti (repo) ülevaatlikkuse hullemaks kõigi jaoks.
