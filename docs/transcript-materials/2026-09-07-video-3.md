## BEB-5 – Login task kirjeldus — `0:06:02` {#beb-5-login-task-kirjeldus}

### Selgitus

Esimene päris arendustask on **Login** (sisselogimine). Andmebaasi tabelitest mängivad rolli `user` ja `role`. Task'i kirjeldus:

- Frontend saadab backendile **HTTP POST** sõnumi koos `username` ja `password` väljadega.
- Kui andmebaasist leitakse vastava `username`/`password` kombinatsiooniga kasutaja, kelle `status` on `'A'` (aktiivne), tagastab teenus **HTTP 200** ja vastuse, kus on `roleName`.
- Kui sobivat kasutajat ei leitud, tagastab teenus **HTTP 403** ja veaobjekti, kus on `error` (String) ja `errorCode` (String).

### Skeem

```
Frontend                          Backend
   │  POST /api/login                │
   │  { username, password }         │
   ├─────────────────────────────────►
   │                                  │  Otsib user tabelist
   │                                  │  vastava username/password'iga
   │                                  │  aktiivse (status='A') kasutaja
   │                                  │
   │  200 OK { roleName }             │  ← leiti
   │◄─────────────────────────────────┤
   │           VÕI                    │
   │  403 { error, errorCode }        │  ← ei leitud
   │◄─────────────────────────────────┤
```

### Päriselu analoogia

See on nagu turvavalve hoone sissepääsu juures — kui näitad kehtivat kaardit (õige kasutajanimi + parool + aktiivne staatus), lubatakse sisse ja öeldakse, mis tasandile ligipääs on (roll). Kui kaart ei kehti, öeldakse "sisenemine keelatud" koos põhjuskoodiga.

## Error koodid vs tekstisõnumid — `0:07:31` {#error-koodid-vs-tekstisonumid}

### Selgitus

Vearesponsis peaks tagastama **veakoodi (errorCode)**, mitte lihtsalt tekstilist veasõnumit, millel süsteem otsustusi teeb. Tekst võib olenevalt keelest/kontekstist muutuda, aga koodi järgi on süsteemidel palju kindlam ja usaldusväärsem otsuseid langetada.

Selle jaoks on Java's soovitatav kasutada **enum** tüüpi — kokkulepitud, piiratud hulk veakoode.

### Koodinäide

```java
public enum ErrorResponse {
    USER_NOT_FOUND("INCORRECT_USERNAME_OR_PASSWORD"),
    // ... teised veakoodid
    ;

    private final String errorCode;

    ErrorResponse(String errorCode) {
        this.errorCode = errorCode;
    }
}
```

### Anekdoot: miks empaatia?

Õpetaja tõi näite huntide karjast — kui üks hunt hakkab haigutama (väsimuse märk), hakkavad ka teised hundid haigutama, kuna karja ellujäämiseks on kasulik, et kõik oleksid ühtemoodi "häirekella kuulnud". Sarnaselt soovivad tarkvarasüsteemid teineteisele edastada **standardiseeritud, üheselt mõistetavaid signaale** (veakoodid), mitte suvalisi tekstilauseid, mille tähendus võib muutuda.

### Reegel

> Süsteemidevaheline suhtlus peaks toimuma **kokkulepitud koodide/staatuste** kaudu, mitte vabas vormis tekstiga — tekst võib olla mis keeles tahes, kood jääb alati samaks ja masinloetavaks.

## SQL skriptid: reset, create, import — `0:18:21` {#sql-skriptid-reset-create-import}

### Selgitus

Projektis on kolm SQL skripti, mida käivitatakse **järjekorras**, et andmebaas puhtast lehest üles seada:

1. **`1_reset_database.sql`** — kustutab olemasoleva `bank` skeema (kõik tabelid koos) ja loob selle uuesti tühjana.
2. **`2_create.sql`** — loob kõik tabelid (struktuur, veerud, kitsendused).
3. **`3_import.sql`** — lisab algandmed (`INSERT` laused).

### Koodinäide (`docs/database/1_reset_database.sql`)

```sql
-- Kustutab bank schema (mis põhimõtteliselt kustutab kõik tabelid)
DROP SCHEMA IF EXISTS bank CASCADE;
-- Loob uue bank schema koos vajalike õigustega
CREATE SCHEMA bank
    -- taastab vajalikud andmebaasi õigused
    GRANT ALL ON SCHEMA bank TO postgres;
GRANT ALL ON SCHEMA bank TO PUBLIC;
```

### Koodinäide (`docs/database/3_import.sql`, väljavõte)

```sql
INSERT INTO bank.city (id, name) VALUES (default, 'Pärnu');
INSERT INTO bank.city (id, name) VALUES (default, 'Tallinn');
INSERT INTO bank.city (id, name) VALUES (default, 'Tartu');
```

### Kasutamine

Kõiki kolme skripti saab IntelliJ-is käivitada korraga ("Run"), luues neist ühise "compound" run-konfiguratsiooni (nt nimega `reset database`), mis lihtsustab andmebaasi taastamist iga kord, kui testimise käigus on andmed segamini läinud.

### Päriselu analoogia

Need kolm skripti on nagu "vabrikuseadete taastamine" nutiseadmel: kustutab kõik olemasoleva (1), paigaldab tühja süsteemi (2) ja laeb esialgsed näidisandmed (3) — nii saab alati kiirelt tagasi minna tuttavasse algseisu.

## Andmebaasi struktuur: database → schema → table — `0:26:11` {#andmebaasi-struktuur-database-schema-table}

### Selgitus

PostgreSQL andmebaasi struktuur on **hierarhiline**:

```
Andmebaas (database)          ← nt "postgres" või "vali_it"
   └── Skeem (schema)          ← nt "bank" (eraldi "liivakast")
         └── Tabel (table)     ← nt "city", "user", "role"
```

**Skeem** on nagu eraldi kaust andmebaasi sees — see võimaldab mitmel projektil/rakendusel eksisteerida **samas andmebaasis**, ilma et tabelinimede kokkulangevus (nt kaks eri projekti, mõlemal tabel `user`) probleeme tekitaks. Kuna kõik selle kursuse tabelid elavad `bank` skeemas, ei lähe need kunagi kokku teiste projektide (nt õpilase enda hobiprojekti) tabelitega, mis võivad elada eri skeemas.

### Oluline

Kõik, mis toimub sinu **lokaalses** andmebaasis (lisatud read, testandmed jms), on ainult sinu enda arvutis — see ei jõua kunagi "maagiliselt" tiimikaaslaste juurde. Ainuke viis andmeid jagada on **SQL skriptid, mis on git-i commititud** (nt `3_import.sql`) — kõik, kes need skriptid käivitavad, saavad samad algandmed.

### Päriselu analoogia

Andmebaas on nagu suur hoone, skeem on nagu korrus/tiib selles hoones, ja tabel on nagu konkreetne tuba. Erinevad tiivad (skeemad) võivad kasutada sama numbriga tuba, ilma et see segadust tekitaks.

## CREATE TABLE süntaks — `0:35:01` {#create-table-syntaks}

### Selgitus

SQL (Structured Query Language) on suhtlemiskeel andmebaasidega — palju maalähedasem kui Java, aga sellel on ka oma reeglid.

### Koodinäide (`docs/database/2_create.sql`)

```sql
CREATE TABLE city (
    id serial NOT NULL,
    name varchar(255) NOT NULL,
    CONSTRAINT city_pk PRIMARY KEY (id)
);
```

### Selgitus reas

```
CREATE TABLE city (           ← loo tabel nimega "city"
    id serial NOT NULL,       ← veerg "id", automaatselt kasvav number, kohustuslik
    name varchar(255) NOT NULL, ← veerg "name", kuni 255 tähemärki, kohustuslik
    CONSTRAINT city_pk PRIMARY KEY (id) ← "id" on primaarvõti (unikaalne identifikaator)
);
```

- **`serial`** — PostgreSQL'i tüüp, mis loob automaatselt kasvava täisarvu (kasutab sisemiselt "sequence counter'it").
- **`varchar(255)`** — muutuva pikkusega tekstiväli, maksimaalselt 255 tähemärki.
- **`NOT NULL`** — see veerg ei tohi olla tühi.
- **`PRIMARY KEY`** — märgib veeru unikaalseks identifikaatoriks, mille abil saab leida konkreetse rea.

### Päriselu analoogia

`CREATE TABLE` on nagu tabeli joonistamine tühjale paberile — määrad kohe ette, mitu veergu on, mis tüüpi andmed igasse veergu sobivad, ja millised reeglid (nt "ei tohi olla tühi") kehtivad.

## Sequence counter — automaatne ID — `0:38:28` {#sequence-counter-automaatne-id}

### Selgitus

`id serial` veeru taha luuakse automaatselt eraldi **loendur (sequence)**, mis annab igale uuele reale automaatselt järgmise vaba numbri. Kirjutades `INSERT INTO city (id, name) VALUES (default, 'Pärnu')`, ütled ID-le sõna **`default`** — see tähendab "lase loendur ise otsustada, mis number siia läheb".

### Oluline reegel

> **Ära pane ID väärtusi käsitsi ise!** Kui käsitsi kirjutad ID väärtuseks nt `1`, ei tea loendur sellest — ta jätkab ikkagi loendamist eelmisest punktist. See võib tekitada olukorra, kus loendur pakub hiljem välja väärtuse, mis on juba käsitsi kasutusse võetud → **unique constraint viga**.

### Skeem

```
INSERT INTO city (id, name) VALUES (default, 'Pärnu');
                    │
                    ▼
        Loendur annab järgmise vaba väärtuse (nt 1)
                    │
                    ▼
        Rida salvestatakse: id=1, name='Pärnu'

INSERT INTO city (id, name) VALUES (default, 'Tallinn');
                    │
                    ▼
        Loendur annab järgmise vaba väärtuse (2, EI 1!)
```

Kui käsitsi pandaks `id=1` juba varem, ja loendur ka ise proovib väärtust `1` anda, tekib konflikt (kaks rida ei tohi jagada sama ID-d).

### Päriselu analoogia

Sequence counter on nagu järjekorranumbrite masin pangas või kliinikus — kui sa võtaksid endale käsitsi numbri "5" ilma masinast tõmbamata, võib masin ikkagi mõne aja pärast anda kellelegi teisele täpselt sama numbri "5", kuna ta ei teadnud, et see number oli juba käiku läinud.

## CRUD baaskäsud: INSERT, SELECT, UPDATE, DELETE — `0:49:05` {#crud-baaskasud}

### Selgitus

Neli põhitoimingut, mida andmebaasiga saab teha, moodustavad akronüümi **CRUD**:

| Toiming | SQL käsk | Tähendus |
|---|---|---|
| **C**reate | `INSERT` | uue rea lisamine |
| **R**ead | `SELECT` | andmete lugemine |
| **U**pdate | `UPDATE` | olemasoleva rea muutmine |


### Päriselu analoogia

CRUD on nagu neli baastoimingut, mida saad teha kirjaliku päevikuga: **lisada** uus sissekanne, **lugeda** olemasolevaid sissekandeid, **parandada** vana sissekanne, või **kustutada** sissekanne täielikult.

## Relatsiooniline andmebaas: primary key ja foreign key — `0:53:20` {#relatsiooniline-andmebaas-primary-key-ja-foreign-key}

### Selgitus

**Primary key** (primaarvõti, IntelliJ-is kollane võtmeikoon) on veerg, mis identifitseerib **unikaalselt** iga rea tabelis (nt `city.id`). **Foreign key** (võõrvõti, sinine võtmeikoon) on veerg, mis **viitab** teise tabeli primaarvõtmele — see loob seose kahe tabeli vahel.

### Koodinäide (`docs/database/2_create.sql`)

```sql
CREATE TABLE role (
    id serial NOT NULL,
    name varchar(255) NOT NULL,
    CONSTRAINT role_pk PRIMARY KEY (id)      -- primaarvõti
);

CREATE TABLE "user" (
    id serial NOT NULL,
    role_id int NOT NULL,                     -- võõrvõti (viitab role.id-le)
    username varchar(255) NOT NULL,
    password varchar(255) NOT NULL,
    status char(1) NOT NULL,
    CONSTRAINT user_pk PRIMARY KEY (id)
);
```

### Skeem

```
role (vanemtabel)              user (lapsetabel)
┌───────────────┐              ┌──────────────────────┐
│ id (PK) 🟡      │◄──────────── │ role_id (FK) 🔵        │
│ name             │              │ username               │
└───────────────┘              │ password               │
                                │ status                 │
                                └──────────────────────┘
```

### Päriselu analoogia

Primary key on nagu isikukood — igal inimesel unikaalne, ei kordu kellelgi teisel. Foreign key on nagu viide isikukoodile mõnel teisel dokumendil (nt "lapse sünnitunnistusel on kirjas ema isikukood") — see loob seose kahe registrikande vahel.

## JOIN — kahe tabeli ühendamine — `0:55:35` {#join-kahe-tabeli-uhendamine}

### Selgitus

Kuna relatsioonilises andmebaasis hoitakse seotud andmeid **eraldi tabelites**, on vaja viis, kuidas need "koos" küsida — selleks on **`JOIN`**. `JOIN` ühendab kaks tabelit ühise võtme (primary key ↔ foreign key seos) alusel, moodustades ühe suurema, kombineeritud tulemuse.

### Koodinäide

```sql
SELECT u.id, r.name
FROM bank."user" u
JOIN bank.role r ON r.id = u.role_id;
```

### Selgitus reas

```
FROM bank."user" u        ← võta user tabel, hüüdnimeks "u"
JOIN bank.role r           ← liida role tabel, hüüdnimeks "r"
    ON r.id = u.role_id    ← ühenduspunkt: role.id peab võrduma user.role_id-ga
SELECT u.id, r.name        ← näita user'i id ja role'i nime koos
```

Enne `JOIN`-i tegemist tagastab lihtne `SELECT * FROM bank."user"` ainult `role_id` numbrit (nt `1` või `2`) — kasutajale arusaadava rolli nime (nt "Admin", "Customer") saamiseks on vajalik `role` tabeliga ühendamine.

### Skeem

```
user tabel                role tabel
┌────┬─────────┐          ┌────┬──────────┐
│ id │ role_id │          │ id │ name     │
├────┼─────────┤          ├────┼──────────┤
│ 1  │ 2       │  ──JOIN──►│ 2  │ Customer │
│ 2  │ 1       │          │ 1  │ Admin    │
└────┴─────────┘          └────┴──────────┘
        │
        ▼ tulemus pärast JOIN-i
┌────┬──────────┐
│ id │ name     │
├────┼──────────┤
│ 1  │ Customer │
│ 2  │ Admin    │
└────┴──────────┘
```

### Päriselu analoogia

`JOIN` on nagu kahe eraldi kartoteegi kõrvutamine kontoris — üks kartoteek hoiab töötajate isikuandmeid ja viitab osakonna numbrile, teine kartoteek hoiab osakondade nimesid numbri järgi. Et saada "töötaja + tema osakonna nimi" ühel kaardil, tuleb need kaks kartoteeki numbri (võtme) järgi kõrvutada.
