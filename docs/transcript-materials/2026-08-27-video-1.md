## If-lause: kuidas otsuseid tehakse koodis — `0:00:47` {#if-lause}

### Selgitus

**If-lause** on kõige põhilisem tööriist otsuste tegemiseks koodis, sõltumata programmeerimiskeelest või raamistikust. See on nagu **teelahk** — kas minna ühes suunas või teises.

If-lause sulgudes peab olema midagi, mis **rehkendub tõeseks (`true`) või vääraks (`false`)** — see peab olema võrdlus või võrrand, mitte lihtsalt suvaline väärtus.

```javascript
if (vanus >= 18) {
    // see koodiplokk käivitub AINULT siis, kui tingimus on true
}
```

`else` lisab teise variandi — mida teha, kui tingimus **ei** kehti:

```javascript
if (uusEmailTuli) {
    saadaTeavitus();
} else {
    // ei tehta midagi
}
```

### Päriselu analoogia

If-lause on nagu teelahku juures olev viit: "kui oled täiskasvanud, mine paremale; kui mitte, mine vasakule." Programm "loeb" seda viita ja liigub vastavalt tingimuse tõesusele ühte või teise suunda.

## AND ja OR koodi tasandil — `0:06:06` {#and-or}

### Selgitus

Kui if-lauses on vaja kontrollida **mitut tingimust korraga**, kasutatakse AND-i ja OR-it.

**AND** — mõlemad tingimused peavad olema tõesed:
```javascript
if (onJuhiluba && onTaiskasvanu) {
    // mõlemad peavad kehtima
}
```

**OR** — piisab, kui üks tingimustest on tõene:
```javascript
if (onJuhiluba || onIdKaart) {
    // piisab ühest
}
```

**Tähtis optimeerimise nüanss:** programm ei kontrolli AND-i puhul teist poolt, kui esimene pool on juba väär (`false`) — kogu tulemus on niikuinii `false`. Samamoodi OR-i puhul, kui esimene pool on juba tõene (`true`), ei vaadata teist poolt üldse — see on põhjus, miks järjekord AND/OR lausetes võib jõudluse mõttes mängida rolli.

### Skeem

```
AND: A && B
  Kui A on false --> tulemus on kohe false, B-d EI kontrollita
  Kui A on true  --> peab vaatama ka B-d

OR: A || B
  Kui A on true  --> tulemus on kohe true, B-d EI kontrollita
  Kui A on false --> peab vaatama ka B-d
```

### Päriselu analoogia

See sarnaneb Excelis kolme AND-tingimusega valemile: "kui oled täiskasvanud JA sul on juhiluba JA oled sündinud pärast teatud aastat" — kõik kolm peavad kehtima. OR-i puhul piisab ainult ühest sõnast reageerimiseks — nagu turvakontrollis, kus piisab, et sul on kas ID-kaart VÕI pass.

## `==` vs `===` JavaScriptis — `0:14:43` {#vordlemine}

### Selgitus

JavaScriptis on kaks võrdlusviisi:

- **`==`** — võrdleb väärtusi, aga **teisendab tüübid automaatselt sarnaseks** enne võrdlemist
- **`===`** — **tüübikindel** võrdlus: nii väärtus kui tüüp peavad ühtima

```javascript
10 == "10"    // true — JavaScript teisendab automaatselt
10 === "10"   // false — number ja string ei ole sama tüüpi
```

**Miks see on tähtis:** kui võtad väärtuse `input` kastist (nt vanuse), on see **alati string**, isegi kui `input` tüüp on `number`. Kui sa unustad selle numbriks teisendada ja võrdled `===` abil programmis oleva numbriga, saad ootamatu `false` tulemuse, kuigi väärtused "tunduvad" samad.

Java on sarnaselt tüübikindel — seal ei saagi erinevat tüüpi asju otse omavahel võrrelda, kompilaator lihtsalt keeldub sellist koodi kompileerimast.

### Päriselu analoogia

`==` on nagu tuttav, kes ütleb "kümme on kümme, ükskõik kas see on kirjutatud numbrina või sõnadega". `===` on nagu range ametnik, kes nõuab, et vorm oleks täpselt õiges formaadis — number peab olema number, mitte tekst, mis "näeb numbri moodi välja".

## Uue vaate loomine: samm-sammult töövoog — `0:34:58` {#uus-vaade}

### Selgitus

Iga uue Vue vaate lisamise standardsamm on:
1. **Loo uus haru** Master'ilt (või õppekeskkonnas "õpetaja" harult)
2. **Loo uus vaatekomponent** `views/` kaustas — vaated, mis reageerivad URL-idele, peaksid alati olema selles kaustas
3. **Lisa route** `router/index.js` faili — seosta URL rada komponendiga
4. **Lisa link navigatsioonimenüüsse**, kui kasutaja peab saama sinna klõpsata

### Koodinäide (projektist, `frontend/src/router/index.js`)

```javascript
import { createRouter, createWebHistory } from 'vue-router'
import HomeView from '@/views/HomeView.vue'
import ErrorView from '@/views/ErrorView.vue'
import AtmsView from '@/views/AtmsView.vue'

const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    { path: '/', name: 'homeRoute', component: HomeView },
    { path: '/error', name: 'errorRoute', component: ErrorView },
    { path: '/atms', name: 'atmsRoute', component: AtmsView },
  ],
})

export default router
```

### Vue komponendi struktuur (Options API)

```html
<template>
  <div>Sisu siia</div>
</template>

<script>
export default {
    name: 'ErrorView'
}
</script>
```

**Tähtis konventsioon:** komponendi `name` väli peaks olema täpselt sama, mis faili nimi (ilma `.vue` laiendita) — see on tähtis, kui hiljem komponente teistest kohtadest välja kutsutakse.

### Koodinäide (projektist, `frontend/src/App.vue`)

```html
<template>
  <nav class="navbar navbar-expand-lg navbar-dark bg-dark px-3 mb-3">
    <RouterLink class="navbar-brand" to="/">Bank</RouterLink>
    <div class="navbar-nav">
      <RouterLink class="nav-link" to="/">Kodu</RouterLink>
      <RouterLink class="nav-link" to="/atms">Pangaautomaadid</RouterLink>
    </div>
  </nav>

  <RouterView />
</template>
```

## Code Review kultuur ja miks see on väärtuslik — `1:19:37` {#code-review}

### Selgitus

**Code Review** on protsess, kus keegi teine vaatab sinu kirjutatud koodi üle enne, kui see jõuab põhiharusse (Master). Reviewer ei testi koodi funktsionaalselt — ta vaatab **koodi ennast**: kas struktuur on selge, kas nimed on head, kas lähenemine on jätkusuutlik.

**Tähtis suhtumine:** Code Review kommentaare ei tohi kunagi võtta isiklikult. See on koht, kus **kogenum inimene aitab sul areneda** — see, et keegi paneb oma aega sinu töö parandamiseks, on väärtuslik, mitte solvav.

**Praktiline nõuanne kordumise vältimiseks:** hea harjumus on pidada endale märkmeid Code Review'l saadud tagasisidest (nt eraldi märkmikus), et tulevastes review'des ei korduks samad vead — reviewer'i jaoks on väga ebamugav, kui ta peab pidevalt sama asja mitu korda korrigeerima.

### Päriselu analoogia

Code Review on nagu mentori parandused inseneri jooniste peal — mitte kriitika inimese vastu, vaid tööriist, mis aitab tööl paremaks saada enne, kui see läheb ehitusse (production).

## Pull Request töövoog Git-is — `1:29:03` {#pull-request}

### Selgitus

**Pull Request (PR)** on formaalne "palve" viia arendusharu (nt `feb5`) muudatused Master'isse. Tegelikus töökeskkonnas ei saa arendaja lihtsalt otse Masterisse merge'ida — see toimub läbi PR platvormi (nt GitHub), kus:

1. Arendaja teeb PR-i, valides suuna (nt `feb5` → `master`)
2. PR näitab kõiki muudetud faile ja muudatusi (diff)
3. Määratakse **reviewer** (kollaboraator, kes peab koodi üle vaatama)
4. Reviewer saab jätta **koodi sisse kommentaare** otse konkreetsete ridade juurde
5. Arendaja teeb muudatused ja märgib kommentaari **lahendatuks (resolve)**
6. Kui kõik on korras, ilmub nähtavale **"Merge Pull Request" nupp**

### Skeem

```
Arendaja haru (feb5) --> PR luuakse --> Reviewer vaatab üle --> Kommentaarid
                                              |
                              Arendaja parandab, resolve't kommentaarid
                                              |
                                    Merge nupp muutub aktiivseks
                                              |
                                         Master uuendub
```

### Miks see nii on üles ehitatud

See kaitseb Master haru: keegi ei saa kogemata (või pahatahtlikult) viga sisse tuua ilma, et keegi teine seda üle vaataks. See on eriti tähtis pangandussüsteemides, kus vead võivad olla väga kulukad.

### Päriselu analoogia

Pull Request on nagu ehitusluba — enne kui saad ehitama hakata (koodi Masterisse viia), peab keegi pädev üle vaatama plaanid ja andma loa.

## Squash merge vs tavaline merge — `1:45:47` {#squash-merge}

### Selgitus

Kui PR merge'itakse, on valikuid, kuidas kommitid Master'isse jõuavad:

- **Tavaline merge** — kõik üksikud kommitid (nt kolm eraldi tööetappi) jäävad Master ajalukku alles eraldi kommititena
- **Squash and merge** — kõik kommitid **lükatakse kokku üheks** kommitiks enne Masterisse liikumist

Õpetaja eelistus: squash merge, sest Master ajaloos pole tavaliselt vaja näha iga väikest vahepealset sammu (nt "WIP 1", "WIP 2", "parandasin kirjaviga") — piisab ühest tervikliku funktsionaalsuse kommitist.

### Päriselu analoogia

Squash merge on nagu esitluse jaoks kokkuvõtte kirjutamine — protsessi käigus tehtud mustandid ja parandused (üksikud kommitid) ei pea kõik lõplikku dokumenti (Master ajalugu) jõudma, piisab lõplikust versioonist.

## Git hügieen: harude kustutamine pärast merge't — `1:49:03` {#git-hugieen-2}

### Selgitus

Kui haru töö on Masterisse viidud, tuleks see **haru kustutada** nii lokaalselt kui remote'ist (pilvest). Git tööriistad (nt GitHub, IntelliJ) pakuvad seda tavaliselt automaatselt PR merge'imise ajal ("Delete branch?").

**Miks see on ohutu:** kogu tehtud töö on juba Master'is olemas — haru kustutamine ei kaota mitte midagi. Kui tulevikus vaja, saab luua uue haru samast punktist sama tiketinumbriga.

**Miks harude kuhjumine on halb:** suurtes projektides (nt tuhandete tiketitega) tekitab lahtiste harude kuhjumine visuaalset segadust ja raskendab teistel orienteerumist — kes ikka veel selle kallal töötab, mis on aegunud.

## Merge suund: "kummal oksal pead istuma" — `2:10:12` {#merge-suund}

### Selgitus

See on üks tähtsamaid IntelliJ Git-menüü nüansse. Kui teed parem klõpsu harul ja valid Merge, on kaks võimalust:

- **`Merge 'feature' into 'current'`** — toob **teise haru** (feature) muudatused sinu praegusesse harusse
- **`Pull into 'current' Using Merge`** — uuendab **sinu enda praegust harut** selle remote-vastest (fetch + merge), Karli/feature'i haruga pole pistmist

**Rusikareegel:** kui tahad tuua kellegi teise (või teise haru) tööd enda harusse, pead olema **checkout'itud sellel harul, kuhu töö peab minema**. Sa ei saa "lükata" tööd teise harusse, milles sa parasjagu ei viibi — saad ainult **tõmmata** teisest harust enda praegusesse harusse.

### Skeem

```
Sa oled harul: OPETAJA
Paremklõps harul: KARLI-FEB-5

"Merge KARLI-FEB-5 into OPETAJA"  --> toob Karli töö SINU harusse (õige, kui tahad Karli tööd)
"Pull into OPETAJA Using Merge"   --> uuendab OPETAJA-t selle OMA remote-vastest, Karliga pole seost
```

### Päriselu analoogia

See on nagu kaks erinevat kirja postkasti panemist. "Merge X into Y" on nagu konkreetse kirja (X) toomine konkreetsesse postkasti (Y) — täpne, sihitud tegevus. "Pull using merge" on nagu oma enda postkasti tühjendamine — kontrollid ainult oma kirju, mitte kellegi teise omi.

## Andmebaasi mudel: User ja Role tabelid — `2:44:29` {#andmebaasi-mudel}

### Selgitus

**Relatsiooniline andmebaas** koosneb tabelitest, mis on omavahel seotud numbrite (ID-de) kaudu, mitte korduva tekstiga. Näide: kasutaja sisselogimise süsteemis on tavaliselt kaks eraldi tabelit:

- **`role`** tabel — sisaldab kõiki võimalikke rolle (`id`, `name`: admin, customer, moderaator)
- **`user`** tabel — sisaldab kasutajaid (`username`, `password`, `status`, ja **`role_id`**, mis viitab `role` tabeli `id`-le)

### Skeem

```
role tabel:              user tabel:
+----+----------+        +----+----------+----------+---------+
| id | name     |        | id | username | password | role_id |
+----+----------+        +----+----------+----------+---------+
| 1  | admin    |        | 1  | rain     | ...      | 2       |
| 2  | customer |        | 2  | admin    | ...      | 1       |
+----+----------+        +----+----------+----------+---------+
                                                         ^
                                              viitab role.id-le
```

### Miks numbrite kaudu, mitte tekstiga

Kui kirjutaksid iga kasutaja juurde teksti "customer" otse (mitte number, mis viitab role tabelile), tekiks **andmete liiasus (redundancy)** — sama sõna korduks tuhandeid kordi, mis raiskab ruumi ja teeb otsingu aeglasemaks. Andmebaasidele on numbrite võrdlemine palju kiirem kui pikkade tekstide tähthaaval võrdlemine.

### Päriselu analoogia

See on nagu pileti number kontserdil versus terve nimekirja kirjutamine iga kord uuesti — kordumatu number viitab kiiresti õigele reale, samas kui kogu teksti (nt linna nime) korduv väljakirjutamine oleks aeglane ja ruumi raiskav.

## Auto-increment ID-d ja andmete terviklikkus — `2:52:20` {#auto-increment}

### Selgitus

Iga uue rea lisamisel andmebaasi tabelisse antakse talle automaatselt **järgmine vaba unikaalne number** (nn auto-increment, tehniliselt sarnane operaatorile `++`, mis suurendab loendurit ühe võrra iga uue kirje kohta).

**Tähtis printsiip — andmete terviklikkus (data integrity):**
- Neid ID-sid **ei taaskasutata kunagi**, isegi kui vahepealne rida kustutatakse
- Ei saa viidata (`role_id`-ga) väärtusele, mida `role` tabelis olemas ei ole — süsteem lihtsalt ei luba seda

### Koodinäide (kontseptuaalne, ID genereerimise loogika)

```javascript
let nextId = 0;

function addRole(name) {
    nextId++;               // suurenda loendurit
    return { id: nextId, name: name };
}

addRole("admin");     // { id: 1, name: "admin" }
addRole("customer");  // { id: 2, name: "customer" }
// isegi kui id 2 kustutatakse, järgmine roll saab ID 3, mitte 2 uuesti
```

### Päriselu analoogia

See on nagu isikukoodide süsteem — kord antud number ei lähe kunagi teisele inimesele uuesti, isegi kui esimene inimene sureb (rida kustutatakse).

## API leping (contract) ja Stoplight — `3:05:53` {#api-leping}

### Selgitus

Enne kui frontend ja backend on mõlemad valmis, on vaja kokkulepet (**contract**), mis kirjeldab:
- Milliseid teenuseid (endpoint'e) backend pakub
- Millise URL-i ja meetodi (GET/POST) kaudu neid kutsutakse
- Mida frontend peab saatma (request body)
- Mida backend vastab (response), nii õnnestumise kui vea korral

**Stoplight** on tööriist, mis lubab seda lepingut **kirja panna JSON formaadis** (standardil OpenAPI baseeruv) ja isegi **simuleerida (mockida)** backend'i vastuseid, ilma et päris backend server oleks veel olemas. See lubab frontend'i arendust alustada juba enne, kui backend on valmis.

### Skeem

```
Frontend (arendatakse esimesena) --> Stoplight (mock server, simuleerib backend'i vastuseid)
                                          |
                    (hiljem, kui backend valmis:)
                                          v
Frontend --> päris Backend server (URL vahetatakse konfiguratsioonis)
```

### Koodinäide (projektist, `frontend` konfiguratsioon — kontseptuaalne)

```javascript
// Enne backend'i valmimist:
const API_BASE = 'https://stoplight.io/mocks/...'  // mock server

// Pärast backend'i valmimist, lihtsalt vahetatakse rida:
const API_BASE = 'http://localhost:8080'  // päris backend
```

### Päriselu analoogia

API leping on nagu ehitusplaan, mille arhitekt ja sisearhitekt mõlemad kokku lepivad enne ehituse algust — sisearhitekt (frontend) saab hakata mööblit planeerima juba enne, kui hoone (backend) on valmis, sest mõlemad teavad juba täpselt, millised on ruumide mõõdud (API leping).

## Brauseri Session Storage ja Local Storage — `3:17:49` {#storage}

### Selgitus

Brauseril on sisseehitatud kohad, kuhu saab ajutiselt salvestada infot (nt kes on sisse loginud kasutaja):

| | Session Storage | Local Storage |
|---|---|---|
| Kestvus | Kaob, kui vahekaart/aken suletakse | Säilib "igavesti" (kuni käsitsi kustutatakse) |
| Kasutusjuht | Ajutine info (nt praeguse sessiooni kasutaja ID) | Püsivam info |

Mõlemad töötavad **võti-väärtus** (key-value) põhimõttel — sarnaselt JavaScripti objekti literaalile.

### Koodinäide (kontseptuaalne)

```javascript
// Sisselogimise järel salvestame kasutaja info:
sessionStorage.setItem('userId', '10');
sessionStorage.setItem('role', 'admin');

// Teisel vaatel saame selle kätte:
let userId = sessionStorage.getItem('userId');
```

### Miks see on vajalik

Kui kasutaja liigub ühelt vaatelt (leheküljelt) teisele SPA-s, kaovad kõik muutujad ja andmed, mis olid eelmise vaate mälus — **standardina läheb kõik "unustuse hõlma"**. Kui on vaja teada, kes kasutaja on ka pärast vaate vahetust (nt näidata "Logi välja" nuppu ainult sisselogitud kasutajale), tuleb see info salvestada Session/Local Storage'i, kust seda saab hiljem programmiliselt uuesti kätte küsida.

### Päriselu analoogia

Session Storage on nagu käekott, mida kannad kaasas ainult ühe päeva jooksul — õhtul (session lõppedes) tühjeneb see. Local Storage on nagu kodune sahtel — jääb sinna, kuni sa ise midagi sealt eemaldad.
