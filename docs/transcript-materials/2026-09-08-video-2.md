## Kontroller ainult delegeerib – äriloogikat siia ei kirjutata — `0:01:17` {#kontroller-delegeerib}

### Selgitus

Kõige tähtsam reegel: **`@RestController`-klassi meetodisse ei kirjutata äriloogikat**. Mitte `if`-e, mitte andmete teisendusi, mitte arvutusi — mitte midagi sellist.

Ainuke asi, mida kontroller teeb, on **delegeerimine** (ülesande edasiandmine): ta võtab sõnumi vastu ja kutsub kohe välja järgmise kihi (service) meetodi.

```
Internetist tuleb sõnum
        │
        ▼
┌─────────────────┐   "ma ei tee ise midagi,
│  LoginController│    annan ülesande edasi"
└────────┬────────┘
         │  loginService.loginUser(loginRequest)
         ▼
┌─────────────────┐   siin toimub päris töö
│   LoginService  │
└─────────────────┘
```

### Miks nii?

Kui äriloogika on hajutatud kontrollerite vahele, muutub kood kiiresti loetamatuks ja seda on raske testida. Kihiline struktuur (kontroller / service / repository) hoiab iga faili ühe selge ülesandega.

## LoginService klass, `service` pakett ja Java nimetamisreeglid — `0:01:48` {#service-klass}

### Selgitus

Videos rõhutatakse mitut reeglit:

| Reegel | Näide |
|---|---|

## `@Service` annotatsioon ja bean-objektid — `0:03:43` {#service-annotatsioon}

### Selgitus

`LoginService` on **teenustüüpi klass** ja me soovime, et Spring teeks temast **bean-objekti** ("uba" — objekt, mille loomise ja eluea eest hoolitseb Spring ise, mitte meie).

Selleks paneme klassi kohale annotatsiooni **`@Service`**. See annab Springi konteinerile ("laevakonteiner, mille sees on objektid nagu kaubad") märku: *"sellest klassist tee bean"*.

```
┌──────────────── Spring Container ────────────────┐
│                                                  │
│   @Service                @RestController        │
│   ┌────────────┐          ┌────────────────┐     │
│   │LoginService│◀─────────│ LoginController│     │
│   │  (bean)    │          │    (bean)      │     │
│   └────────────┘          └────────────────┘     │
│                                                  │
│   Spring loob need ise, ühe korra, õigel hetkel  │
└──────────────────────────────────────────────────┘
```

### Tähelepanek

`@Service`, `@RestController`, `@Repository`, `@Component` on kõik "sama pere" — nad kõik ütlevad Springile "tee sellest klassist bean". Erinevus on peamiselt tähenduslik: nad näitavad lugejale, mis **rolli** klass süsteemis täidab.

## Service-meetodi loomine: struktuur ja parameeter — `0:04:36` {#service-meetod}

### Selgitus

Meetodit ehitatakse alati kindlas järjekorras: **nähtavus → tagastustüüp → nimi → sulud (parameetrid) → keha**.

1. **Nähtavus** — `public`, sest seda meetodit kutsutakse välja teisest klassist (`LoginController`).
2. **Tagastustüüp** — alguses pannakse ajutiselt midagi lihtsat (nt `void`), et saaks edasi liikuda; hiljem täpsustatakse taski nõude järgi.
3. **Nimi** — **sama, mis kontrolleris**: `loginUser`. Tegevus ei muutu delegeerimisel — see on lihtsalt "sama asi teises koodifailis". Meie soovime **teadlikult** ühesugust nimetamist läbi kihtide.
4. **Sulud** — siia tulevad parameetrid (vt allpool).
5. **Keha** — `{ }`, mille sisu esialgu tühi.

### Parameeter: `LoginRequest` objekt

Meetod on **"orb"** — ta ei tea oma väljaspoolsest maailmast midagi. Kõik, mida ta vajab, tuleb talle **kaasa anda** parameetrina.

Sisselogimiseks on vaja kasutajanime ja parooli. Need mõlemad on `LoginRequest` objekti sees, seega parameeter on:

```java
public void loginUser(LoginRequest loginRequest) {
    // loginRequest.getUsername(), loginRequest.getPassword()
}
```

Muutuja nimi `loginRequest` — **väikese algustähega**, tüübi nime peegeldav. IntelliJ pakub sedasama automaatselt (Ctrl+Space).

## Teise klassi meetodi väljakutsumine: vaja objekti ja viidet — `0:10:50` {#meetodi-valjakutse}

### Selgitus

`LoginController` tahab käivitada meetodi `loginUser`, mis asub **teises klassis** (`LoginService`). Mida on selleks vaja?

1. **Objekt** — meetod `loginUser` on *objektimeetod*, mitte staatiline. Ilma objektita seda käivitada ei saa. Objekti tekitab `new`:
   ```java
   new LoginService();
   ```
2. **Viide (muutuja)** — objektiga saab "suhelda" ainult läbi nime. Seega objekt tuleb salvestada muutujasse:
   ```java
   LoginService loginService = new LoginService();
   ```
3. **Väljakutse** — punkti abil:
   ```java
   loginService.loginUser(loginRequest);
   ```

### Töövõte: kirjuta enne, mõtle IntelliJ abiga

Videos korratakse töövõtet: **kirjuta lihtsalt see, mida tahad**, isegi kui meetodit/klassi veel pole. IntelliJ näitab punast pirni ("intention action") ja pakub: *"tee `loginUser` meetod `LoginService`-klassi?"* — vajutad Enter ja ta genereerib selle sinu eest. Sina ei roni ise teise faili midagi käsitsi kirjutama.

### Mäluviide

Videos rõhutatakse: parameetrina antakse üle **ainult mäluviide**, mitte objekti koopia. `loginRequest` objekt istub mälus (nt "aadressil 603") ja meetodile antakse see aadress: *"toimeta selle sama objektiga edasi"*.

## Lokaalne muutuja vs objekti väli – miks mitte iga kord `new` — `0:20:00` {#lokaalne-vs-vali}

### Selgitus

Kui kirjutada `new LoginService()` **meetodi sisse**, siis see on **lokaalne muutuja**: iga kord, kui meetod käivitub, luuakse **uus objekt**, mis kohe pärast meetodi lõppu sureb.

```
1. kasutaja logib sisse  →  new LoginService()  (objekt #1, sureb)
2. kasutaja logib sisse  →  new LoginService()  (objekt #2, sureb)
3. kasutaja logib sisse  →  new LoginService()  (objekt #3, sureb)
...
```

See on **ebaefektiivne**: objekti loomine võtab aega ja mälu, aga meile piisaks **ühest** objektist kogu rakenduse elueaks.

### Lahendus: tõsta muutuja klassi tasandile

Võtame `new`-i meetodist välja ja teeme temast **objekti välja** (klassimuutuja):

```java
public class LoginController {
    // objekti väli, mitte lokaalne muutuja
    private LoginService loginService = new LoginService();

    public void loginUser(...) {
        loginService.loginUser(...);   // kasutame olemasolevat
    }
}
```

Nüüd luuakse `LoginService` objekt **üks kord**, kui luuakse `LoginController` objekt — mitte iga päringu peale. Kui kontrolleris oleks mitu meetodit (GET, POST jne), saaksid nad kõik sama objekti jagada.

### Endiselt üks probleem

Kui iga klass teeb oma `new LoginService()`, tekib süsteemi ikkagi **mitu instantsi** samast objektist. Tegevuste käivitamiseks piisab **ühest**. Selle probleemi lahendab lõpuks Spring (vt [Dependency Injection](#dependency-injection)).

## NullPointerException, 500 viga ja stack trace'i lugemine — `0:24:39` {#null-pointer}

### Selgitus

Kui kirjutada ainult

```java
private LoginService loginService;   // väärtustamata!
```

ja **mitte** anda `= new LoginService()`, siis välja väärtus on **`null`**. `null` peal ei ole meetodit `loginUser` — seega tuleb **`NullPointerException`**.

Kliendile (Swagger, frontend) paistab see kui **`500 Internal Server Error`** — "midagi läks serveris valesti". Sama viga, mida oleme frontendis `catch`-plokis näinud.

### Kuidas stack trace'i lugeda

Konsoolis on pikk veateade. Kuidas leida, **kus** jama algas?

1. Keri konsoolis **ülevalt alla**.
2. Esimene **sinine link**, mis viitab **meie enda klassile** (mitte Java enda ega raamistiku klassidele) — sealt algas probleem.
3. Klõpsa lingil → IntelliJ viib täpsele koodireale.
4. Veateade ütleb sisuliselt: *"ei suuda käivitada `LoginService.loginUser` meetodit, **because** `loginService` is `null`"*.
5. Järeldus: `null`-il ei saa objektimeetodit käivitada, sest objekti pole olemas.

### Päriselu analoogia

Stack trace on nagu **kuriteo sündmuskoha raport**: kõige alt üles on kirjas terve ahel, kust "jada läbi käis". Sind huvitab esimene rida, mis puudutab **sinu** koodi — ülejäänu on raamistiku sisemine köök.

## Kuidas objekte luuakse: `new` käivitab konstruktori — `0:27:34` {#konstruktor-new}

### Selgitus

Küsimus: kuidas saaks Spring `LoginController`-ist objekti teha? Vastus: **täpselt samamoodi nagu meie** — `new`-iga.

## Vaikimisi konstruktor ja `final` võtmesõna — `0:30:16` {#final-konstruktor}

### Reegel: vaikimisi konstruktor

- Kui klassil **ei ole ühtegi** konstruktorit kirjutatud, teeb **kompilaator ise** tühja (parameetriteta) konstruktori — "back in business".
- Niipea kui sa **kirjutad kasvõi ühe** konstruktori ise, kompilaator **enam tühja ei tee**. Nüüd saab objekti luua ainult sinu kirjutatud konstruktoriga.

```java
class Student {
    private String firstName;

    // Kui ma kirjutan selle konstruktori...
    public Student(String firstName) {
        this.firstName = firstName;
    }
    // ...siis new Student() enam ei tööta! Ainult new Student("Rain").
}
```

### `final` võtmesõna

`final` väli tähendab: **väärtuse saab anda ainult ühe korra** — ja seda **objekti sünni hetkel**.

```java
private final String firstName;
```

- `final` väljale **ei teki setterit** (Lombok `@Setter` ignoreerib seda) — pärast loomist muuta ei saa.
- Vaikimisi konstruktoriga jääks `final` väli igaveseks `null`-iks — mõttetu.
- Seega: `final` väli **nõuab konstruktorit**, mis ta väärtustab.

### Miks see meid huvitab?

Kui teha kontrolleri sõltuvused (`LoginService`) `final`-iks, siis **kompilaator sunnib** meid tegema konstruktori, mis need kaasa võtab. Ja täpselt seda Spring vajabki (vt järgmine peatükk).

## Lombok `@RequiredArgsConstructor` ja Dependency Injection — `0:36:10` {#dependency-injection}

### Selgitus

Konstruktoreid ise käsitsi kirjutada on tüütu. Appi tuleb **Lombok** annotatsiooniga **`@RequiredArgsConstructor`**:

> Lombok teeb kompileerimise hetkel meie eest konstruktori **kõikide `final` väljade jaoks** (need on "nõutud" väljad — `required args`).

```java
@RestController
@RequiredArgsConstructor
public class LoginController {

    private final LoginService loginService;   // "nõutud" väli

    // Lombok genereerib nähtamatult:
    // public LoginController(LoginService loginService) {
    //     this.loginService = loginService;
    // }
}
```

### Kuidas Spring seda kasutab (Dependency Injection)

Spring töötab **tagurpidi**:

1. Vaatab kõik klassid läbi ja leiab need, mille loomiseks **pole midagi vaja** (tühi konstruktor, sõltuvusteta). Loob need beanid valmis.
2. Liigub edasi. `LoginController` konstruktor **nõuab** `LoginService` objekti. Spring vaatab: *"kas mul on konteineris juba `LoginService` bean olemas?"*
3. `LoginService`-l on `@Service` peal → jah, bean on olemas.
4. Spring **süstib** (injects) olemasoleva `LoginService` beani `LoginController` konstruktorisse ja loob `LoginController` beani.

Seda lähenemist — "keegi teine ühendab objekti ja muutuja automaatselt kokku" — nimetatakse **Dependency Injection** (sõltuvuste süstimine). IntelliJ näitab muutuja kõrval väikest **`DI`** märgist ja noolekesi ("Navigate to autowired dependency").

```
      "mind kasutatakse siin"
LoginService  ◀───────────────  LoginController
   @Service        nool          private final LoginService loginService
   (bean)                        @RequiredArgsConstructor
```

### Kokkuvõttev retsept

> Iga kord, kui teed `@RestController` (või `@Service`) klassi, mis tarbib mõnda teist beani:
> 1. `private final SomeService someService;`
> 2. `@RequiredArgsConstructor` klassi peale
> 3. Spring teeb ülejäänu — õige objekt õigel hetkel.

## Kordamine: kontroller algusest, `@PostMapping`, `@RequestBody` — `0:47:47` {#kordamine-controller}

### Selgitus

Videos kustutatakse kõik ära ja ehitatakse `LoginController` **uuesti nullist**, et võtet harjutada:

1. **`@RestController`** klassi peale — "see on kontroller".
2. **`private final LoginService loginService;`** — juba ette teades, et vajame teenust.
3. **`@RequiredArgsConstructor`** — sest hakkame kedagi niikuinii tarbima.
4. Punase pirni abil loo `LoginService` klass; pane sellele **`@Service`**.
5. Loo meetod: **nähtavus → tagastustüüp → nimi (`loginUser`) → sulud → keha**.

### Annotatsioonid käivad koodirea peal

Oluline nüanss: **annotatsioon elab alati koodirea kohal**. Seepärast:

> Kirjuta **enne päris Java koodirida** (meetodi signatuur), ja **alles siis** pane annotatsioon (`@PostMapping`) selle kohale. Kui kirjutad annotatsiooni enne meetodit, on kood "katki".

### `@PostMapping` ja rada

```java
@PostMapping("/api/login")
public void loginUser(@RequestBody LoginRequest loginRequest) {
    loginService.loginUser(loginRequest);
}
```

- **`@PostMapping`** — kaardistus: kui tuleb `POST`-sõnum sellele rajale, käivita see meetod. (`@GetMapping`, `@PutMapping` jne on samast perest.)
- Kui `@PostMapping`-ul on **ainult rada** ja rohkem midagi, siis rea saab kirjutada lihtsalt `@PostMapping("/api/login")` (ilma `path = ...`).
- **Ära unusta `@`-märki** annotatsiooni ees! Kui `PostMapping` on ilma `@`-ta, näeb IntelliJ seda kui klassiviidet ("kõik on kollane") ja see viga võib "rämedalt kätte maksta".

### `@RequestBody`

`@RequestBody` **parameetri ees** ütleb Springile: *"selle sildi taha pane sõnumi kehas (body) tulnud JSON, tee sellest `LoginRequest` Java objekt"*.

> Sisenditüüpe on mitu: `@RequestBody` (JSON kehas), `@PathVariable` (`.../city/{cityId}` — rajamuutuja) jne. Seepärast peab Springile **eraldi ütlema**, kust see parameeter tuleb.

## `@Data` vs `@Service` – andmed ja tegevused eri failidesse — `0:56:57` {#data-vs-service}

### Selgitus

`LoginRequest` on **andmeklass** — tema sisse tulevad ainult **väljad** (`username`, `password`), mitte tegevused. Seega tema peale **ei panda `@Service`**, vaid **`@Data`** (Lombok: getterid, setterid, `toString`, `equals` jne).

### Kaks suurt eesmärki, miks me faile teeme

| Eesmärk | Näide | Annotatsioon |
|---|---|---|
| **Andmed** (mida hoida/liigutada) | `LoginRequest`, `User` entity, DTO-d | `@Data`, `@Entity` |
| **Tegevused** (mida teha) | `LoginService`, `LoginController` | `@Service`, `@RestController` |

> "Üks teenindab ühte eesmärki, teine teist." `LoginRequest`-i ei panda `service`-kausta ega `@Service` alla — ta on andmete pool.

### Koodinäide

```java
package ee.bcs.bank.controller;

import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
@AllArgsConstructor
public class LoginRequest {
    private String username;
    private String password;
}
```

## Service-kihi ülesanne ja sisselogimise loogika (BEB-5 nõuded) — `1:05:36` {#service-ulesanne}

### Selgitus

Korratakse üle: **kontroller-kihi ainus ülesanne** on käivitada väljast tulnud tegevus. Äriloogikat kontrolleris ei ole. Lubatud on:

- **automaatne valideerimine** (kui sõnum tuleb ebakorrektsel kujul, visata kohe viga);
- piiripealselt **autoriseerimine** (rollid) — aga ka see ehitatakse pigem eraldi;
- **väga lihtne** sisendi teisendamine. Mitte protsessi suunamuutused, mitte otsustuspuud.

### Sisselogimise loogika (service'is)

Nüüd oleme `LoginService`-is. Sisse tuleb `username` ja `password`. **Suur eesmärk:** kontrollida andmebaasis, kas **kasutaja on olemas**.

## Mis on Entity klass — `1:10:17` {#entity}

### Selgitus

**Entity** ("olem") on Java klass, mille **struktuur vastab üks-ühele** ühele andmebaasitabelile:

- iga tabeli veerg → klassi väli;
- klassi peal olevad **annotatsioonid** (`@Entity`, `@Table`, `@Column`, `@Id` ...) teevad ta "eriliseks" — ütlevad JPA-le, milline tabel ja veerud tema taga on.

Entity on **väga tugevalt seotud andmebaasiga**. Kogu JPA/Hibernate mõte on lahendada probleem: *kuidas Java-programm ja andmebaas omavahel suhtlevad*.

### Koodinäide (genereeritud `User`)

```java
@Getter
@Setter
@Entity
@Table(name = "\"user\"", schema = "bank")
public class User {
    @NotNull
    @Column(name = "status", nullable = false, length = Integer.MAX_VALUE)
    private String status;

    @Size(max = 255)
    @NotNull
    @Column(name = "password", nullable = false)
    private String password;

    @Size(max = 255)
    @NotNull
    @Column(name = "username", nullable = false)
    private String username;

    @NotNull
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "role_id", nullable = false)
    private Role role;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id", nullable = false)
    private Integer id;
}
```

Tähelepanek: `role_id` (number tabelis) → Java-s **`Role role`** (terve objekt). Sellest räägime [lazy loadingu juures](#testimine-lazy).

## Migratsioonid, Flyway ja produktsiooni-andmed — `1:35:03` {#migratsioonid-flyway}

### Selgitus

Kui rakendus on juba **produktsioonis** ja seal on **päris kliendiandmeid**, siis "kustuta kõik ja loo tabelid uuesti" **ei ole enam variant**. Andmebaasi muudatused peavad toimuma **kontrollitult** koos uue koodiversiooni väljalaskega.

### Kuidas Flyway (vms migratsioonitööriist) töötab

- Andmebaasi **skriptid on osa koodibaasist** (kaustas, nt `resources/db/migration`).
- Flyway peab **oma väikest tabelit**, kus on kirjas, milline skript on juba käivitatud ja milline mitte.
- Kui serverit käivitatakse:
  1. Flyway vaatab kausta skripte;
  2. leiab need, mida pole varem käivitatud;
  3. käivitab need **enne** serverikoodi laadimist;
  4. kui midagi läheb valesti → keerab muudatused tagasi, server ei käivitu.
- Olemasolevat skripti **ei muudeta** — tehakse **uus** skript `ALTER TABLE ...`-iga.

### Miks see keeruline on

- **Downtime** — serveri ajaks maha võtmine, et keegi andmeid vahepeal ei muudaks.
- Ühe tabeli **kaheks/kolmeks jagamine** töötavate andmetega on "korralik ooper".
- Pangad harjutavad selliseid asju **liivakastis** (sandbox): võta live-andmebaasi **backup**, pane oma lokaali, mängi migratsioon läbi. Kui töötab → alles siis live'i.
- Kõrvale mainitud mõisted: **andmehoidla / data warehouse** (vanad andmed eraldi süsteemis kiiruse huvides), clearing-maksed, valveinimesed öise release'i ajal.

### Greenfield-projektile

> Kui teete **uut asja nullist** (greenfield), kasutage kohe Flyway'd või sarnast — kõik need probleemid on seal juba "algusest peale sisse keevitatud".

## Repository interface'i loomine ja JpaRepository meetodid — `1:47:08` {#repository}

### Selgitus

**Repository** ("uks andmebaasi") on **`interface`**, mis viitab entity klassile. Läbi selle saab teha päringuid.

**Järjekord ("muna ja kana"):** enne peab olema **entity** (`User`), alles siis saab teha **repository** (`UserRepository`).

### Loomine töövõttega

Nagu varem: kirjuta service'is `private final UserRepository userRepository;` (väikese tähega viide muutujale, mida veel pole) → punane pirn → IntelliJ pakub *"tee uus repository User'i kohta"* → Tab.

Küsib **parent**'i (mille laiendame) — vali **kõige kõrgem pärand**: `JpaRepository`. Küsib paketti — pane `ee.bcs.bank.persistence.user` (sinna, kus `User` elab).

### Koodinäide

```java
package ee.bcs.bank.persistence.user;

import org.springframework.data.jpa.repository.JpaRepository;

// <User, Integer> = mis entity, mis tüüpi on tema ID (primaarvõti)
public interface UserRepository extends JpaRepository<User, Integer> {
}
```

### Sisseehitatud meetodid

`JpaRepository` **kingib** hulga meetodeid, mida ise kirjutada ei pea:

| Meetod | Mida teeb |
|---|---|
| `findAll()` | tagastab `List<User>` — kõik read |
| `save(user)` | salvestab (lisab või uuendab) |
| `findById(id)` | otsib primaarvõtme järgi, tagastab `Optional<User>` |
| `getReferenceById(id)` | tagastab "laisa" viite (kasutame harvem) |
| `deleteById(id)`, `count()` ... | jne |

> IntelliJ näitab punktiga meetodite loendis ka "rohelisi" kirjeid — need on **dünaamilised** (derived query, vt allpool), mitte päris olemasolevad meetodid.

## Mis on `interface` — `1:58:49` {#interface}

### Selgitus

**`interface`** ("liides") on midagi klassilaadset, aga:

- ta **defineerib** meetodid (nimi, mida tagastab, mida sisse võtab);
- ta **ei sisusta** neid — **koodiblokki `{ }` ei ole**, lahendus puudub;
- kõik meetodid on automaatselt `public` (ei pea kirjutama);
- ta on **mall / blueprint** teistele klassidele.

### Koodinäide

```java
public interface Animal {
    void makeNoise();              // "iga loom teeb mingit häält"
    String eat(String food);       // "iga loom sööb midagi ja reageerib"
}
```

Siin **ei ole öeldud**, *milline* hääl või *mida* täpselt süües juhtub — ainult et need tegevused **peavad olemas olema**.

### Päriselu analoogia

Kui klass on nagu **piparkook** ja objekt on üks konkreetne küpsetatud piparkook, siis `interface` on **piparkoogivorm koos juhisega**: *"kasuta punast ja valget glasuuri"*. Vorm ütleb, **millised tegevused/koostisosad peavad olema**, aga ei ütle, **mida täpselt joonistada**.

## `implements` ja `@Override` – Animal / Dog / Cat — `2:03:02` {#implements}

### Selgitus

Klass **kasutab** interface'i malliks võtmesõnaga **`implements`** ("implementeerib" = "lahendab"). Niipea kui klass ütleb `implements Animal`, **nõuab kompilaator**, et klassis oleks **kõikide** interface'i meetodite **sisustatud** versioonid. Iga sellise meetodi peale tuleb **`@Override`**.

### Koodinäide

```java
public class Dog implements Animal {

    @Override
    public void makeNoise() {
        System.out.println("Auh-auh!");
    }

    @Override
    public String eat(String food) {
        if ("Chappi".equals(food)) {          // objekte võrreldakse .equals()-iga,
            return "Auh-auh :)";              // MITTE ==
        }
        return "Vurr...";
    }
}

public class Cat implements Animal {
    @Override
    public void makeNoise() { System.out.println("Mjäu"); }

    @Override
    public String eat(String food) {
        if ("Whiskas".equals(food)) return "Nurr";
        if ("kala".equals(food))    return "Urr-mjäu!";
        return "Mjäu?";
    }
}
```

### Skeem

```
              interface Animal          (mall, koodikeha PUUDUB)
              ├─ makeNoise()
              └─ eat(String) : String
                     ▲            ▲
         implements  │            │  implements
              ┌──────┴───┐   ┌────┴─────┐
              │   Dog    │   │   Cat    │   (siin ON koodikeha)
              │ "Auh"    │   │ "Mjäu"   │
              └──────────┘   └──────────┘
```

Mõlemad loomad **teevad häält** ja **söövad** — tegevused on samad, aga **iga klass lahendab need omamoodi**.

## Interface päriselus: PaymentProcessor — `2:13:05` {#interface-paris}

### Selgitus

Pangas on erinevaid **maksetüüpe** ja need töötavad sisemiselt **täiesti erinevalt**:

- **välkmakse** (instant payment) — kohene, kallim;
- **hulgimakse / palgamaksed** (bulk) — ajastatud, lähevad suure hunnikuna, võib-olla teise süsteemi vastu;
- **SEPA**, vanasti **TARGET2** (aeglane, odav) jne.

Aga **tegevused**, mida iga makse juures teha tuleb, on samad: kliendile raha juurde, kliendilt raha maha.

```java
public interface PaymentProcessor {
    void creditCustomer(int amount, String iban);   // raha juurde
    void debitCustomer(int amount, String iban);    // raha maha
}

public class InstantPayment implements PaymentProcessor { /* oma lahendus */ }
public class BulkPayment    implements PaymentProcessor { /* hoopis teine lahendus */ }
public class SepaPayment    implements PaymentProcessor { /* jälle teine */ }
```

### Miks see kasulik on

`interface` **paneb malli varakult paika**: kui tulevikus lisandub **uus** maksetüüp, on kohe teada, millised meetodid (etapid, validatsioonid) tal peavad olema. Sisustamine toimub igas implementatsiooniklassis eraldi.

**Ja siin ongi seos:** `JpaRepository` on samuti `interface`. Meie kirjutame sinna ainult **meetodi definitsiooni**, ja Spring Data teeb **lahenduse meie eest**.

## Derived query: päringumeetod meetodi nime järgi — `2:19:49` {#derived-query}

### Selgitus

`UserRepository` on `interface` — seal **ei ole** programmilist koodi, mis päringut lahendaks. Ja **meile see meeldibki**: me lihtsalt **defineerime meetodi kokkulepitud sõnadega**, ja JPA (Spring Data) **koostab päringu ise**.

### Meetodi ehitamine

1. **Tagastustüüp** — tahame **tervet rida objektina**, seega `User` (mitte `String`, mitte üks väli).
2. **Nimi** — peab kasutama **väga konkreetseid võtmesõnu**, millest JPA aru saab: `find` + `User` + `By` + väljad, ühendatud sõnaga `And`.

```java
public interface UserRepository extends JpaRepository<User, Integer> {

    User findUserByUsernameAndPasswordAndStatus(
            String username, String password, String status);
}
```

IntelliJ pakub juba `find...` kirjutades variante, sest repository on seotud `User` entity'ga ja "näeb" kõiki tema välju (`username`, `password`, `status`).

### Kuidas JPA nimest SQL-i koostab — `2:34:16`

JPA teab `application.properties`'ist, et andmebaas on **PostgreSQL**. Meetodi **nime** järgi paneb ta kokku lause:

```sql
SELECT *
FROM bank."user"
WHERE username = ?     -- 1. parameeter
  AND password = ?     -- 2. parameeter
  AND status   = ?;    -- 3. parameeter
```

Kui sisend on `username = "admin"`, `password = "123"`, `status = "A"` ja selline rida on olemas — JPA leiab selle rea ja **teeb sellest `User` objekti**.

> Miks mitte küsida kogu objekt välja ja siis Java `if`-idega parool üle kontrollida? Sest see tekitaks **tarbetut keerukust koodis**. Sama tulemuse saab **lihtsamalt** juba andmebaasi tasandil: kui JPA **leiab** objekti, siis parool ja staatus **klappisid**.

### Lazy loading: `Role` `User`-i sees

Andmebaasis on `user`-tabelis lihtsalt `role_id` (number). Java `User`-klassis on aga **`private Role role;`** — terve objekt.

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "role_id", nullable = false)
private Role role;
```

Mis taustal toimub:

- Kui otsid `User`-i, siis `role`-tabeli vastu **veel ei minda**. Debuggeris näitab `role` kohta "ei ole veel midagi teada".
- **Niipea kui** sa päriselt küsid `user.getRole()...`, teeb JPA **eraldi päringu**: `SELECT * FROM bank.role WHERE id = 2`, ehitab `Role` objekti ja paneb selle `user`-i külge.
- Seda "too alles siis, kui päriselt vaja" nimetatakse **lazy loading**'uks ("laisk laadimine"). Konsoolis on näha, kuidas tuleb **teine päring** alles siis, kui rolli poole pöördud.

`Role` on **ise ka entity**:

```java
@Entity
@Table(name = "role", schema = "bank")
public class Role {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;
    @Size(max = 255) @NotNull
    private String name;
}
```

Meid ei huvita terve `Role` objekt, vaid ainult tema nimi — seega ketitakse getterid: **`user.getRole().getName()`** ("customer"). See on sama, mida JavaScriptis tegime pesastatud objektidega — lihtsalt getter-meetodite kaudu, mitte välju otse puutudes.
