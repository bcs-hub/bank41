## Abstraktsioon ja miks Java väljad on private — `0:00:00` {#abstraktsioon}

Video algab aruteluga objektorienteeritud programmeerimise elutsüklist ja sellest, miks Java klassi väljad on vaikimisi **private** (privaatsed).

### Selgitus

Kui objektil (nt `Student`) on väljad `firstName`, `lastName`, siis JavaScriptis pöördutakse nende poole otse punktiga: `student.firstName`. Javas see nii lihtsalt ei toimi — väljad on tavaliselt **private**, mis tähendab, et nendele saab ligi ainult sama klassi seest.

Selle asemel kasutatakse **avalikke (public) meetodeid** — gettereid ja settereid:
- **Getter** — meetod, mis väärtuse **tagastab** (annab kätte)
- **Setter** — meetod, mis väärtuse **muudab**

### Päriselu analoogia

Kujuta objekti kui inimest, kellel on kodus seif (private väljad). Sa ei saa lihtsalt sirutada kätt seifi ja võtta raha — pead paluma inimesel (avaliku meetodi kaudu) sulle raha anda või sinna panna. Inimene ise otsustab, mida ta sulle näitab ja mida mitte.

### Miks see hea on

Kui väljadele saab ligi ainult meetodite kaudu, on võimalik **jälgida**, millal ja kuidas objekti sisu muutub — iga muudatus käib läbi konkreetse, jälgitava koodilõigu (meetodi). Kui väljale saaks otse ligi, ei jääks jälgegi sellest, kes ja millal midagi muutis.

## Getterid, setterid ja raamistike mõte — `0:07:36` {#getterid-setterid}

### Selgitus

Ajalooliselt kirjutasid arendajad gettereid ja settereid käsitsi — iga klassi jaoks eraldi. Kuna see muster kordus alati samamoodi (`return this.field`), tekkisid esmalt **IDE-generaatorid** (nupuvajutusega genereeritud kood) ja hiljem **raamistikud** (nt Spring), mis teevad sama asja taustal, ilma et arendaja peaks koodirida nägemagi.

### Abstraktsiooni ajalugu

```
Perfokaardid (nullid/ühed)
        ↓
Assembler (lühikesed käsud, nt "MOV", "ADD")
        ↓
Kõrgema taseme keeled (Java, JavaScript — inglise keele sarnased)
        ↓
Raamistikud (Spring, Vue — annotatsioonid/mustrid teevad töö ära)
```

Iga samm lisab **abstraktsiooni** — programmeerija kirjutab vähem, aga peab usaldama, et taustal toimuv on korrektne. Näide: `@RestController` annotatsioon Springis tähendab, et suur hulk koodi on juba olemas ja ei vaja käsitsi kirjutamist.

### Päriselu analoogia

## If/else ja andmepõhine renderdus Vue's — `0:14:26` {#if-else-vue}

See on video kõige olulisem põhimõte, mis kordub kogu video jooksul.

### Selgitus

> "Kõik käib läbi data bloki. Jätke see endale meelde."

Vue (ja sarnased raamistikud) ei luba otse öelda "näita seda elementi" või "peida see element". Selle asemel **manipuleeritakse andmeid** (data blokis), ja raamistik ise otsustab andmete põhjal, mida kuvada.

### Skeem

```
┌─────────────┐        ┌──────────────┐
│  <script>   │───────▶│    data()    │  ← siin muudetakse muutujaid
│  (loogika)  │        └──────────────┘
└─────────────┘               │
                               │ andmed voolavad alla
                               ▼
                        ┌──────────────┐
                        │  <template>  │  ← siin KUVATAKSE andmete põhjal
                        └──────────────┘
```

### Koodinäide

```html
<template>
  <div v-if="message !== ''" class="alert alert-danger">{{ message }}</div>
</template>
```

See ei ütle "näita alert kasti" — see ütleb "kui `message` muutuja ei ole tühi, siis renderda see div". Programmeerija muudab ainult `message` väärtust; Vue otsustab ise, kas element kuvatakse.

### If / else if / else Vue's

```html
<div v-if="rida1">Rida üks</div>
<div v-else-if="rida2">Rida kaks</div>
<div v-else>Rida kolm</div>
```

Nagu Java `if`-plokkides: **esimene tingimus, mis vastab tõele, käivitub**, ülejäänuid ei kontrollita enam.

## `message` muutuja tühjenemine ja täitumine — `0:38:12` {#message-muutuja}

Praktiline harjutus: kuidas teha nii, et veateade (`message`) ilmub ja kaob õigel ajal.

### Selgitus

Algselt oli koodis probleem — `message` väli sai sisu, aga ei läinud kunagi tagasi tühjaks, kui kasutaja täitis väljad õigesti. Lahendus: **enne igat kontrolli lähtestada `message` tühjaks**, seejärel otsustada, kas anda sellele uus sisu.

### Koodinäide (lõplik versioon `LoginView.vue`-st)

```js
login() {
  this.resetMessage()

  if (this.allFieldsHaveInput()) {
    // proovime sisse logida. saadame backile sõnumile
  } else {
    this.message = 'Täida kõik väljad'
  }
},

resetMessage() {
  this.message = ''
},

allFieldsHaveInput() {
  return this.loginRequest.username.length > 0 && this.loginRequest.password.length > 0
},
```

Video näitab, kuidas panna brauseri arendajatööriistadesse **breakpoint** (peatuspunkt) koodireale ja sammhaaval (`F8`) läbi käia, et näha täpselt, millal ja mis järjekorras muutujad oma väärtusi saavad. See on kasulik, kui pole kindel, kas kood käitub oodatult.

## Kohvimasina analoogia — meetodid, sisend ja väljund — `1:02:16` {#kohvimasin}

### Selgitus

Kasutati näidet kohvimasina koodist, et selgitada, kuidas suur meetod (`getCappuccino`) peaks koosnema **väiksematest, hästi nimetatud meetoditest**, mitte olema üks pikk koodijupp.

```java
public Coffee getCappuccino() {
    CoffeeBeans beans = getCoffeeBeans();
    Water water = getWater(150);
    Coffee coffee = mixWaterAndCoffee(water, beans);
    addMilkFoam(coffee);
    return coffee;
}
```

### Päriselu analoogia

Kui loed retsepti, ei taha sa näha iga üksikut molekulaarset protsessi ("kuumuta vesi 100 kraadini, mis paneb molekulid liikuma kiiremini...") — tahad lugeda **tegevuste nimekirja**: "keeda vesi", "jahvata oad", "sega kokku". Alles siis, kui midagi läheb valesti (bugi), lähed **süvitsi ühte konkreetsesse sammu** ja uurid seda lähemalt.

### Meetodi tüübid, mis videos esile tulid

| Meetodi tüüp | Näide | Mida teeb |
|---|---|---|
| Tagastab objekti | `getCoffeeBeans()` | Annab midagi tagasi, pane muutujasse |
| Ei tagasta midagi | `addMilkFoam(coffee)` | Muudab objekti, ei anna midagi tagasi |
| Võtab sisendi, tagastab tulemuse | `mixWaterAndCoffee(water, beans)` | Sisend + väljund kombineeritud |

## Extract Method — koodi tükeldamine loetavateks osadeks — `1:14:26` {#extract-method}

### Selgitus

"Koodi tuleks lugeda nagu raamatut" — mitte nagu if-lausete rägastikku. Selleks kasutatakse IDE refaktoreerimistööriista **Extract Method**, mis võtab valitud koodiploki ja teeb sellest eraldi, loogilise nimega meetodi.

### Kiirklahvid (IntelliJ)

| Klahvikombinatsioon | Tegevus |
|---|---|
| `Ctrl + Alt + M` | Extract Method — vali koodiplokk, tee sellest meetod |
| `Ctrl + Shift + Enter` | Lõpeta rida / loo automaatselt plokk (nt `else`) |
| `Shift + F6` | Rename — muuda nime kõikjal, kus seda kasutatakse |

### Reegel: kuhu uus meetod paigutada?

> "Alati, kui me tahame ekstraktida, läheme top level'ist üks level allapoole — peaasi, et see on meetodi bloki sees."

See tähendab: uue meetodi definitsioon läheb samasse konteksti (klass / komponendi `methods` plokk), kust seda välja kutsutakse — mitte kõrgemale (nt väljapoole `<script>` plokki) ega madalamale (nt teise meetodi sisse).

## Meetodi nime valimine — miks eitust vältida — `1:19:16` {#meetodi-nimi}

Video kesksemaid õppetunde: **meetodi ja muutuja nimi peab olema jaatav lause, millele saab vastata "jah" või "ei"**.

### Selgitus

Halb nimi jätab lugejale küsimuse, mitte vastuse:

| Halb nimi | Miks halb |
|---|---|
| `validateInput` | Kas tagastab true/false? Kas viskab erindi? Ebaselge |
| `inputCheck` | Ei ütle, mida see kontrollib ega mida tagastab |
| `isNotAdult` | Eitav — raske lugeda `if`-lauses koos `!`-ga |

Hea nimi:

```js
allFieldsHaveInput()  // saab vastata: JAH või EI
```

### Miks eitust vältida

> "Eitust keerata jaatuseks on raskem kui jaatust eituseks."

Kui meetod on nimetatud jaatavalt (`isAdult`), saab seda hüüumärgiga (`!isAdult()`) lihtsalt tagurpidi pöörata, kui vaja. Aga kui meetod on juba nimetatud eitavalt (`isNotAdult`), ja hiljem on vaja vastupidist loogikat, tuleb koodi lugejal peas topelt-eitust lahti harutada — palju raskem.

### Päriselu analoogia

See on nagu kellegi käest küsida "Kas sa **ei** taha kohvi?" — vastus "Ei" on segadusseajav (kas see tähendab "ei, ma ei taha" või "ei, see pole tõsi, ma tahan")? Otsene küsimus "Kas sa tahad kohvi?" on alati selgem.

## Refaktoreerimine (Rename, Shift+F6) ja skoop — `1:22:45` {#refaktoreerimine}

### Selgitus

Kui muutuja või meetodi nimi on juba kasutuses mitmes kohas, ei tohi seda kunagi **käsitsi üle kirjutada** (lihtsalt teksti muuta) — tuleb kasutada **Refactor → Rename** (`Shift+F6`), mis muudab nime kõikjal korraga, kus see on kasutusel.

### Ettevaatust: Vue vs Java

Java puhul (staatiliselt tüübitud keel) teab IDE alati täpselt, kus muutuja on kasutusel, ja refaktoreerimine on turvaline. Vue/JavaScript puhul (dünaamiline keel) võib IDE olla **liiga agressiivne** — võib pakkuda muutmiseks isegi kohti, mis pole tegelikult seotud (nt sama nimega, aga täiesti erinev `message` muutuja teises failis).

**Lahendus:** enne `Enter` vajutamist saab valida **skoobi** (scope) — nt "ainult see fail" — et vältida soovimatuid muudatusi mujal.

## Jaatav If/Else — koodi loetavaks tegemine — `1:53:03` {#jaatav-if-else}

### Selgitus

Algne kood kontrollis eitavat tingimust ("kui väljad EI ole täidetud"). Parem lähenemine: kontrolli **jaatavat** tingimust ja pane negatiivne juhtum `else` harusse.

### Koodinäide — samm-sammult muutus

```js
// Halvasti loetav (eitus if-is)
if (username === '' || password === '') {
  this.message = 'Täida kõik väljad'
}

// Parem — jaatav tingimus if-plokis, negatiivne else's
if (this.allFieldsHaveInput()) {
  // proovime sisse logida
} else {
  this.message = 'Täida kõik väljad'
}
```

### Reegel

> "Kui vähegi võimalik, üritage hoida asja jaatavana. If-lause peab olema selline, et positiivne olukord läheb if-plokki, negatiivne (probleemne) olukord läheb else-plokki."

## AlertDanger komponendi ekstraheerimine — `2:21:19` {#alertdanger-komponent}

Praktiline demo: kuidas eraldada korduvkasutatav visuaalne osa (veateate kast) omaette Vue komponendiks.

### Selgitus

Kuni selle hetkeni oli veakast otse `LoginView.vue` sees. Task nõudis, et see oleks **eraldi komponent** — nii saab sama kasti kasutada mitmel vaatel korraga.

### Sammud

1. Loo uus fail `src/components/AlertDanger.vue`
2. Tõsta HTML sinna
3. `LoginView.vue`-s tee **import**: `import AlertDanger from '@/components/AlertDanger.vue'`
4. Registreeri komponentide plokis: `components: { AlertDanger }`
5. Kasuta template'is ühe tagiga: `<AlertDanger/>`

### Koodinäide (reaalne tulemus koodibaasist)

`../../frontend/src/components/alert/AlertDanger.vue`:
```html
<script>
export default {
  name: 'AlertDanger',
}
</script>

<template>
  <div>
    <div class="alert alert-success" role="alert">
      AAAAAAAAAAAAAAAAAAAAA
    </div>
  </div>
</template>
```

`frontend/src/views/LoginView.vue` (väljavõte):
```html
<script>
import AlertDanger from '@/components/AlertDanger.vue'

export default {
  name: 'LoginView',
  components: { AlertDanger },
  // ...
}
</script>

<template>
  <div class="container text-center">
    <div class="row justify-content-center">
      <div class="col col-6">
        <AlertDanger/>
        <!-- ... -->
      </div>
    </div>
  </div>
</template>
```

Praegusel hetkel on `AlertDanger` veel **staatilise sisuga** (kõva tekst "AAAA...") — see on tahtlik vahepealne samm. Järgmisena on vaja teha sisu **dünaamiliseks** — see viib otse Props-teemani.

### Dev Tools — komponentide puu

Vue Dev Tools brauseris näitab komponentide hierarhiat: `LoginView` on vanem, `AlertDanger` on selle laps ("child"). Nagu matrjoškanukud — iga vaade koosneb väiksematest komponentidest, millel igaühel on oma fail ja oma sisu.

## Props — andmete voog vanemalt lapsele — `2:37:59` {#props}

### Selgitus

**Props** on mehhanism, mille kaudu vanemkomponent (parent) annab andmeid edasi lapsele (child). Andmed voolavad **ainult ühes suunas — ülevalt alla**, nagu kosk.

### Skeem

```
┌─────────────────┐
│   LoginView      │  (parent / vanem)
│   message: "..."  │
└────────┬─────────┘
         │ props (andmed voolavad ALLA)
         ▼
┌─────────────────┐
│  AlertDanger      │  (child / laps)
│  kuvab saadud sisu │
└─────────────────┘
```

### Reegel

> "Props ei tohi olla interaktiivselt seotud ühegi elemendiga, mis suudaks muuta tema väärtust. Propsi muutmine Child'is on keelatud."

Kui laps (`AlertDanger`) saab props'i kaudu teksti, ei tohi ta seda **ise muuta** — muudatus peab alati tulema vanemalt. Kui laps püüaks propsi väärtust ise muuta, rikuks see ühesuunalise andmevoo põhimõtte, millel kogu Vue reaktiivsus põhineb: *andmed muutuvad → pilt (HTML) joonistub uuesti*.

### Päriselu analoogia

Props on nagu **täditäti annab lapsele kingituse** — üks suund, vanem otsustab, mida jagada. Laps ei saa kingitust "tagasi muuta" ja vanemale teistsugusena tagasi anda.

Vastandina: soovitud lapsed (child-komponendid) peaksid olema nagu **orvud** — nad ei tea, kes on nende "vanem" (milline komponent neid kasutab). See tähendab, et sama komponenti (nt `AlertDanger`) saab kasutada **kus iganes**, ilma et see oleks kõvasti seotud ühe konkreetse vaatega.

### Millal kasutada Propsi vs v-model'it

| Tööriist | Kasutus |
|---|---|
| **Props** | Ühesuunaline: vanem annab lapsele andmed kuvamiseks (nt teade, pealkiri) |
| **v-model** | Kahepoolne side: kasutaja saab väärtust otse muuta (nt tekstiväli) |

Kui kasutad Props'i, ei tohi kasutada `v-model`-it samal andmel — need on vastandlikud lähenemised.

## Emit — sündmuste voog lapselt vanemale — `2:45:22` {#emit}

### Selgitus

Kui Props voolab **alla** (vanem → laps), siis **`emit`** (väljastamine) võimaldab infol voolata **üles** (laps → vanem) — aga mitte otsese andmemuutusena, vaid **sündmuse (event) teavitusena**.

### Päriselu analoogia — postituvi

> "See tuvi ei pane teate ise midagi juhtuma — ta lihtsalt teavitab. Kiri jala küljes ütleb, mis toimub, aga vastuvõtja otsustab ise, mida sellega teha."

Laps ei ütle vanemale "muuda oma andmeid selliseks" — laps ütleb "hei, midagi juhtus" (nt "kasutaja valis Tallinna"), ja **vanem ise otsustab**, kuidas oma andmeid selle sündmuse põhjal muuta.

### Skeem

```
┌─────────────────┐
│  AlertDanger      │  (child / laps)
│  emit('valiti')    │
└────────┬─────────┘
         │ event (sündmus voolab ÜLES)
         ▼
┌─────────────────┐
│   LoginView      │  (parent / vanem)
│  reageerib, muudab │
│  oma andmeid       │
└─────────────────┘
```

### Miks see nii on üles ehitatud

> "Me ei programmeeri kuskil visuaalset käitumist. Kõik renderdatakse andmete peal — kui andmed muutuvad, pilt muutub."

Kogu Vue filosoofia taandub sellele: programmeerija ei ütle kunagi otse "näita seda" või "peida see" — programmeerija **muudab andmeid**, ja raamistik ise otsustab, kuidas ekraan selle põhjal ümber joonistada.

## Kokkuvõte

| Mõiste | Selgitus |
|---|---|
| Private väljad (Java) | Objekti sisu kaitstud, ligipääs ainult getterite/setteritega |
| Abstraktsioon | Iga arenguetapp (assembler → kõrgtasemekeeled → raamistikud) peidab keerukust |
| Andmepõhine renderdus | Vue ei luba otse "näita/peida" — ainult andmete muutmine, raamistik otsustab kuvamise |
| Extract Method | Koodiploki tükeldamine eraldi, loetava nimega meetodiks (`Ctrl+Alt+M`) |
| Jaatav nimetamine | Meetodi/muutuja nimi peab olema statement, millele saab vastata jah/ei, mitte eitus |
| Refaktoreerimine (Rename) | Nime muutmine kõikjal korraga (`Shift+F6`), mitte käsitsi üle kirjutades |
| Props | Andmed voolavad vanemalt lapsele, ainult ühes suunas, last ei tohi neid muuta |
| Emit | Sündmused voolavad lapselt vanemale, vanem otsustab, kuidas reageerida |

## Järgmised sammud

Kui see teema oli huvitav, tasub edasi õppida:
- **Vue `props` deklaratsioon** — kuidas komponendis ametlikult defineerida, milliseid props'e see vastu võtab (`props: { message: String }`)
- **Vue `emits` deklaratsioon** — kuidas dokumenteerida, milliseid sündmusi komponent väljastab
- **Extract Method vs Extract Function** — refaktoreerimise erinevad tasemed (meetod klassis vs eraldi fail)
- **Java getter/setter genereerimine IDE-s** — praktiline harjutus samade mõistetega Java kontekstis
- **HTTP `POST` päringu saatmine Axiosiga** — järgmine loogiline samm pärast `allFieldsHaveInput()` kontrolli õnnestumist
