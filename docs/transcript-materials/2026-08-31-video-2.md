## `SessionStorageService`: kontrollmeetodi lühendamine üherealiseks — `0:00:11` {#session-storage-service}

### Selgitus

Eelmise video lõpus jäi pooleli kohmakas `if`/`else` konstruktsioon, mis kontrollis, kas kasutaja on sisse logitud. Tund algas selle **lühendamisega** — kui `if`/`else` ainult väärtustab muutujat `true`/`false` vastavalt tingimusele, on tingimuse tulemus **juba ise** `true` või `false` — pole vaja seda uuesti kontrollida.

Lisaks liigutati see loogika eraldi **service-faili** (`SessionStorageService.js`), et:
1. Vältida sama koodi kirjutamist mitmes kohas.
2. Muuta koodi loetavaks — nimeline meetod (`userIsLoggedIn()`) ütleb kohe, mida see teeb, ilma detaile lugemata.

### Koodinäide (`frontend/src/services/SessionStorageService.js`)

```js
export default {
  userIsLoggedIn() {
    return sessionStorage.getItem('userId') !== null
  },
}
```

See on palju lühem kui algne variant:

```js
// EBAMUGAV VARIANT — üleliigne if/else
if (userId !== null) {
  isLoggedIn = true
} else {
  isLoggedIn = false
}

// LÜHEM — võrdlus ise ongi juba true/false
userIsLoggedIn() {
  return sessionStorage.getItem('userId') !== null
}
```

Kasutamine `App.vue`-s:

```js
data() {
  return {
    isLoggedIn: SessionStorageService.userIsLoggedIn(),
  }
}
```

### Päriselu analoogia

See on nagu küsimuse "kas uks on lukus?" vastuse andmine — pole vaja öelda "kui lukk on kinni, siis vastan 'jah', kui lukk on lahti, siis vastan 'ei'"; piisab öelda otse "lukk on kinni" (mis ongi juba jah/ei vastus).

## Custom event: laps teavitab vanemat sündmusest ($emit) — `0:12:23` {#custom-event}

### Selgitus

Vue's voolavad **andmed ülevalt alla** (parent → child, läbi props'ide). Aga mis siis, kui **laps** peab **vanemat** millestki teavitama (nt "kasutaja logis just sisse")? Selleks on **custom event** (kohandatud sündmus) mehhanism — töötab nagu tuvipost vastupidises suunas: alt üles.

Meetod, millega laps saadab sündmuse: **`$emit(eventName, data?)`**

- `eventName` (kohustuslik) — sündmuse nimi (string)
- `data` (valikuline, küsimärgiga tähistatud) — lisainfo, mis sündmusega kaasa läheb

### Skeem

```
┌─────────────────────┐
│  App.vue (parent)     │
│  <RouterView          │
│    @event-user-       │  ← kuulaja: "kui alt tuleb see event, tee midagi"
│      logged-in="..." />│
└──────────┬────────────┘
           ▲  event "lendab" alt üles
           │
┌──────────┴────────────┐
│  LoginView.vue (child)│
│  this.$emit(           │
│    'event-user-        │
│     logged-in')        │
└─────────────────────┘
```

### Koodinäide (`frontend/src/views/LoginView.vue`)

```js
handleLoginResponse(response) {
  this.loginResponse = response.data
  this.saveLoginResponseInfoToSessionStorage()

  this.$emit('event-user-logged-in')
  NavigationService.navigateToAtmsView()
},
```

### Päriselu analoogia

`$emit` on nagu tuvipost, mille kiri lendab **alt üles** — laps (tuvi puuris) saadab teate ("midagi juhtus!") vanemale, kes ootab ülal ja loeb kirja, kui see saabub. Vanem ei tea, mis lapse sees toimus, ainult seda, mida sõnum ütleb.

## Event nimetamise konventsioon (`event-` eesliide) — `0:23:24` {#event-nimetamine}

### Selgitus

Õpetaja järgib isiklikku (mitte kohustuslikku) konventsiooni: kõik ise loodud eventid algavad sõnaga **`event-`** (kebab-case kirjaviisis). See aitab kiirelt eristada, kas tegemist on Vue enda sisseehitatud sündmusega (nt `@click`) või rakenduse enda kohandatud sündmusega.

**Oluline põhimõte:** event'i nimi peaks kirjeldama, **mis juhtus lapse sees**, mitte seda, mida vanem peaks tegema. Näiteks `event-user-logged-in` ("kasutaja logis sisse") on hea nimi, sest see kirjeldab **fakti**, mitte tegevust ("uuenda menüüd" oleks halb nimi, kuna see kirjeldaks vanema vastutust, mitte lapse fakti).

### Koodinäide

```js
// HEA — kirjeldab, mis JUHTUS
this.$emit('event-user-logged-in')

// HALB — kirjeldab, mida VANEM peaks tegema
this.$emit('event-update-menu')
```

### Päriselu analoogia

Hea event-nimi on nagu uudisepealkiri ("Sadas lund") — see kirjeldab fakti, mitte käsku ("Pane kummikud jalga"). Fakti teadmisega saab iga lugeja ise otsustada, mida teha; käsk eeldaks, et sündmuse allikas teab juba ette, mida kõik kuulajad peaksid tegema.

## Kuulaja seadmine: `@event-nimi` RouterView'l — `0:27:45` {#event-lisener}

### Selgitus

Selleks, et vanem (parent) saaks lapse (child) saadetud eventi kätte, peab ta looma **kuulaja (event listener)** täpselt seal, kus laps välja kutsutakse — tag'i sees. Vue's kirjutatakse see `@` sümboliga.

Kuna `LoginView` (ja teised vaated) kutsutakse välja `App.vue`'s **`<RouterView />`** kaudu (Vue Routeri sisseehitatud komponent, mis kuvab vastavalt marsruudile ühte vaadet korraga), on just see koht, kus kuulaja tuleb üles seada.

### Koodinäide (`frontend/src/App.vue`)

```vue
<RouterView @event-user-logged-in="isLoggedIn = true" />
```

Siin `@event-user-logged-in` ütleb: "kui mistahes laps (praegu kuvatav vaade, mis iganes see parajasti on) saadab sündmuse nimega `event-user-logged-in`, siis käivita `isLoggedIn = true`".

### Skeem

```
Router otsustab: praegu on RouterView sisu = LoginView
                          │
LoginView.$emit('event-user-logged-in')
                          │
                          ▼
        RouterView'l on kuulaja @event-user-logged-in
                          │
                          ▼
              App.vue: isLoggedIn = true
```

### Päriselu analoogia

`RouterView` on nagu ukseava, kust erinevad "toad" (vaated) võivad omavahel vahetuda, aga uks ise (koht, kus kuulatakse) jääb samaks — nii saab vanem alati sealt kuulata, ükskõik milline tuba parasjagu ukse taga on.

## Kaks varianti eventi käsitlemiseks: otse muutuja vs meetod — `0:29:15` {#event-kasitlemise-variandid}

### Selgitus

Kui event saabub, on **kaks võimalust**, mida teha:

1. **Otse template'is väärtustada** muutuja — sobib **lihtsate** tegevuste puhul (üks väärtuse muutmine).
2. **Käivitada meetod** — sobib, kui tegevus on **keerukam** (mitu sammu) või kui koodi loetavus paraneb nimelise meetodiga.

Õpetaja demonstreeris mõlemat, ning ennustas, et projekt liigub tulevikus meetodi-põhise lähenemise poole, kuna loogika kasvab keerulisemaks (nt lisaks sisselogimise olekule tuleb hiljem ka **roll**, mis nõuab mitme väärtuse korraga otsustamist).

### Koodinäide — variant 1: otse template'is

```vue
<RouterView @event-user-logged-in="isLoggedIn = true" />
```

### Koodinäide — variant 2: meetodi kaudu

```vue
<RouterView @event-user-logged-in="updateMenu" />
```

```js
methods: {
  updateMenu() {
    this.isLoggedIn = true
  },
}
```

### Päriselu analoogia

See on nagu vahe lühikese post-it märkuse ja pikema tegevuskava vahel — kui ülesanne on "keera lüliti", piisab ühest märkusest (otse template); kui ülesanne on "tee kolm asja järjest", on parem kirjutada eraldi juhend (meetod), mida saab hiljem uuesti kasutada.

## `executeLogOut()`: väljalogimise meetod — `1:09:12` {#execute-logout}

### Selgitus

Väljalogimise nupu vajutamisel peab kolm asja toimuma:
1. `sessionStorage` tühjendatakse (`.clear()`)
2. `isLoggedIn` muutuja väärtustatakse `false`
3. Kasutaja suunatakse koduvaatele (`NavigationService`)

Kuna nupp asub **globaalses menüüs** (`App.vue`), mitte ühe konkreetse vaate sees, tuleb arvestada, et kasutaja võib väljalogimise hetkel olla **suvalisel vaatel** — mõned vaated (nt tulevikus lisanduv "pangaautomaadi lisamine") eeldavad sisselogitud olekut, mistõttu tuleb pärast väljalogimist alati **navigeerida** turvalisele lehele (koduvaade), mitte jätta kasutajat vaatele, kuhu ta enam ei tohiks pääseda.

### Koodinäide (`frontend/src/App.vue`)

```js
methods: {
  executeLogOut() {
    sessionStorage.clear()
    this.isLoggedIn = false
    NavigationService.navigateToHomeView()
  },
},
```

```vue
<div v-if="isLoggedIn">
  <button @click="executeLogOut" class="btn btn-primary" type="submit">Logi välja</button>
</div>
```

### Päriselu analoogia

Väljalogimine on nagu hotellitoast väljaregistreerimine — võti (sessionStorage) antakse tagasi, staatus muutub ("külaline" → "mitte-külaline"), ja külaline saadetakse fuajeesse (koduvaade), mitte jäetakse üksinda tema endisesse tuppa, kuhu tal enam õigust pole.

## Stoplight: veaolukorra simuleerimine `Prefer` päisega — `1:21:47` {#stoplight-error-simulation}

### Selgitus

Kuna Stoplight vastab vaikimisi alati **eduka** vastusega, on vaja seda "petta" veaolukorra simuleerimiseks. Selleks kasutatakse spetsiaalset HTTP **päist (header)** nimega **`Prefer`** — see on Stoplight'i enda kokkulepitud atribuut, mis ei ole standardne HTTP funktsionaalsus, vaid Stoplight'i disainerite loodud tööriist testimiseks.

Sõnumiga saab kaasa saata `Prefer: code=403, example=error`, mis ütleb: "vasta mulle staatusega 403 ja kasuta salvestatud näidet nimega `error`".

Sarnaselt saadab reaalne autentimissüsteem tavaliselt **tokenid** just headeris (mitte URL-is ega body's), sest see info pole visuaalselt nii "nähtaval" nagu URL või JSON keha.

### Koodinäide — Stoplight'i simuleerimise loogika viidi koodi

```js
if (this.loginRequest.username === 'error') {
  preferValue = 'code=403, example=error'
} else if (this.loginRequest.username === 'admin') {
  preferValue = 'code=200, example=admin'
} else {
  preferValue = 'code=200, example=customer'
}
```

### Päriselu analoogia

`Prefer` päis on nagu salajane märkus kirjaümbriku sees, mis pole osa kirja tavapärasest sisust, vaid mõeldud ainult "postiljonile" (siin: testkeskkonnale) — see ütleb postiljonile, millist vastust saata, ilma et see mõjutaks kirja enda tavapärast lugemist.

## Dünaamiline `Prefer` väärtus vastavalt kasutajanimele — `1:35:23` {#dunaamiline-prefer}

### Selgitus

Praktikas ehitati `if`/`else if`/`else` konstruktsioon, mis vastavalt sisestatud kasutajanimele valib, millist Stoplight'i näidet küsida:
- `"error"` → küsitakse 403 vea näidet
- `"admin"` → küsitakse admin-kasutaja näidet
- muu → küsitakse tavakasutaja (customer) näidet

See võimaldab arendajal **kohapeal juhtida**, milliseid stsenaariume katsetada, ilma et peaks Stoplight'i veebiliideses käsitsi seadeid muutma.

### Koodinäide (loogika `LoginService.js`-s, mudel `LoginView.vue`-s)

```js
axios.get('/api/login', {
  headers: {
    Prefer: `code=${code}, example=${example}`,
  },
})
```

### Päriselu analoogia

See on nagu drive-through tellimine, kus ütled kohe ette, mida tahad ("tavaline" vs "vale kasutajanimega vastus") — testides saad valida stsenaariumi lihtsalt sisendväärtust muutes, selle asemel et minna iga kord eraldi seadistama serveri poolt tagastatavat vastust.

## Catch bloki ehitamine: error response mudel — `1:46:41` {#catch-blokk}

### Selgitus

Sarnaselt õnneliku vastuse (`response.data`) käsitlusega, vajab ka **veaobjekt** enda kirjeldava **mudeli**. HTTP veaolukorras on struktuur veidi **rohkem kihiline**: kogu viga (`error`) sisaldab omakorda `response` blokki, mille sees on alles `data` — reaalne sisu, mida server veast rääkides saatis.

```
error
 └── response
      └── data
           ├── message   (nt "Vale kasutajanimi või parool")
           └── errorCode (nt "INCORRECT_CREDENTIALS")
```

Sarnaselt õnnelikule vastusele tehti selle jaoks eraldi **andmemudel** `data` bloki sisse, et koodi lugedes oleks kohe selge, mis kujul viga tuleb.

### Koodinäide (`frontend/src/views/LoginView.vue`)

```js
data() {
  return {
    // ...
    errorResponse: {
      message: '',
      errorCode: '',
    },
  }
}
```

```js
login() {
  this.resetErrorMessage()
  if (this.allFieldsHaveInput()) {
    this.startSpinner()

    LoginService.postLoginRequest(this.loginRequest)
      .then((response) => this.handleLoginResponse(response))
      .catch((error) => this.handleLoginErrorResponse(error))
      .finally(() => this.stopSpinner())
  } else {
    this.errorMessage = 'Täida kõik väljad'
  }
},

handleLoginErrorResponse(error) {
  this.errorResponse = error.response.data
  // ... edasine loogika
},
```

Töövõte on sama, mida kasutati eduka vastuse puhul (nähtud eelmises videos): kirjutatakse esmalt meetodi väljakutse (`this.handleLoginErrorResponse(error)`), IDE märgib selle kollasega, ja `Alt+Enter` genereerib meetodi tühja põhja.

### Päriselu analoogia

Veaobjekti mitmekihilisus on nagu kirjaümbrik kirjaümbriku sees — päris viga on peidetud mitme kihi taha (`error.response.data`), samamoodi nagu tähtis dokument võib olla pakitud sisemisse ümbrikku, mis omakorda on suuremas väliskestas.

## Staatuskoodi ja error koodi kontroll (403 + INCORRECT_CREDENTIALS) — `2:15:39` {#staatuse-kontroll}

### Selgitus

Ülesanne nõudis kahe tingimuse **korraga** kontrollimist (loogiline `AND`, `&&`):
1. HTTP staatuskood on **403**
2. Vastuse `errorCode` väli on **`INCORRECT_CREDENTIALS`**

Kui mõlemad kehtivad, on tegemist teadaoleva veaga (vale kasutajanimi/parool), mida saab kasutajale sõbralikult kuvada `AlertDanger` komponendi kaudu.

**Miks kaks tingimust korraga?** Ainult error koodi kontrollimisest ei piisa — sama koodivõiks teoreetiliselt esineda erinevate staatuste all, seega täpsuse mõttes kontrollitakse mõlemat väärtust koos.

### Koodinäide (`frontend/src/views/LoginView.vue`)

```js
handleLoginErrorResponse(error) {
  this.errorResponse = error.response.data

  if (error.response.status === 403 && this.errorResponse.errorCode === 'INCORRECT_CREDENTIALS') {
    this.errorMessage = this.errorResponse.message
  } else {
    NavigationService.navigateToErrorView()
  }
},
```

### Päriselu analoogia

See on nagu kahe võtme süsteem seifi avamiseks — mõlemad võtmed (staatuskood ja error kood) peavad korraga sobima, enne kui saab kindel olla, et tegemist on just selle konkreetse, tuntud veaolukorraga, mitte millegi muuga, mis lihtsalt sarnaneb.

## Meetodi ehitamine "seestpoolt väljapoole" mustri kordamine — `2:49:19` {#meetodi-ehitamine-muster}

### Selgitus

`getCitiesRequest()` meetodi kasutamisel korrati sama mustrit, mida on nüüdseks korduvalt näidatud:

1. Kutsu meetod välja, mis tagastab midagi (`CityService.getCitiesRequest()`)
2. Kui tahad tulemusega midagi teha, lisa **`.then()`**
3. `.then()` sees kirjuta väljakutse **veel loomata** meetodile (nt `handleGetCitiesResponse`)
4. Kasuta IDE kollast pirni (`Alt+Enter`), et genereerida meetodi tühi põhi
5. Täida meetodi sisu

Andmete toomine käivitatakse **`beforeMount`** hookis — see tähendab, et kohe kui `AtmsView` laetakse, tuuakse linnade andmed automaatselt, ilma et kasutaja peaks nuppu vajutama.

### Koodinäide

```js
beforeMount() {
  this.getCities()
},

methods: {
  getCities() {
    CityService.getCitiesRequest()
      .then((response) => this.handleGetCitiesResponse(response))
  },
}
```

### Päriselu analoogia

See on käsitöölise korduv rutiin — sama tööriistakomplekti ja sama järjestust kasutatakse iga kord uue sõnumitüübi jaoks (kutsu meetod → oota vastust → käsitle vastust eraldi nimelises meetodis), sõltumata sellest, kas tegu on sisselogimise, väljalogimise või andmete pärimisega. Kord õpitud muster kordub kogu projektis.
