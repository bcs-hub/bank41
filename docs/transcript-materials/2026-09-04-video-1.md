## Automaatide miinimumarv – äriline vs tehniline otsus — `0:00:04` {#automaatide-miinimumarv}

Video algab lühikese aruteluga: kas pangaautomaatide asukohal peab alati olema vähemalt üks automaat, või võib see olla ka null?

### Selgitus

Õpetaja selgitab, et see pole tehniline piirang, vaid **äriline valik**. Kui frontendi vormis on numbrisisendi miinimumväärtus seatud ühele, ei saagi kasutaja liuguri või nupu abil väiksemat väärtust valida — aga kui ta trükib väärtuse käsitsi, tuleb see backendis (või frontendi validatsioonis) ikkagi üle kontrollida. Seda tüüpi otsused ("kas eeltäidetud väli, kas miinimum on 0 või 1") mõjutavad kasutajakogemust, aga ei ole tehniliselt kohustuslikud — need lepitakse kokku äripoolega.

### Koodinäide

Kontroll on juba olemas `LocationView.vue` failis:

```js
checkFormForErrors() {
  if (this.location.cityId === 0) {
    this.errorMessage = 'Vali linn'
  } else if (this.location.locationName === '') {
    this.errorMessage = 'Lisa asukoha nimi'
  } else if (this.location.numberOfAtms < 1) {
    this.errorMessage = 'Automaatide arv peab olema vähemalt 1'
  } else if (!this.transactionTypeIsSelected()) {
    this.errorMessage = 'Vali vähemalt üks ATM teenus'
  }
}
```

Näed, et `numberOfAtms < 1` on täpselt see äriline reegel, millest jutt käis — see on kokkulepe, mitte matemaatiline paratamatus.

## Uue "Ligipääs keelatud" vaate ja marsruudi loomine — `0:02:09` {#ligipaas-keelatud-vaade}

Kasutaja võib sisestada brauseri aadressiribale otse URL-i (nt `/location`), ilma et ta oleks sisse loginud või et lingile oleks üldse kuskil viidatud. Sellisel juhul peab rakendus näitama midagi mõistlikku, mitte lihtsalt tühja lehte.

### Selgitus

Õpetaja pakub kaks varianti: näidata "lehte ei leitud" (404) või näidata spetsiifilisemat teadet "sul ei ole siia ligipääsu". Valitakse teine variant — luuakse uus Vue komponent `NotAuthorizedView`, mis registreeritakse marsruuterisse (Vue Router) omaette marsruudina.

### Skeem

```
Kasutaja sisestab URL-i
        │
        ▼
  Vue Router leiab route'i
        │
        ▼
  Kas kasutaja tohib seda vaadet näha?
   ├─ Jah → näita algset komponenti (nt LocationView)
   └─ Ei  → suuna NotAuthorizedView peale
```

### Koodinäide

Marsruudid defineeritakse ühes kesksed kohas — `router/index.js`:

```js
import { createRouter, createWebHistory } from 'vue-router'
import LocationView from '@/views/LocationView.vue'
import NotAuthorizedView from '@/views/NotAuthorizedView.vue'

const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    {
      path: '/location',
      name: 'locationRoute',
      component: LocationView,
    },
    {
      path: '/not-authorized',
      name: 'notAuthorizedRoute',
      component: NotAuthorizedView,
    },
  ],
})

export default router
```

Iga marsruudil on kolm olulist osa: **path** (URL, mida kasutaja brauseris näeb), **name** (sisemine viide, mida koodis kasutatakse) ja **component** (Vue komponent, mis selle vaate joonistab).

Ise loodud `NotAuthorizedView.vue` näeb reaalses koodis välja nii:

```vue
<script>
import { PhProhibit } from '@phosphor-icons/vue'

export default {
  name: 'NotAuthorizedView',
  components: { PhProhibit },
}
</script>

<template>
  <div class="container text-center">
    <div class="row">
      <div class="col">
        <h1>Ligipääs keelatud! <PhProhibit class="bg-danger" :size="50" /></h1>
        <img class="img-fluid"
          src="https://media.tenor.com/7J77iJcHMA8AAAAM/penguins-madagascar.gif"
          alt="Pingviinid kaklevad. Ligipääs keelatud "
        />
      </div>
    </div>
  </div>
</template>
```

Video jooksul valitakse ikoon **Phosphor Icons** teegist (`PhProhibit` — keelumärgi ikoon) ja lisatakse "veidi huumorit" GIF-pilt, et vaade poleks täiesti kuiv.

### Päriselu analoogia

See sarnaneb turvatud hoonega: kui sul pole pääsukaarti, ei jää uks lihtsalt tumedaks — valvur ütleb sulle konkreetselt "sul ei ole siia ligipääsu", mitte ei jäta sind segadusse.

## Autoriseerimise kontroll enne vaate laadimist (beforeMount) — `0:15:32` {#beforemount-kontroll}

Nüüd tuleb otsustada, **kust kohast** koodis kontrollitakse, kas kasutajal on üldse õigus antud vaadet näha.

### Selgitus

Vue komponendi elutsüklis on hulk "hook'e" (elutsükli meetodeid), mis käivituvad kindlatel hetkedel. `beforeMount` käivitub **enne**, kui komponent jõuab ekraanile kuvatud saada — see on ideaalne koht kontrollimaks, kas kasutaja tohib seda vaadet üldse näha, sest see toimub enne, kui midagi jõuab ekraanile joonistuda.

Loogika on lihtne if-lause: "kas kasutaja on administraator? Kui jah, lae andmed. Kui ei, suuna eemale."

### Skeem

```
Component beforeMount()
        │
        ▼
  userIsAdmin() === true?
   ├─ Jah → lae andmed (getCities, getLocationTransactionTypes)
   └─ Ei  → NavigationService.navigateToNotAuthorizedView()
```

### Koodinäide

Reaalne kood `LocationView.vue` failist:

```js
beforeMount() {
  if (SessionStorageService.userIsAdmin()) {
    this.getCities()
    this.getLocationTransactionTypes()
  } else {
    NavigationService.navigateToNotAuthorizedView()
  }
},
```

Kontroll ise elab omakorda eraldi teenuses `SessionStorageService.js`, kus on lihtsad, taaskasutatavad meetodid:

```js
export default {
  userIsLoggedIn() {
    return sessionStorage.getItem('userId') !== null
  },

  userIsAdmin() {
    return sessionStorage.getItem('roleName') === 'admin'
  },
}
```

### Miks mitte kirjutada if-lauset otse komponenti?

Õpetaja rõhutab: kui `userIsAdmin()` juba tagastab `true`/`false`, ei ole vaja kirjutada `if (SessionStorageService.userIsAdmin() === true)` — see on üleliigne, sest meetod ise ongi juba tõeväärtus. Samuti on kasulik hoida "kas kasutaja on logitud sisse" ja "kas kasutaja on admin" loogika ühes kindlas failis (`SessionStorageService`), et seda ei peaks igas komponendis uuesti kirjutama.

## Navigeerimine kesksüsteemi kaudu (router.push, NavigationService) — `0:21:11` {#navigationservice}

Kui otsustus on tehtud ("kasutaja ei tohi siia"), on vaja kasutaja programmiliselt teisele lehele suunata.

### Selgitus

Vue Routeri objektil on meetod `push()`, mis võtab argumendiks marsruudi kirjelduse — soovitavalt **nime järgi**, mitte otse teekonna (path) järgi. Nime kasutamise põhjus: kui path (nt `/not-authorized`) kunagi muutub, jääb nimi (`notAuthorizedRoute`) samaks ja koodis ei pea midagi muutma — kõik viited jäävad kehtima, sest tee on defineeritud ühes kohas (`router/index.js`).

Selle asemel, et igas komponendis kirjutada `router.push({ name: '...' })` otse, luuakse eraldi teenus `NavigationService`, kuhu koguneb kogu rakenduse navigeerimisloogika.

### Koodinäide

```js
import router from '@/router/index.js'

export default {
  navigateToHomeView() {
    router.push({ name: 'homeRoute' })
  },

  navigateToAtmsView() {
    router.push({ name: 'atmsRoute' })
  },

  navigateToErrorView() {
    router.push({ name: 'errorRoute' })
  },

  navigateToNotAuthorizedView() {
    router.push({
      name: 'notAuthorizedRoute',
    })
  },
}
```

Nüüd saab iga komponent lihtsalt kirjutada `NavigationService.navigateToNotAuthorizedView()`, ilma et peaks teadma, milline on täpne route'i nimi või path.

### Päriselu analoogia

See on nagu maja siseses telefoniraamatus nime järgi helistamine, mitte otsenumbri peast meelespidamine — kui inimene vahetab numbrit (path muutub), jääb tema nimi (route name) kataloogis samaks ja kõik saavad talle ikka helistada.

## Meetodite järjekord ja koodi loetavus — `0:27:33` {#meetodite-jarjekord-arutelu}

Pärast turvakontrolli valmimist tekib teemaarutelu: kas meetodite järjekord failis on oluline?

### Selgitus

Tehniliselt ei oma järjekord absoluutselt mingit tähtsust — programm käivitub ikka õigesti, olenemata sellest, mis järjekorras meetodid failis kirjas on. Küll aga on järjekord oluline **koodilugeja** jaoks: kui meetodid, mis üksteist välja kutsuvad, asuvad üksteise lähedal, ei pea sa lakkamatult failis üles-alla kerima ja klõpsama, et aru saada, mida kood teeb.

Erinevatel keeltel/tavadel on erinevad konventsioonid — Java's on tavaks, et kõik `public` meetodid tulevad enne `private` meetodeid; JavaScript/Vue's ei ole nii ranget reeglit, kuid loogiline lähenemine on ikkagi kasulik.

### Päriselu analoogia

Õpetaja võrdleb seda riidekapi korrastamisega — mõnel inimesel on kõik läbisegi, mõnel on särgid värvi ja pikkuse järgi süsteemselt järjestatud. Tehniliselt töötab mõlemal juhul (särk on ikka olemas), aga süsteemne kapp teeb otsimise kiiremaks.

## FEB-11 – Task valmis, meetodite järjestamise praktika — `1:22:05` {#feb-11-jarjestamine}

Pärast pikemat arutelu näitab õpetaja praktikas, kuidas ta ise meetodeid **väljakutsumise hierarhia** järgi ümber tõstab.

### Selgitus

Meetod loetakse "väljakutsumise hierarhia" järgi: kõige tähtsam meetod (see, mida nupp otse käivitab, nt `addLocation()`) pannakse kõige ette. Seejärel otsitakse, mis meetodit see esimesena välja kutsub, ja tõstetakse see kohe selle järele. Nii jätkatakse rekursiivselt — iga meetod järgneb sellele, kes teda kutsub, ja meetodid, mida kasutab mitu erinevat "haru" (nt `resetErrorMessage()`, mida kutsub nii `login()` kui ka teised meetodid), jäetakse faili lõppu, kuna need on jagatud (shared) abimeetodid.

### Skeem

```
addLocation()                  ← peameetod (käivitub nupu klõpsuga)
 ├─ checkFormForErrors()       ← kutsutakse esimesena
 ├─ errorMessageIsEmpty()      ← kutsutakse teisena
 └─ handleAddLocationResponse()
      └─ resetAllFields()

...

resetSuccessMessage()          ← jagatud abimeetod, faili lõpus
resetErrorMessage()            ← jagatud abimeetod, faili lõpus
```

### Praktiline reegel

1. Leia meetod, mida kasutaja otseselt käivitab (nupuklõps, `beforeMount` jne).
2. Vaata, mida see meetod järgmisena välja kutsub — tõsta see kohe selle alla.
3. Kui üht abimeetodit kasutab mitu erinevat peameetodit, jäta see faili kõige lõppu.
4. Kasuta AI-assistenti (nt Claude) selle korrastuse tegemiseks, andes talle täpse juhise: *"palun järjesta meetodid väljakutsumise hierarhia järgi — loogiline tippsand, sellele järgnevad tema poolt otse kutsutud abimeetodid, ning kõige lõpus jagatud (shared) meetodid."*

## Task/tiketite kirjutamise kultuur ja meeskonnatöö — `0:42:23` {#tiketite-kultuur}

Enne praktilise osa jätkamist arutletakse tiketite (taskide) sisu üle laiemalt.

### Selgitus

Õpetaja jagab kahte äärmust: **"oneliner"** tiketid (üherealine pealkiri, mõni sõna kirjeldust) versus väga detailsed, skeemide ja piltidega lahti kirjutatud taskid. Tema kogemuse põhjal kirjutavad kogenud analüütikud tihti lühemaid taske, kuna nad eeldavad, et meeskond tunneb projekti juba läbi ja lõhki — algajad analüütikud aga kirjutavad detailsemalt, kuna nemad ise alles õpivad asja selgeks tegema.

Kesksed mõtted:
- **Tiketi eesmärk ei ole öelda igat üksikasja**, vaid anda arendajale piisavalt konteksti otsuste tegemiseks — spetsiifilised failinimed, muutujanimed jms jäävad arendaja enda otsustada.
- **Reaalses töös on suhtluskanalite arv oluline** — mida rohkem inimesi on kliendi ja arendaja vahel (analüütik, projektijuht jne), seda suurem tõenäosus, et info moondub või kaob teel.
- **Kursuse tegelik eesmärk pole projekti valmimine**, vaid tiimitöö, arutamine ja üksteiselt õppimine — üks õpilastest, kes tegi kogu frontendi AI-ga ühe käsuga ("one-shot") valmis, pidi oma töö nullist uuesti tegema, kuna see võttis teistelt meeskonnaliikmetelt võimaluse ise õppida.

### Päriselu analoogia

Sarnaneb "katkise telefoni" mänguga — mida rohkem inimesi info edastamise ahelas, seda rohkem see moondub, isegi kui igaüks püüab võimalikult täpselt edasi anda.

## Vastutustundlik AI kasutus arenduses — `1:07:23` {#ai-vastutus}

Õpetaja sõnastab selged reeglid AI-assistentide kasutamiseks kursuse projektides.

### Selgitus

Kesksed põhimõtted:

1. **Igast koodireast vastutad ikkagi ise.** Kui õpetaja küsib "mida see osa täpselt teeb?", ei ole vastuseks vastuvõetav "ei tea, AI tegi".
2. **Ükski "one-shot" (ühe käsuga terve funktsionaalsuse tegemine) pole aktsepteeritav õppimise kontekstis.** Isegi kui see on tehniliselt kiirem, jääb arusaam ja oskus omandamata.
3. **Ehita jupikaupa** — tee üks väike osa korraga valmis, kontrolli, kas see töötab ja kas käekiri (koodistiil) vastab sinu enda ootustele, alles siis liigu edasi.
4. **Kui AI kirjutab tundmatu süntaksi või võttega koodi, palu kohe selgitust** ("Palun tee sellest õppematerjal, selgita, mida see teeb ja kuidas see töötab") — mitte liikuda edasi enne, kui see on selge.
5. **Juhised (nt CLAUDE.md failid) kasvavad ajas** — kui AI teeb midagi, mis sulle ei meeldi, lisa juhistesse reegel, et ta seda tulevikus vältiks. Nii saab AI-d aja jooksul "vormida" sinu soovitud stiili järgi.

### Koodinäide

Õpetaja tõi näite oma isiklikust praktikast: kui meetodite järjekorda tuleb korduvalt korrastada, on mõistlikum kirjutada see projekti reeglitesse (nt CLAUDE.md faili), et AI teeks seda automaatselt iga kord, kui lisab uue meetodi — selle asemel, et iga kord uuesti sõnadega selgitada:

```
Kui lood uue meetodi, järgi seda hierarhiat:
1. Peameetod (see, mida kasutaja otse käivitab)
2. Tema poolt otse kutsutud abimeetodid
3. Kõige lõpus jagatud (shared) meetodid
```

### Miks see on oluline?

Kui projekti lasta täielikult AI-l "one-shotida" (kogu dokumentatsioon ette anda ja lasta korraga valmis teha), muutub tulemus praktiliselt loetamatuks — isegi tehniliselt korrektne kood võib olla nii teistsuguse "käekirjaga", et keegi ei suuda seda hiljem hooldada. Jupikaupa ehitamine tagab, et arendaja saab kogu aeg kontrolli ja arusaamise säilitada.

## Git: merge õpetaja harusse ilma checkout'ita — `1:45:19` {#git-merge}

Lühike praktiline Git-teema: kuidas viia oma valminud töö õpetaja põhiharusse.

### Selgitus

Varem tuli Git-is teha `checkout` sellele harule, kuhu soovid muudatusi merge'ida, ja alles siis käivitada merge-käsk. Tänapäevased IDE tööriistad (nt IntelliJ) võimaldavad seda teha otse graafiliselt, ilma harusid vahetamata — valid sihtharu ja käivitad merge'i sealtsamast.

### Oluline hoiatus

Kui keegi kogemata merge'iks otse õpetaja harusse, tekiks probleeme kogu kursuse jaoks (õpetaja mainib, et keegi pole seda viga siiani teinud, "mis on veidi kahju" — see on nali, mitte julgustus seda proovida).

## VEB-12 – Modal komponendi kontseptsioon ja riskid — `1:48:11` {#modal-kontseptsioon}

Pärast lõunapausi algab uus task (VEB-12): pangaautomaadi asukoha info kuvamine **modalina** (hüpikaknana).

### Selgitus

**Modal** on aken, mis avaneb olemasoleva lehe *peale*, ilma et kasutaja liiguks uuele lehele. See annab paindlikkust — ei pea iga väikese info jaoks looma eraldi vaadet ja marsruuti.

Modalidel on aga ka omad riskid, millega tuleb arvestada:

- **Mobiilis toimivad modalid tihti halvemini** — võid kogemata mööda klõpsata ja aken sulgub, paigutus võib minna "nihu".
- **Brauseri "tagasi" nupp ei sulge modali** — modal ei muuda URL-i, seega tagasi-nupp viib kasutaja hoopis eelmisele lehele, mis võib olla ootamatu käitumine.
- **Ära pane modali sisse liiga suurt/keerulist vormi** — kui sisu on väga mahukas, on mõistlikum teha selle jaoks eraldi vaade.
- **Ära ava modali seest teist modali** — see tekitab kasutajale segadust ja halba kasutuskogemust.

### Päriselu analoogia

Modal on nagu sahtel, mille tõmbad lauast lahti, et midagi kiirelt vaadata, ilma et peaksid kogu tuppa (lehele) minema — aga kui sahtlisse üritad panna kogu kapi sisu, ei ole see enam mugav ega otstarbekas.

## Korduvkasutatav BaseModal ja Vue slotid ("pesad") — `1:55:28` {#baseModal-slotid}

Selle asemel, et kirjutada iga modali jaoks uuesti kogu funktsionaalsus (näita/peida, sulgemisnupp, tausta hallitamine), luuakse **üks korduvkasutatav põhikomponent**, mille sisse saab paigutada erineva sisu.

### Selgitus

Vue's on selle jaoks olemas **slot** (eesti keeles "pesa" — nali klassis oli, et see kõlab nagu "slott/šlott") — koht komponendi malli (template) sees, kuhu väljastpoolt saab HTML-sisu sisestada. See on nagu tühi pesa linnu jaoks: raamistik (pesa ise) on alati sama, aga selle sisse saab panna erinevaid asju.

Ilma slotideta saaks komponendile anda ainult **props'e** — lihtsaid väärtusi (tekst, number, boolean). Slotid võimaldavad anda kaasa terve HTML-struktuuri (ikoonid, nupud, vormid, mis iganes).

### Skeem

```
BaseModal.vue (raamistik, korduvkasutatav)
┌─────────────────────────────┐
│  <slot name="title">        │  ← väljastpoolt antav pealkiri
├─────────────────────────────┤
│  <slot name="body">         │  ← väljastpoolt antav sisu
├─────────────────────────────┤
│  <slot name="buttons">      │  ← väljastpoolt antavad nupud
│    (vaikimisi: "Sulge")     │     (kui midagi ei anta, kasutatakse vaikeväärtust)
└─────────────────────────────┘
```

### Koodinäide

Reaalne `BaseModal.vue` komponent koodibaasist:

```vue
<script>
export default {
  name: 'BaseModal',
  props: {
    isOpen: {
      type: Boolean,
      default: false,
    },
  },
  emits: ['event-modal-closed'],
  methods: {
    close() {
      this.$emit('event-modal-closed')
    },
  },
}
</script>

<template>
  <div v-if="isOpen">
    <div class="modal d-block" tabindex="-1" @click.self="close">
      <div class="modal-dialog">
        <div class="modal-content">
          <div class="modal-header">
            <h5 class="modal-title">
              <slot name="title"></slot>
            </h5>
            <button type="button" class="btn-close" @click="close" />
          </div>
          <div class="modal-body">
            <slot name="body"></slot>
          </div>
          <div class="modal-footer">
            <slot name="buttons">
              <button type="button" class="btn btn-secondary" @click="close">Sulge</button>
            </slot>
          </div>
        </div>
      </div>
    </div>
    <div class="modal-backdrop show" />
  </div>
</template>
```

Kõige olulisemad detailid:

- **`isOpen` prop** kontrollib, kas modal üldse kuvatakse (`v-if="isOpen"`). Kui väärtust kaasa ei anta, on vaikeväärtus `false`.
- **`close()` meetod** ei sulge modali ise, vaid saadab sündmuse (`emit`) üles vanemkomponendile — vanemkomponent otsustab, mis tegelikult juhtub (nt muudab `isOpen` väärtuseks `false`).
- **Nimega slotid** (`name="title"`, `name="body"`, `name="buttons"`) võimaldavad täpselt öelda, millisesse kohta mingi sisu läheb.
- **`buttons` slotil on vaikesisu** (default content) — kui kasutaja ei anna oma nuppe, kuvatakse automaatselt "Sulge" nupp. Kui aga sisu antakse, sõidetakse vaikesisust üle (see asendatakse täielikult).

## Slot vs Props – millal kumbagi valida — `2:36:47` {#slot-vs-props}

Video lõpus arutletakse, millal peaks komponendi liidesel kasutama slotti ja millal lihtsat propsi.

### Selgitus

Reegel on lihtne: **kui sisu on alati lihtne tekst/väärtus ja seda pole vaja täiendada HTML-elementidega, piisab propsist.** Kui aga soovid tulevikus (või juba praegu) lisada sisusse ikoone, nuppe, vorme või muud struktureeritud HTML-i, on vaja slotti.

Näiteks: kui modali pealkiri on **alati** ainult tavaline tekst, piisaks lihtsast propsist (`title="Minu pealkiri"`). Kui aga soovid vahel pealkirja kõrvale panna ka ikooni või erilise stiili, on parem kasutada slotti, mis lubab suvalist HTML-sisu.

### Tuleviku vs praeguse vajaduse tasakaal

Õpetaja toob näite oma kogemusest Eesti Energias — üks kolleeg tegi lihtsa andmebaasipäringute käitlemise asemel (mida Spring Boot juba pakub) täiesti uue, väga abstraktse omaenda lahenduse "juhuks kui tulevikus vaja läheb". Tulemus: ainult tema teadis, kuidas see taustal töötab, ja teised meeskonnaliikmed pidid seda õppima kasutama.

Sellest tuleneb üldine põhimõte:

> **Ära ehita abstraktsiooni "igaks juhuks", kui pole reaalset alust arvata, et seda vaja läheb.** Aga kui on üsna tõenäoline, et paindlikkust läheb peagi vaja, on mõistlik teha see otsus juba varakult (nagu slotiga modal), sest hilisem ümberehitamine on kallim.

See on tunnetuse küsimus — kood peab olema piisavalt loetav ja lihtne, aga samas ei tohi olla nii jäik, et iga väike muudatus nõuab suurt ümberkirjutamist.

### Koodinäide otsustuspunktist

Videos arutati konkreetselt, kas modali pealkiri (`title` slot) võiks selle asemel olla lihtne prop:

```vue
<!-- Variant A: prop (lihtsam, aga piiratud - ainult tekst) -->
<BaseModal :title="'Asukoha info'" />

<!-- Variant B: slot (paindlikum, lubab ikoone/HTML-i) -->
<BaseModal>
  <template #title>
    <PhMapPin :size="20" /> Asukoha info
  </template>
</BaseModal>
```

Kursuse projektis valiti slot-lahendus, kuna see annab tulevikus rohkem paindlikkust ilma, et peaks komponendi liidest hiljem muutma.
