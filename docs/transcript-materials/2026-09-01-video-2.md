## 1. Uue teenuse loomine — LocationService ja Axiose `params` — `0:00:43`

Video jätkab otse eelmisest sessioonist — tabel on visuaalselt olemas, aga andmeteta. Nüüd tuleb luua uus service-fail pangaautomaatide asukohtade jaoks.

### Selgitus

Nagu `CityService.js` tegeleb linnadega, peaks asukohtadega tegelema eraldi fail — **mitte** `CityService` alla, sest see on loogiliselt vale koht:

```
CityService  → linnadega seotud tegevused (linnade toomine, lisamine, muutmine)
LocationService → asukohtadega seotud tegevused (see on uus, eraldi fail)
```

Failinimede puhul eelistatakse **ainsust** (`LocationService`, mitte `LocationsService`), kuna nimi viitab teenusele, mis tegeleb ühe entiidi tüübiga.

### Query parameeter Axiose `params`-objektiga

Eelmises videos räägiti query-parameetritest teoreetiliselt (URL-i `?cityId=2` osa). Nüüd tuli esimest korda päris põhjus, miks seda vaja on: linna järgi filtreerimine.

Axios pakub selleks teist argumenti — **konfiguratsiooni objekti**, mille sees on `params`:

```js
// frontend/src/services/LocationService.js
import axios from 'axios'

export default {
  getAtmLocations(cityId) {
    return axios.get('/api/atm/locations', {
      params: {
        cityId: cityId,
      },
    })
  },
}
```

Axios võtab `params`-objekti ja lisab selle URL-ile automaatselt query-stringina (nt `?cityId=2`) — pole vaja ise stringi kokku panna (`'?cityId=' + cityId`), mis oleks vigadele altim.

### Miks mitte käsitsi stringi kokku panna?

```
❌ Käsitsi: axios.get('/api/atm/locations?cityId=' + cityId)
✅ Objektiga: axios.get('/api/atm/locations', { params: { cityId: cityId } })
```

Käsitsi variant töötaks samuti, aga on vigadele altim ja vähem loetav — eriti kui parameetreid on mitu. `params`-objekti kasutamine on ka Swaggeri/Stoplighti "piibliga" kooskõlas, sest see peegeldab otse, mida teenus ootab.

## 4. Return puudumine — kadunud Promise — `0:25:40`

Video demonstreerib klassikalist algajaviga: kui service-meetodi ette unustatakse `return`, kaob kogu Promise.

### Selgitus

```js
// ❌ Vale — puudub return
getAtmLocations(cityId) {
  axios.get('/api/atm/locations', { params: { cityId: cityId } })
}
```

IDE annab siin hoiatuse: *"Promise returned from get is ignored"* — see tähendab, et Axiose tagastatud Promise objekt "sureb" meetodi sees, ilma et keegi seda kunagi kätte saaks.

### Skeem

```
Ilma return-ita:
  axios.get(...) → Promise objekt tekib → EI LÄHE KUHUGI → sureb meetodi sees

Return-iga:
  axios.get(...) → Promise objekt tekib → RETURN → jõuab väljakutsujani
```

### Koodinäide (õige)

```js
// ✅ Õige — return olemas
getAtmLocations(cityId) {
  return axios.get('/api/atm/locations', {
    params: { cityId: cityId },
  })
},
```

## 8. Kaks `v-for` tsüklit — location'id ja transactionType'id — `0:58:09`

### Skeem

```

```

```html
  <tr v-for="location in locations" :key="location.locationId">
    <td>{{ location.cityName }}</td>
    <td>{{ location.locationName }}</td>
    <td>
      <div v-for="transactionType in location.transactionTypes" :key="transactionType.transactionTypeId">
        {{ transactionType.transactionTypeName }}
      </div>
    </td>
  </tr>
</tbody>
```

## 9. `v-for` ja `v-if` ei tohi olla samal elemendil — `1:13:39`

Kuna teenuseid tuleb kuvada ainult siis, kui `isAvailable` on `true`, üritati algul panna `v-for` ja `v-if` samale elemendile — see aga ei tööta.

### Selgitus

```
❌ Ei tööta: <div v-for="..." v-if="...">
✅ Töötab: lisa v-if lapselemendile (eraldi div tsükli sees)
```

Vue's ei saa `v-for` ja `v-if` koos samal elemendil kasutada (varasemates Vue versioonides oli ka prioriteedireegel, mis tegi selle veelgi eksitavamaks). Lahendus on lisada eraldi element sisse:

### Koodinäide

```html
<div v-for="transactionType in location.transactionTypes" :key="transactionType.transactionTypeId">
  <div v-if="transactionType.isAvailable">
    {{ transactionType.transactionTypeName }}
  </div>
</div>
```

### Levinud algajaviga

```js
// ❌ Vale: võrdlus true-ga, kui väärtus on juba boolean
v-if="transactionType.isAvailable === true"

// ✅ Õige: boolean väärtus on juba iseenesest tingimus
v-if="transactionType.isAvailable"
```

Kui muutuja väärtus on juba `true`/`false` (boolean), pole vaja seda uuesti `true`-ga võrrelda — see on üleliigne ja segadust tekitav (sisuliselt "kas true on true?").

```html
<CitiesDropdown :cities="cities" @event-new-city-selected="reloadLocationsTable" />
```

### Kellele tütar, kellele ema

Meetodite ja muutujate nimetamine on osaliselt **maitseasi** — arendajate vahel võib alati tulla arutelu, kas mingi nimi on parim. Õpetaja soovitus: kui argument nime kasuks pole väga tugev, ei tasu selle üle liiga palju vaielda — see on koht, kus nooremad arendajad vahel tarbetult vastu vaidlevad.

## 12. String vs. number — tüübiviga võrdluses — `1:54:39`

Kui `CitiesDropdown` saadab `$event.target.value`, on selle väärtus alati **string**, isegi kui HTML-elemendi `option`-i `value` on kirjutatud numbrina.

### Selgitus

```
HTML select option value="2"  →  JavaScript saab kätte:  "2"  (string, mitte number 2!)
```

See tekitas vea, kus `LocationService`-i `if`-kontroll (`cityId === 0`, `cityId === 2` jne) alati ebaõnnestus, kuna string `"2"` ei võrdu numbriga `2` kolmese võrdlusmärgiga (`===`).

### Skeem

```
cityId tuleb sisse:      "0", "2", "3"   (string)
if kontroll ootab:        0,   2,   3    (number)
Kolmene võrdlus (===):   FALSE alati, sest tüübid erinevad
```

### Miks see raske avastada oli?

Viga oli varjatud, sest `LocationService`-is oli näiliselt korrektne kood (`if (cityId === 0) {...}`), aga kuna sisend oli tegelikult string, ei sobinud ükski tingimus kokku ja alati jõuti `else`-haru (viga 404).

## 13. `Number()` konstruktor ja tüübiteisendus — `1:57:57`

Lahenduseks oli teisendada string number'iks juba selle **tekkimise kohas** — seal, kus `$event.target.value` kätte saadakse.

### Selgitus (Java analoogia konstruktoriga)

Video kasutas Java klassi analoogiat, et selgitada, mis on konstruktor: meetod, mis loob objekti ja täidab selle väljad sissetuleva sisuga (nt `new Student(firstName)`). JavaScriptis on sarnaselt olemas sisseehitatud "konstruktorid" primitiivsete tüüpide jaoks.

### Koodinäide (enne)

```html
<select @change="$emit('event-new-city-selected', $event.target.value)">
```

### Koodinäide (pärast — tüübiteisendus)

```html
<select @change="$emit('event-new-city-selected', Number($event.target.value))">
```

`Number(...)` võtab sisse mistahes väärtuse (siin: stringi) ja tagastab selle **numbrina**. See on lühike ja loetav viis stringi numbriks teisendamiseks.

### Päriselu analoogia

```
HTML vormide väljad (isegi type="number") annavad JavaScriptile alati stringi.
See on nagu kviitung poest — kõik hinnad on trükitud tekstina paberile,
isegi kui need tähistavad numbreid. Enne arvutamist tuleb need "lugeda" numbriteks.
```

## 14. Kolmene (`===`) vs. kahene (`==`) võrdlus — `2:07:44`

Video demonstreeris ka teist lahendusviisi — kasutada kahest võrdlusmärki (`==`), mis teeb automaatse tüübiteisenduse.

### Selgitus

```
===  (kolmene) — range võrdlus: tüüp JA väärtus peavad kokku minema
==   (kahene)  — lõdvem võrdlus: JavaScript teisendab tüübid ise ühesuguseks enne võrdlemist
```

### Koodinäide

```js
"2" === 2  // false (erinevad tüübid)
"2" == 2   // true  (JS teisendab automaatselt)
```

### Miks `===` ikkagi eelistatud on

Kuigi `==` "lahendaks" probleemi automaatselt, on see **libe tee** — see peidab endas ootamatuid käitumisi (nt võrdlemine `>`/`<` operaatoritega samuti teeb varjatud teisendusi). Parem on probleem lahendada juures, kus see tekib (teisendades väärtuse õigeks tüübiks kohe selle allikas), mitte peita seda lõdva võrdlusega.

**Java** ei luba selliseid asju üldse — see annab kompileerimisvea, kui üritada võrrelda erinevaid tüüpe (nt `String` ja `int`). TypeScript pakub sarnast tüübikindlust JavaScripti peale.

## 15. Backendi vea simuleerimine Stoplightis (Prefer header) — `1:51:21`

Kuna Stoplight (mock-server) vastab vaikimisi alati esimese näidisega, tuli õpetada, kuidas simuleerida erinevaid stsenaariume (sh vigu) sõnumi headeri kaudu.

### Koodinäide

```js
// frontend/src/services/LocationService.js
getAtmLocations(cityId) {
  // todo: Kustuta prefer osa ära, kui enam Stoplight mock back ei kasuta
  let preferValue

  if (cityId === 0) {
    preferValue = 'code=200, example=0'
  } else if (cityId === 2) {
    preferValue = 'code=200, example=2'
  } else if (cityId === 3) {
    preferValue = 'code=200, example=3'
  } else {
    preferValue = 'code=404, example=1'
  }

  return axios.get('/api/atm/locations', {
    headers: {
      Prefer: preferValue,
    },
    params: {
      cityId: cityId,
    },
  })
},
```

### Selgitus

`Prefer` header on Stoplighti spetsiifiline mehhanism (mitte üldine HTTP-standard), mis ütleb mock-serverile, millist staatuskoodi ja näidisvastust ta peaks andma. See kood on **ajutine** (märgitud `todo`-kommentaariga) — päris backendi vastu töötades pole seda vaja, sest server ise otsustab vastuse sisu tegelike andmete põhjal.

## 16. Veakäsitlus — 404 No Location Found — `2:13:46`

Kui otsitud linnast (nt Pärnu) ei leitud ühtki pangaautomaati, tagastab backend taotluslikult **404 vea** (mitte tühja massiivi, mis on tavapärasem muster).

### Koodinäide

```js
// AtmsView.vue
data() {
  return {
    errorMessage: '',
    errorResponse: {
      message: '',
      errorCode: '',
    },
    // ...
  }
},
methods: {
  handleGetLocationsErrorResponse(error) {
    this.errorResponse = error.response.data

    if (error.response.status === 404 && this.errorResponse.errorCode === 'NO_LOCATION_FOUND') {
      this.errorMessage = this.errorResponse.message
      this.locations = []
    }
  },
}
```

### Selgitus

Kontrollitakse **kahte tingimust korraga** `&&`-ga:
1. HTTP staatuskood on `404`
2. Vea sees olev äriloogiline `errorCode` on täpselt `'NO_LOCATION_FOUND'`

See on turvalisem kui kontrollida ainult staatuskoodi, sest 404 võib tähendada ka muid asju (nt vale URL). Konkreetne `errorCode` tuvastab täpselt, mis liiki viga see on.

## 18. Vea sisu reset — algseisu taastamine — `2:38:20`

Probleem: kui kasutaja valib linna, mille kohta tuleb viga (nt Pärnu), ja seejärel valib teise linna, mille kohta viga ei tule (nt Tallinn), jääb vana veateade endiselt nähtavale.

### Selgitus

```
Reaktiivsus ei "puhasta" ise vana väärtust —
kui muutuja väärtust ei muudeta uuesti, jääb see püsima.
```

Vue ei tea automaatselt, et vana viga enam ei kehti — programmeerija peab ise selle **tagasi lähtestama** enne uue päringu tegemist.

### Koodinäide

```js
getLocations() {
  this.errorMessage = ''  // reset enne iga uut päringut
  LocationService.getAtmLocations(this.cityId)
    .then((response) => this.handleGetLocationsResponse(response))
    .catch((error) => this.handleGetLocationsErrorResponse(error))
    .finally()
},
```

### Miks reset just siin, mitte nupu vajutuse peal?

Kõige lihtsam ja töökindlam koht on **enne** uue päringu tegemist, mitte hiljem tingimuslikult — nii on garanteeritud, et vana viga eemaldub alati, olenemata sellest, kas uus päring õnnestub või ebaõnnestub uuesti.

## 19. Uue komponendi ekstraktimine — LocationsTable — `2:40:04`

```js
// LocationsTable.vue
export default {

  props: {
    locations: {},
  },
}
```

### Selgitus — mida propsina üle anda?

Küsimus oli, mitu propsi see komponent vajab. Kuna `transactionTypes` on juba `location`-objekti sees (`location.transactionTypes`) ja `location` on omakorda `locations`-massiivi sees, on vaja anda üle **ainult üks props**: `locations`.

```
locations (props)
  └─ location (v-for muutuja)
       └─ transactionTypes (juba location'i küljes, ei vaja eraldi propsi)
```

## 21. Projekti planeerimine — MVP ja tiimitöö nõuded — `2:49:17`

Video lõpus antakse üldisi juhiseid tulevaste grupiprojektide planeerimiseks.

### Selgitus — töö prioriteedid

```
1. CREATE-tegevused (postitegevused) — kõige väärtuslikumad, annavad süsteemile sisu
2. READ-tegevused — andmete kuvamine (võib alustada juba loodud andmetega)
3. UPDATE/DELETE — vähem kriitilised, tehakse viimasena
```

Loogika: kui saab andmeid **lisada** (create), saab kohe kasutada seda sama liidest testimiseks ja andmebaasi täitmiseks — see annab kiiremini nähtava tulemuse kui alustada kuvamisest (mille jaoks peab andmed käsitsi eelnevalt sisestama).

### MVP (Minimum Viable Product)

```
MVP = miinimum elujõuline toode
Otsustage ette, milline on kogu süsteemi kõige väärtuslikum tuumfunktsionaalsus.
Tehke see esimesena valmis, alles siis lisage "nice to have" funktsioone.
```

### Tiimitöö nõue

**Kõik tiimiliikmed peavad arendama nii frontendi kui backendi** vähemalt korra projekti käigus — see tagab, et tiimisiseselt on igaühel piisavalt konteksti, et üksteist aidata. Kui üks inimene teeb ainult fronti ja teine ainult backendi, tekib olukord, kus keegi tiimist ei saa toppama jäädes teiselt tiimiliikmelt abi küsida.
