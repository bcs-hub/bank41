## Swagger / OpenAPI: veebiteenuse "piibel" — `0:03:27` {#swagger-openapi}

### Selgitus

**Swagger** (kaks G-tähte) on tehnoloogia, mis on tihedalt seotud **OpenAPI** standardiga — see kirjeldab veebiteenuseid (REST API-sid) struktureeritud JSON-formaadis. Swagger'i logo (kaks nurksulgu ja kolm punkti vahel) viitabki JSON-ile.

See dokumentatsioon on **leping (contract)** kliendi ja serveri vahel — kokkulepe selle kohta:
- Mis teenused on olemas
- Kuidas nende poole pöörduda (URL, HTTP meetod)
- Mis sisendid on vajalikud ja mis tüüpi
- Mis vastuse teenus tagastab
- Mis veaolukorrad on võimalikud

Õpetaja kutsub seda **"piibliks"** — see on dokument, mille vastu iga kord kontrollitakse, kui midagi programmeeritakse. Kui programmeerid täpselt selle spetsifikatsiooni järgi, ei teki vigu; kui hakkad "peast" andmeid saatma, tekivad väikesed vead, mida on hiljem raske avastada.

### Päriselu analoogia

Swagger-dokumentatsioon on nagu rahvusvaheline pangandusleping kahe panga vahel — see kirjeldab täpselt, milliseid sõnumeid tohib saata, mis vormis need peavad olema, ja mida vastuseks oodata. Ilma sellise lepinguta peaks iga integratsioon "ise ära arvama", mida teine pool tahab, mis viib vigadeni.

## Meetodi nimetamine HTTP meetodi järgi (postLoginRequest) — `0:18:39` {#meetodi-nimetamine}

### Selgitus

Kui luuakse meetod, mis saadab HTTP sõnumi, soovitab õpetaja panna meetodi nimeks **kombinatsioon HTTP meetodist ja URL-i osast** — see teeb meetodi nime kohe informatiivseks, ilma et peaks meetodi sisu lugema.

Muster: `<httpMeetod><UrlOsa>Request`

- `GET` → `get...`
- `POST` → `post...`
- `PUT` → `put...`
- `DELETE` → `delete...`

### Koodinäide (`frontend/src/services/LoginService.js`)

```js
import axios from "axios";

export default {
  postLoginRequest(loginRequest) {
    return axios.post('/api/login', loginRequest)
  },
}
```

Nimi `postLoginRequest` ütleb kohe: see on **POST** sõnum, mis läheb **login** teele, ja see võtab sisse midagi, mida nimetatakse **request**'iks (sõnum, mis läheb "välja").

### Päriselu analoogia

See on nagu kirjaümbrike märgistamine kirja saatmisel: "Väljaminev kiri — Tallinn" ütleb kohe, mis tüüpi kiri see on ja kuhu see läheb, ilma et peaksid ümbrikku avama.

## Meetodid ei tea oma välisest elust midagi (skoop) — `0:20:10` {#meetodid-skoop}

### Selgitus

Meetodid ja funktsioonid on üldiselt disainitud nii, et need **ei tea midagi väljaspool ennast toimuvast** — nad on iseseisvad koodilõigud, mida saab kasutada suvalisest kohast koodibaasis, ilma et neil oleks mingit seotust kellegagi.

Õpetaja võrdleb seda Vue komponentidega: "nad on orvud" — meetodit ei "kuulu" kellelegi, seda saab välja kutsuda kust iganes (kui see on korrektselt eksporditud/imporditud).

**Ainus info**, mida meetod teab, on:
1. See, mida meetod ise oma sees defineerib
2. See, mis talle **parameetrina** kaasa antakse

### Päriselu analoogia

Meetod on nagu kohvimasin — masin ei tea, kes seda kasutab ega mis toas ta seisab. Ta teab ainult: kui sisse anda vesi ja kohvipulber (parameetrid), tuleb välja kohv (tulemus). See ei sõltu millestki muust ruumis.

## Parameeter: kuidas anda meetodile infot kaasa — `0:21:52` {#parameeter}

### Selgitus

**Parameeter** on muutuja, mis eksisteerib ainult meetodi sulgude vahel — see on viis, kuidas meetodile "väljast" infot sisse anda. Kui meetod peab midagi saatma serverile, peab see saama teada, **mida** saata — see antakse kaasa parameetrina.

Nimi valitakse loogiliselt lähtudes sellest, mis andmed sinna lähevad — antud juhul `loginRequest`, sest sama nimi kasutati juba `data` blokis muutuja jaoks, mis hoiab kasutajanime ja parooli.

### Koodinäide

```js
// meetod, mis võtab sisse parameetri "loginRequest"
postLoginRequest(loginRequest) {
  return axios.post('/api/login', loginRequest)
}

// väljakutsumisel antakse kaasa reaalne objekt
LoginService.postLoginRequest(this.loginRequest)
```

### Päriselu analoogia

Parameeter on nagu tellimisleht restoranis — kelner (meetod) ei tea ise, mida sa tahad süüa, aga kui sa täidad tellimislehe (parameeter) ja annad selle üle, teab ta täpselt, mida kööki edastada.

## Axios post: url, request body, config — `0:24:23` {#axios-post}

### Selgitus

`axios.post()` võtab sisse kuni kolm parameetrit:

1. **URL** (`String`) — kuhu sõnum saadetakse
2. **Request Body** (mis tahes tüüp) — mis andmed sõnumiga kaasa lähevad
3. **Config** (valikuline, objekt) — lisaseadistused (nt query parameetrid, päised)

Swagger'i dokumentatsioon ütles täpselt, mida `/api/login` ootab: `{ username: String, password: String }` — see teave läks otse koodi.

### Koodinäide

```js
axios.post('/api/login', this.loginRequest)
//          ^URL          ^request body (JSON kehana)
```

## Promise ja `return`: miks objekt muidu kaob — `0:27:15` {#promise-return}

### Selgitus

`axios.post()` tagastab **Promise objekti** — see on lubadus, et vastus (või viga) tuleb kunagi hiljem. Kui meetod ise **ei tagasta** seda Promise'i (`return` puudub), kaob see objekt ära, kui meetodi täitmine jõuab lõpusulguni — see on muutujate/objektide **elutsükkel (lifecycle)**:

> Kõik, mis tekib meetodi sees, elab alates loomise hetkest kuni koodiploki lõpuni. Kui midagi ei tagastata (`return`), see "sureb" seal ära.

**`return`** annab objekti edasi sinna, kust meetodit välja kutsuti — nii saab väljakutsuja Promise'iga edasi töötada (nt lisada `.then()`).

### Koodinäide

```js
// ILMA returnita — Promise kaob ära, väljakutsuja ei saa midagi teha
postLoginRequest(loginRequest) {
  axios.post('/api/login', loginRequest)  // objekt tekib ja kaob
}

// ÕIGE — return annab Promise'i edasi
postLoginRequest(loginRequest) {
  return axios.post('/api/login', loginRequest)
}
```

### Skeem

```
postLoginRequest(loginRequest) {
   │
   │  axios.post(...) tekitab Promise
   ▼
  [Promise objekt]
   │
   │  RETURN — objekt "põgeneb" välja enne kui koodiplokk sureb
   ▼
väljakutsuja saab Promise'i kätte ja saab lisada .then()
```

### Päriselu analoogia

`return` on nagu käsi, mis ulatab paki üle uksepakule enne, kui tuba (meetod) suletakse ja koristatakse ära. Kui käsi ei ulata pakki üle, jääb see suletud tuppa ja kaob koos kogu sisustusega.

## Service-kiht: `LoginService.js` eraldi failina — `0:35:14` {#service-kiht}

### Selgitus

Sõnumite saatmise loogika koondatakse eraldi **service-failidesse** (nt `LoginService.js`), et:

1. Hoida sõnumi saatmise loogika ühes kindlas kohas — kõik sama teema (nt sisselogimine) sõnumid ühes failis.
2. Muuta `LoginView.vue` fail loetavamaks — see loeb nagu "raamat", mitte tehniliste sõnumidetailide segapuder.
3. Võimaldada sama sõnumit taaskasutada mitmest kohast koodibaasis.

Fail eksporditakse `export default { ... }` mustriga ja imporditakse sihtkohas.

### Koodinäide (`frontend/src/services/LoginService.js`)

```js
import axios from "axios";

export default {
  postLoginRequest(loginRequest) {
    return axios.post('/api/login', loginRequest)
  },
}
```

Kasutamine `LoginView.vue`-s:

```js
import LoginService from '@/services/LoginService.js'

// ...

LoginService.postLoginRequest(this.loginRequest)
  .then((response) => this.handleLoginResponse(response))
  .catch(() => alert("Catch"))
  .finally()
```

### Päriselu analoogia

Service-fail on nagu pangaosakond, mis tegeleb ainult ühe konkreetse teenusega (nt "sisselogimise osakond") — kõik sellega seotud toimingud käivad läbi ühe konkreetse ukse, mitte laiali erinevates hoonetes.

## FEB-7: `.then()` / `.catch()` / `.finally()` ehitamine — `0:39:15` {#feb-7}

### Selgitus

Praktilises osas ehitati `login()` meetod uuesti, seekord kasutades eraldi service-faili. Peale sõnumi saatmist ketistatakse kolm plokki:

- **`.then()`** — käivitub, kui vastus on **edukas** (kõik peale 4xx/5xx staatuste)
- **`.catch()`** — käivitub, kui staatus on **4xx** või **5xx**
- **`.finally()`** — käivitub **alati**, sõltumata tulemusest

Õpetaja rõhutab, et need kolm on loogiliselt nagu `if`/`else`/lõpp-lause kombinatsioon — `.then()` ja `.catch()` on teineteist välistavad, `.finally()` käivitub mõlemal juhul.

### Koodinäide (`frontend/src/views/LoginView.vue`)

```js
login() {
  this.resetErrorMessage()
  if (this.allFieldsHaveInput()) {
    this.startSpinner()

    LoginService.postLoginRequest(this.loginRequest)
      .then((response) => this.handleLoginResponse(response))
      .catch(() => alert("Catch"))
      .finally()
  } else {
    this.errorMessage = 'Täida kõik väljad'
  }
},
```

## Response handleri meetod ja "kollane pirn" — `0:59:31` {#response-handler}

### Selgitus

`.then()` sisu kirjutatakse tavaliselt kohe **eraldi meetodisse** (mitte pikalt inline `.then()` sees), et vältida "jube pikka" koodilõiku ketistuse sees. Kasulik töövõte: kirjuta esmalt meetodi **väljakutse**, isegi kui meetodit veel ei eksisteeri — IDE märgib selle **kollase joone/kollase pirniga**, ja `Alt+Enter` pakub automaatselt "loo see meetod" valikut.

See on tahtlik programmeerimisvõte: kirjutad kõigepealt "mida ma tahan teha" (väljakutse), ja lased IDE-l genereerida meetodi tühja põhja, mille sisu täidad seejärel.

### Koodinäide (`frontend/src/views/LoginView.vue`)

```js
handleLoginResponse(response) {
  this.loginResponse = response.data
  this.saveLoginResponseInfoToSessionStorage()
  NavigationService.navigateToAtmsView()
},

saveLoginResponseInfoToSessionStorage() {
  sessionStorage.setItem('userId', this.loginResponse.userId)
  sessionStorage.setItem('roleName', this.loginResponse.roleName)
},
```

Response objekti sees on palju infot (staatus, päised jne), aga meid huvitab enamasti ainult **`response.data`** osa — reaalne sisu, mille server saatis.

### Päriselu analoogia

"Kirjuta väljakutse enne meetodit" on nagu koosoleku kutse saatmine enne, kui tead täpselt, mida koosolekul räägitakse — kutse (väljakutse) määrab ära, et miski peab toimuma, ja sa täidad detailid (meetodi sisu) hiljem.

## `NavigationService.js`: navigeerimise eraldamine eraldi teenusesse — `1:32:47` {#navigation-service}

## Koodi lugemine "raamatuna" — meetodinimede tähtsus — `1:41:12` {#raamatuna-lugemine}

### Selgitus

Õpetaja rõhutab olulist koodi lugemise põhimõtet: **loe meetodit meetodi kaupa, ülevalt alla**, mitte ära hüplemata detailidesse. Kui iga koodilõik on hästi nimetatud (nagu `resetErrorMessage()`, `startSpinner()`, `saveLoginResponseInfoToSessionStorage()`), räägib kood iseendaga nagu raamat — sa saad tervikpildist aru **ilma** iga meetodi sisu lugemata.

Kui tahad süveneda ühte konkreetsesse detaili, "lähed binokliga sügavamale" (IDE-s `Ctrl+B` / `Ctrl+klõps` meetodi definitsioonile hüppamiseks), aga alles siis, kui see on **päriselt vajalik**.

### Skeem

```
login() {
  resetErrorMessage()           ← "nulli veateade"
  if (allFieldsHaveInput()) {   ← "kas väljad on täidetud?"
    startSpinner()              ← "käivita spinner"
    LoginService.postLoginRequest(...) ← "saada sisselogimise sõnum"
      .then(handleLoginResponse)  ← "kui õnnestub, käsitle vastust"
      .catch(...)                 ← "kui ebaõnnestub"
      .finally(...)                ← "igal juhul lõpuks"
  } else {
    errorMessage = 'Täida kõik väljad'
  }
}
```

Iga rida on **loetav lause**, mitte tehniline detail — nagu lugeda raamatu sisukorda enne peatükkidesse süvenemist.

### Päriselu analoogia

See on nagu otsimine merel — kui pead leidma hädalise, ei vaata sa esmalt läbi binokli iga lainet üksipulgi, vaid skaneerid kõigepealt kogu horisonti (loed kõik meetodinimed) ja alles siis, kui midagi paistab huvitav, võtad binokli (`Ctrl+B`) ja süvened täpsemalt.

## Menüü dünaamiline muutmine: sisse logitud vs mitte — `1:53:56` {#menuu-dunaamiline}

### Selgitus

Praktiline ülesanne: menüüs peab **"Sisselogimine"** link kaduma pärast sisselogimist ja selle asemele peab ilmuma **"Logi välja"** link. Kaks linki peavad olema **teineteist välistavad** — kunagi mõlemad korraga nähtaval.

Selleks kasutati:
1. `<div>` gruppi ümber mõlema lingi, et neid koos kontrollida
2. `v-if` / `v-else` konstruktsiooni, mis tagab, et alati näidatakse ainult **üht** kahest valikust
3. Andmemuutuja (`isLoggedIn`), mis hoiab hetkeseisu

Õpetaja soovitab **vältida eitust** (`!`) muutuja nimedes või tingimustes, kui vähegi võimalik — see teeb koodi lugemise keerulisemaks ("aju peab lisaks protsessima"). Parem on kasutada positiivset nime (`isLoggedIn`), mitte negatiivset (`isNotLoggedIn`).

### Koodinäide (`frontend/src/App.vue`)

```vue
<div class="navbar-nav">
  <RouterLink class="nav-link" to="/">Kodu</RouterLink>
  <RouterLink class="nav-link" to="/atms">Pangaautomaadid</RouterLink>

  <div v-if="isLoggedIn">
    <RouterLink class="nav-link" to="/">Logi välja</RouterLink>
  </div>
  <div v-else>
    <RouterLink class="nav-link" to="/login">Sisse logimine</RouterLink>
  </div>
</div>
```

### Päriselu analoogia

`v-if`/`v-else` sisse- ja väljalogimise lingi jaoks on nagu ukse sissepääsu ja väljapääsu silt — mõlemad silid ei saa korraga näidata "sisenemine" ja "väljumine" ühel real: kas sa oled sees (näita "välju") või oled väljas (näita "sisene").

## `isLoggedIn` andmemuutuja ja `beforeMount` kontroll — `2:04:37` {#is-logged-in}

### Selgitus

Kuna menüü peab töötama korrektselt ka pärast lehe värskendamist (`refresh`), ei saa `isLoggedIn` väärtust hoida ainult mällu — see kaob refreshi ajal. Selle asemel loetakse iga kord, kui `App.vue` komponent laetakse (`beforeMount` hetkel), väärtus **`sessionStorage`-st**.

**`sessionStorage.getItem('userId')`** tagastab `null`, kui võtit pole olemas — see on JavaScript-i märk "midagi ei leitud" (erinevalt `undefined`-ist, mis tähendab tavaliselt "muutuja on defineerimata").

### Koodinäide (`frontend/src/App.vue`)

```vue
<script>
import { RouterLink, RouterView } from 'vue-router'

export default {
  name: 'App',
  components: { RouterLink, RouterView },
  data() {
    return {
      isLoggedIn: false,
    }
  },
  beforeMount() {
    let userId = sessionStorage.getItem('userId')

    if ((userId === null)) {
      this.isLoggedIn = false
    } else {
      this.isLoggedIn = true
    }
  },
}
</script>
```

### Skeem

```
Lehe laadimine / refresh
        │
        ▼
  beforeMount() käivitub
        │
        ▼
  sessionStorage.getItem('userId')
        │
   ┌────┴────┐
   ▼         ▼
 null      väärtus olemas
   │         │
isLoggedIn  isLoggedIn
 = false     = true
   │         │
   ▼         ▼
"Sisse      "Logi
logimine"    välja"
  näidatakse  näidatakse
```

### Päriselu analoogia

`beforeMount` kontroll on nagu turvavärava kontroll iga kord, kui keegi hoonesse siseneb (isegi kui nad on käinud varem) — süsteem ei "mäleta" külastajat automaatselt üle uste sulgemise, vaid kontrollib iga kord uuesti kaardi (sessionStorage) olemasolu.
